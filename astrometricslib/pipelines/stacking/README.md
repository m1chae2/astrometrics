# Stacking

This pipeline combines many individual pictures (sub-exposures) of the same target into one master image. Adding aligned pictures together makes real stars and galaxies brighter, while noise that occurs randomly in each picture — camera read noise, heat noise — tends to cancel out. Before combining, the pipeline also rejects temporary artifacts such as satellite trails, cosmic rays, and hot pixels.

## What the pipeline does, in order

1. **Group frames by exposure length.** Frames taken with different exposure times cannot be combined directly, since a longer exposure collects more light per pixel. The pipeline sorts frames into exposure groups, stacks each group on its own, then combines the group stacks so no frame's light is wasted.
2. **Check that frames within a group agree.** Three checks run before stacking:
    - `frame_homogeneity.py` checks that gain settings match across the group's frames.
    - `frame_quarantine.py` measures each light frame's stars and moves a frame with clouds or trailed stars into an `_excluded` folder beside it. Spectral frames are skipped, because their streaks are the spectra. The step is described below.
    - `background_homogeneity.py` compares each frame's background brightness against the rest of the group to catch a frame taken through cloud or twilight. It finds one sudden jump in sky level, so a gradual build-up of cloud can pass it.

   A frame that disagrees with the group is excluded rather than stacked.

   **The quarantine step.** It compares each frame with the other frames of its own session (frames of one camera, filter and exposure length less than four hours apart) and moves a frame when:
    - it has fewer stars than half the session's median star count (cloud, or heavy trailing); or
    - its stars are much less round than the session's: roundness (a star's narrow width divided by its wide width, 1.0 for a circle) is below 0.80 and at least 0.15 below the session median.

   A satellite or aircraft trail does not trigger it, because the stacker's pixel rejection removes those. A session of fewer than eight frames is left alone, because its median cannot be trusted. If the step would move more than a quarter of a session, it moves none and logs why, because the session itself is then the problem. The measurements come from `shared/quality/raw_frame_check.py`.

   The step moves frames and never deletes them. Each `_excluded` folder holds `excluded_frames.json`, which records every frame's original path, why it was moved and what was measured. The scanner and the downloader both leave `_excluded` alone, so moved frames neither return to the target nor download again. Two calls work with them: `QualityDiagnostics.frame_quality(target, kind="quarantine_preview")` shows what the check would move without moving anything, and with `include=["excluded"]` lists what was moved; `ProcessingPipelines.restore_excluded_frames(target, apply=True)` moves the frames back. `scripts/restore_excluded_frames.py` is the command-line form of the last one. The setting `quarantine_bad_frames_enabled` in `[Processing.Siril]` turns the step off. The step is recorded in the stack's gate record as `frame_quarantine`: `passed` when at least one session was judged and none was over the cap, `failed` when a session had too many bad frames to move (the bad frames are still in the stack), and `not_checked` when no session had enough readable frames, or when the step is off or the stack is spectral.
2b. **Skip a stack that would come out the same.** Stacking a target rebuilds every stack it has: one per filter and one for spectra. Before it stacks, `stack_inputs.py` writes down what the stack is made from: the frames (path, size and modification time), the calibration frames the library picks for them (darks, biases and flats, with their modification times), the settings that change the pixels, and a version number of the stacking code. It saves that record, with a hash of it, next to the stack as `<stack name>_inputs.json`. On the next run it builds the record again. If the hash matches and the stack file is still there, the stage keeps the stack and returns its path. If not, it logs what changed (for example `3 frame(s) added`, `the flat frames changed`, `settings changed: get_stack_weight`) and rebuilds. Adding luminance frames to a target no longer rebuilds its spectral stack. The skip never triggers when the stack has no record (a stack made before the records existed is rebuilt once) or when the inputs cannot be read. To rebuild anyway, pass `force=True` to `ProcessingPipelines.stack`, `--force-restack` to `scripts/run_all_target_processing.py`, or turn off `skip_unchanged_stacks_enabled`. The record travels with the stack into the `_previous` folder. The version number is `STACKING_ALGORITHM_VERSION` in `stack_inputs.py`; raise it whenever a code change would give a different stack from the same inputs, or old stacks will be called up to date. Only the stacking step is skipped: astrometry, photometry and spectroscopy still run on the stack that is there.
3. **Line up the frames.** Frames must be aligned pixel-for-pixel before combining. `group_alignment.py` aligns each exposure group's stack (for images by matching stars, which also removes the small rotation and scale between nights); `spectral_frame_alignment.py` aligns a batch of already-calibrated spectral frames without star detection, since a dispersed spectrum has no normal point-source star pattern to align on; `group_derotation.py` lines up spectral exposure-group stacks onto one common trail tilt.
4. **Check the flat frames.** A flat frame is a picture of an evenly lit surface. Dividing each light frame by the master flat (the combined flats) removes vignetting (darker corners) and dust shadows. The division also copies the master flat's noise into every light frame. That noise is the same pattern in each frame, so stacking does not average it away unless the frames were dithered (moved a few pixels between exposures). `flat_calibration.py` measures the flat set before Siril builds the master:
    - how many frames it has, how bright they are (as a share of full scale), and how noisy the master flat will be (the noise of one frame divided by the square root of the frame count);
    - whether the noise is above the limit, 0.5% of the flat's level. The limit is set so that the fixed pattern adds under 3% to the variance of a typical stack's own noise.

   When the noise is above the limit, the pipeline adds Siril's `gauss` command to the script that builds the master flat. The Gaussian is just wide enough to reach the limit (at most 8 pixels). Siril mirrors the image at its border. Vignetting and dust shadows are many pixels wide and survive the blur. The pixel-to-pixel sensitivity differences, about 1% on a CMOS sensor, do not. Taking more flats is the better cure, because the blur is a fallback. A colour (Bayer) sensor's flat is measured but not blurred, because the blur would mix the colour channels.

   Each finding is recorded in the stack's quality summary: `flatFrameCount`, `flatNoiseFraction` (relative noise of the master flat before smoothing, 0.005 is 0.5%), `flatSmoothingSigmaPx` (the blur width, empty when none was applied) and `flatCalibrationIssues` (one sentence per problem). Each issue also appears in the summary's flag reasons, which flags the stack.
5. **Run the stacking engine.** `stack_runner.py` hands each batch of frames to a stacking engine, the program that calibrates, registers (lines up) and combines them with pixel rejection. Siril is the engine in use. The runner adds the two safeguards spectroscopy needs (its dispersed images cannot use Siril's normal star-based registration). The engine's contract is in `drivers/interfaces/stacking_driver.py`: a `StackSettings` goes in and a `StackRunResult` comes out, so nothing else in the pipeline reads Siril's commands or files. The quality summary records the engine's name and version (`stackingEngine`, `stackingEngineVersion`). To use another program, write a subclass of `StackingDriver` (see `drivers/siril_stacking_driver.py`); the runner and stage need no change. When the frames of an imaging stack have different exposure lengths, `exposure_weighting.py` asks Siril to weight each frame by its noise (`-weight=noise`) unless a weight is configured. A short frame carries less information than a long one, so equal weights add noise: about 17% for the 30, 60, 120 and 300 second frames of the M 27 stack, where the weighting lowered the measured pixel noise by 13%. A restack first moves the stack it replaces, with its pictures, into a `_previous` folder (see `previous_stack.py`), and puts it back if the restack fails.
   After the engine finishes, `stack_crop.py` trims the stack and its rejection map back to where the pixel noise falls to within 15% of the interior's. Frames shift between nights, so the edges of a stack of several nights are covered by fewer frames and are noisier: on the M 27 stack the first 100 columns and 400 rows had 18% to 33% more noise. The trim measures the noise in 25-pixel strips and finds the noisy run on each side. It then cuts out the largest box with the original proportions (a square stack stays square) that fits in what is left, as near the image centre as the clean area allows. It changes nothing on a stack with clean edges (the Bubble Nebula, M 81 and M 13 stacks), it refuses a trim of more than a quarter of a side, and it moves the sky-coordinate reference with the crop. The setting `trim_noisy_stack_edges_enabled` (default `true`) turns it off.
6. **Judge the result.** `stack_quality.py` holds the rules for deciding whether a stacked image is good enough to use. `exposure_saturation.py` checks whether a given exposure length saturates the brightest star in the field, and `exposure_group_report.py` records a description of the exposure groups a stack was built from.
7. **Save a picture of the stack.** `stack_preview.py` saves two pictures next to the finished stack: a JPEG named `<stack name>_preview.jpg` and a FITS file named `<stack name>_processed.fits`. Both hold the same stretched picture, the same way up (Siril writes a JPEG upside down compared with its FITS source, so the JPEG script flips it first). The FITS file holds 32-bit numbers between 0 and 1, so the image viewer can zoom into it without the JPEG's 8-bit banding. It keeps the stack's observation keywords (exposure time, telescope, object) and a header note that it is a stretched picture and not linear data. A stack holds linear data, which looks almost black on a screen, so up to four steps run on a scratch copy first:
    1. GraXpert removes the sky's brightness gradient, if the `[Processing.GraXpert]` setting names a GraXpert command. Its AI model learns what the smooth background looks like and subtracts it.
    2. Siril's Autostretch sets the black point from the image's own background noise and bends the brightness curve so the sky lands on a chosen grey level. `sky_level.py` chooses that level from the stack itself. It measures the brightest extended light (nebulae and galaxy halos, not stars) as a signal-to-noise ratio above the sky, then places that light at a fixed display brightness. A faint target needs a lot of lift, so its sky comes out lighter (up to 0.20) and its faint structure stays visible. A lighter sky also lifts the grain into view, which is why the limit is 0.20 and not Siril's own 0.25. A bright target needs little, so its sky comes out darker (down to 0.11) for more contrast. On the ASI533MM Pro stacks it gives 0.20 for M 101, M 81, M 27 and the faint star fields, about 0.19 for the Bubble Nebula, and 0.11 for M 42. A stack whose sky cannot be measured gets 0.18. The rule has one tuned number. It was set by eye on the Bubble Nebula stack, where the user judged the earlier, darker sky too black and chose a level near 0.20 from rendered options.
    3. Cosmic Clarity removes noise from the stretched picture, if the `[Processing.CosmicClarity]` setting names its denoise program. The `denoise_strength` setting (0 to 1, default 0.9) controls how much it removes. It runs after the stretch because Autostretch measures the noise level of the image it stretches: after a denoise, it measures less noise and turns the contrast back up, so the remaining noise looks as strong as before and large blotchy patches appear. On the M 13 stack, the visible grain fell by 22 percent with the denoise first and by 73 percent with the denoise after the stretch. A strength of 0.9 cut the sky grain by 14 to 39 percent compared with 0.75 on four stacks, and left star brightness unchanged. The program only reads and writes the `input` and `output` folders next to it, so the step takes an exclusive lock, refuses to run if `input` already holds files, and deletes only its own files.
    4. Star toning (`star_tone.py`) dims the stars in proportion to their brightness and compresses the brightest values below pure white. The stretch makes nearly every star a small white dot of about the same brightness. The toning separates the light above the local background, raises it to a power (1.8) so that fainter stars dim more than bright ones, and then applies a soft roll-off above 0.65 so a saturated core ends near 0.92. Only light that stands out by more than 0.05 to 0.12 above the background is dimmed, so low-contrast structure (the knots along a galaxy's spiral arms) keeps its detail. The background and nebulae are not touched. The setting `preview_star_tone_enabled` in `[Processing.Siril]` (default `true`) turns it off. The power and the knee were chosen by eye on the Bubble Nebula stack and are not validated on other targets.

   A stack of a bright extended object, such as the Moon, takes a different route. The Moon's sky is about 3000 times fainter than its disc, so the normal stretch would turn the whole disc white and lose the craters. `bright_object.py` recognises this case from the data: it counts what share of the picture the normal stretch would push to white. A nebula, galaxy or star field leaves at most 0.12% white (the cores of the brightest stars). The Moon leaves 4.4%. A share of 1% or more switches to one Siril script with a different stretch. The black point is the sky level, the white point is near the top of the object's own brightness, and the curve places the object's median at a fixed grey (0.55). GraXpert and the denoise are skipped, because GraXpert would treat the Moon's glow as sky background and the denoise could smooth the surface. The rule is checked on the Moon only. A planet is too small to reach the 1% share, so planet stacks use the normal route.

   Leaving a step's setting blank skips that step. Without Cosmic Clarity and the star toning, one Siril script stretches the image and saves the JPEG. Both pictures are for people only. Nothing in the pipeline reads them, and the stack file is not changed, so photometry and spectroscopy still read the linear data. If GraXpert or Cosmic Clarity fails, the picture is made from the result of the step before it. If Siril is missing or fails, the pipeline logs a warning and keeps the stack. Each step that works logs a line saying so, and one `Preview steps:` line lists every step and its result (for example `GraXpert done; Siril stretch done; Cosmic Clarity done; Star toning done`). A stack made from the viewer shows these lines in its job log, so you can see which steps ran. The step removes any older pictures first, so they always match the current stack. A failed FITS copy does not fail the preview: the JPEG alone is still recorded. The Image Processing viewer's Stretch view shows the JPEG when it is at least as new as the stack.

   The step then records the FITS picture as the target's processed image (`processed_image`), or the JPEG when no FITS was made. The Image Viewer shows it first, with the same zoom and pan as the FITS viewer, and does not stretch it again. It replaces a processed image that a person attached to the target (the attached file stays where it is), and it skips a stack that the target does not show (a target with stacks from several telescope setups shows one). `scripts/backfill_stack_previews.py` makes previews for stacks that already existed and records them the same way.

## Where each piece lives

The folders follow the layout in `pipelines/README.md`.

- `stage.py` is the coordinator: it runs the steps above in order for one target, and is what the rest of the codebase calls to stack a target's frames.
- `stack_runner.py` runs the stacking engine (step 5): exposure groups, registration retries and the final read of the engine's files. The engine is the only code that stacks a batch's pixels. `processing/` combines the group stacks.
- `pre_processing/` checks and prepares the inputs: the gain and background homogeneity checks, the flat-frame check, and the input-quality judgement (`StackingInputQuality`). See its README.
- `processing/` lines up and combines frames: exposure groups, group alignment, spectral frame alignment and derotation. See its README.
- `post_processing/` judges and presents the finished stack: the quality thresholds, the saturation check, the exposure-group report, the output-quality judgement (`StackingOutputQuality`), the bright-object rule, the sky level rule and the preview picture. See its README.

`stage.py` stores the two judgements on the stack's quality summary as `inputQuality` and `outputQuality`. Each carries its own flag reasons, so a reader can tell a bad input from a bad result.

## Where the output goes

The pipeline writes its output (stacks, group stacks, rejection maps, registration files, previews and processed pictures) to `<stacks_path>/lights/<target>/`. The `stacks_path` entry in the `[Image Library]` section of the configuration sets that folder. Without it, the output goes beside the raw frames, in the frames path. The setting lets the large raw frames stay on one disk while the output goes to another. The backend's image server looks for a file in the frames folder first and then in the stacks folder, so the viewer asks for one URL either way. `scripts/move_stacks_to_stacks_path.py` moves the files that already exist and updates the paths in the database.

The raw frames can sit on a network drive. The pipeline does not copy them first. Siril reads each frame once through a symlink and writes its working files to `~/Siril/Work` on the local disk. Set `frames_mount_point` in the same section to the folder where that drive mounts. While nothing is mounted there, downloads and file sorting stop with an error instead of writing frames to the local disk. The pipeline never rewrites a raw frame.

## A note on scope

This pipeline produces one combined image (or one per exposure group/camera setup) from a target's raw frames. It does not detect stars, solve the sky position, or measure brightness — those are astrometry and photometry, which read this pipeline's output rather than duplicate its work.

This README describes the overall flow. For exact behavior, read the code — the code is always the source of truth.
