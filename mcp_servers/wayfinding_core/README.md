# Wayfinding MCP server

This folder exposes the Wayfinder interface (observatory control, planning, execution) as an MCP (Model Context Protocol) server, so an AI agent can call the library's tools directly. It reuses the registry and reflection engine in `mcp_servers/common/`. Run it with `python -m mcp_servers.wayfinding_core`.

## What each file is for

- `__main__.py` — the server executable.
- `definition.py` — registers every public method of the three Wayfinder branches as a tool.
- `tool_manifest.json` — the reviewed list of tools with a class, category and disposition for each. The server offers a client only the tools this file allows. See the next section.

## Which tools the server offers

When the server starts, it removes every tool that the manifest does not allow for the chosen profile. The profile comes from the `ASTROMETRICS_MCP_PROFILE` environment variable. The default is `investigator`, which offers tools that look things up, calculate or measure, plus one write: bringing a target's new frames from the telescope computer into the library (class `ingest`, tool `observatory_remote_sync_frames`), which adds files and records and never deletes. It offers no tool that commands a device, changes settings, or runs code. The `developer` profile also offers the tools that run the project's tests and builds.

The rules fail closed. A tool that is missing from the manifest is not offered, so a new public method stays hidden until someone reviews it. A missing manifest withholds every tool. A tool can also carry an `interim_block`, which hides a read-only tool until a known problem is fixed.

Do not edit `tool_manifest.json` by hand. The script `python -m mcp_servers.inventory --write-runtime-manifests` writes it from the reviewed decisions. `test/test_profile.py` fails if a registered tool has no manifest entry.

## What a client sends

A client sends JSON, and the tools pass it to the Wayfinder methods unchanged. The methods accept what a client can send:

- `target`: a target id such as `"M 52"`. A remote folder name such as `"M_52"` also matches. The library reads the stored targets again before the lookup, so a target another program changed is seen. An unknown id raises `NotFoundError` with a message that names it.
- `position` and `destination` (a sky position): a dictionary `{"ra_deg", "dec_deg"}`. A dictionary that is not a position raises `InvalidArgumentError` that names the expected keys.
- `get_visibility` takes `objects` as names or ids (looked up in the library and then in SIMBAD, an online star database) or `{"id", "ra_deg", "dec_deg"}` dictionaries, and `time` and `end_time` as `"now"` or ISO 8601 strings. An offset such as `-06:00` is honored, and a string with no offset means UTC.

A slow method (marked `@background_job`) is called with `register_job=True` and records its own job; see `mcp_servers/README.md`. `observatory_remote_sync_frames` for one target therefore records a `remote_sync` job too.

For exact behavior, read the code. The code is the source of truth.

## Tools for judging a night

These tools answer the questions that come up during and after a night of imaging:

- `visualization_render_fits` returns a real image of a frame or stack, with a stretch. A crop (`crop_center_x`, `crop_center_y`, `crop_size`) zooms on one place so trailing can be judged by eye. It replaces the older tools that returned the picture as base64 text, which the reply limit cut in half.
- `diagnostics_frame_quality` measures frames. It picks them by filter, file range (a bare number such as `013` means frame 013) and time, and leaves out spectroscopy frames unless asked. The code that picks frames is `pipelines/shared/quality/frame_selection.py`. The answer also has `trends`: it looks at the newest `trend_frames` frames and flags a steady drift in star width, star count or sky level when it passes `trend_threshold_percent` (code in `pipelines/shared/quality/frame_trends.py`).
- `observatory_history_frame_guiding` (wayfindinglib) cuts the stored guide-log samples to each frame's exposure window. It reports the guide error inside each window and lists the frames well above the group's median. With `include=["quality"]` each row also carries the frame's star count, star width, roundness, trail length, sky level and quality flags, so image quality and guide error sit in one table (about a second a frame, at most 60 frames).
- `observatory_history_get_live_session_status` (wayfindinglib) reads tonight's Ekos and KStars logs. With `include` it adds sections of the Ekos record, such as `autofocus_runs` (with each focus curve and whether the fit succeeded), `aborted_captures`, `guide_state_events`, `mount_state_events`, `align_events` and `mount_positions` (declination, altitude, azimuth, pier side), so the cause of a flag can be read. The log records when a capture aborted but not why; the reason has to be read from the guider and mount events around that time.
- `diagnostics_spectral_frame_check` measures a target's raw spectrum frames: the zero-order position, the streak's tilt and width, the sky, the peaks of the zero order and the spectrum, and every saturated patch with its distance along the spectrum from the zero order (a clipped zero order is normal; clipped spectrum pixels lose data). `predict_exposure_seconds` scales the peaks to another exposure and says whether the spectrum would clip there. The summary groups frames by exposure length and by pier side (median, smallest and largest tilt), which answers whether the tilt depends on the side of the pier. The code is `pipelines/shared/quality/spectral_frame_check.py`. `diagnostics_frame_quality` reports `spectral_light_frames_in_target` next to `light_frames_in_target`, which counts imaging frames only.
- `planning_get_visibility` with an `end_time` also lists `sun_events` under `night`: when the Sun reaches sunset, civil, nautical and astronomical twilight, interpolated between time steps.
- A frame sync (`observatory_remote_sync_frames`) now writes log lines and a `N of M frames transferred` progress message into its job while it runs, so `jobs_query` shows it moving.
- `app_status` (backend) now reports the live app: `telescope` (RA/Dec, Alt/Az, tracking or parked, ambient temperature and humidity, camera temperature and state, focuser, filter, and the mount's pier side and tracking switches read from its INDI properties), `guiding` (running, RMS, the newest 20 samples), `indi_devices`, and `indi_properties` for one `device`. It asks the backend, which holds the hardware connection. `observatory_mount_status`, `observatory_imaging_status` and `observatory_safety_status` are blocked because the MCP process has no hardware connection: their device sections would return `0`, `[]` and `unknown`, or open the connection with a device command.
- `target_query` reads targets in short records: one row per target (frame counts, cameras, last night imaged, stack flags), or with `detail=full` one target with its frames grouped by night, filter, exposure and camera and its quality summaries condensed. It covers what `target_get` and `target_list` returned, whose answers overflowed the 40,000 character reply. `detail=cameras` lists the cameras used and `detail=camera_index` each target's frames per configured camera. `target_imaged_field_centers` lists the imaged sky positions.
- `star_query` has `spectral_class`, `search`, `has_photometry`, `has_catalog_magnitude`, `order`, `detail=class_counts`, `detail=target_counts`, `detail=overlay` (a target's stars placed in pixels on its stacked image) and `detail=analysis` (the old `full`). Single-frame photometry detections (ids ending in `:Star_<n>`) are hidden unless `include_unresolved` is true. An analysis record holds the star's own spectral type and how well it matched, the closest reference types, the absorption features and emission lines found, and the cycle and repeating-dip verdicts, about 2 KB per star, with no raw arrays. With `spectral_class` the best-matched stars come first. The code is `astrometricslib/pipelines/shared/star_analysis.py`. `star_get` returns one star's full record.
- `planning_find_sources` (library targets and stars near a point, brightest first, capped, with the total) and `planning_lookup_coordinates` (a position) replace `planning_get_sources`, `planning_get_library_star_summaries` and `planning_resolve_target_coordinates`, which returned whole target records.
- `visualization_plot` draws one chart (`kind` is `dashboard`, `star`, `astrometry`, `photometry`, `spectroscopy`, `focus` or `asteroids`) and returns a PNG image with the panel titles, not the text `Figure(1600x900)`.
- Slow read tools run as background jobs: `diagnostics_frame_quality`, `diagnostics_spectral_frame_check`, `diagnostics_stack_quality`, `calibration_assess_flats`, `observatory_history_query`, `target_imaged_field_centers` and `planning_deep_catalog_status` (when it estimates the catalog size). A call that finishes within 20 seconds returns `{"jobId", "result"}`; a slower one returns a job id to follow with `jobs_query` (`detail=result` gives the answer). These jobs appear in the app's job history with the type `diagnostics`.
- `processing_remake_preview` makes a target's preview picture again (GraXpert, Siril stretch, Cosmic Clarity, star toning) from the stack that is already there, so a changed post-processing setting shows up without a restack. `denoise`, `denoise_strength` and `star_toning` apply to that run only and are never written to the configuration. By default the old pictures are copied into a `_previous_preview` folder beside the stack first (one earlier set is kept) and are put back if the run fails. The reply lists the steps that ran and says whether the stack file was left unchanged. Class `process`; it writes only the preview JPEG, the processed FITS and the target's processed-image pointer. The code is `pipelines/stacking/post_processing/preview_remake.py`; the overrides are `PreviewSettings` in `stack_preview.py`.
- `processing_stack` stacks a target the way the app's Stack button does. `kind` is `imaging` or `spectral` (they are never mixed), and `filter_name`, `first_file`, `last_file`, `since` and `until` choose the frames. `plan_only` lists the chosen frames without stacking. Its class is `process`: it runs the app's own stage, so bad frames are set aside (never deleted), one previous stack is kept, and the target is saved. `frames` stacks an exact list of frames instead.
- `processing_stack_summary` gives one short answer for a target's stack. `observatory_remote_frame_status` counts a target's frames on the telescope, on the drive and in the library. `jobs_query` marks a job idle for over an hour as `looks_stale`.
- The `observatory_` tools follow the topic groups of `Wayfinder.control`: `observatory_mount_*`, `observatory_imaging_*`, `observatory_guiding_*`, `observatory_remote_*`, `observatory_history_*`, `observatory_safety_*` and `observatory_equipment_*`. `definition.py` reflects each group under its own prefix, so `control.mount.park` becomes `observatory_mount_park`. Each group with readable state has one `*_status` tool, whose `include` argument picks the sections of the reply. The mount's `position` and `destination` arguments take a `{"ra_deg": ..., "dec_deg": ...}` dictionary.
- `planning_get_visibility` (wayfindinglib) says where objects are at one moment: altitude, azimuth, rise, set and transit, and with `include=["meridian"]` the hour angle and flip status. With an `end_time` it builds a night table for up to 30 objects: horizon clearance (with blocked sky ranges such as trees), meridian crossings, and the Sun and Moon. Without `objects` it covers every library target, highest first.
- The other planning tools follow `Wayfinder.planning`: `planning_get_advisory` (`kind` is `quality` or `calibration`), `planning_calculate_panels` and `planning_create_mosaic`, `planning_create_plan` (`kind` is `sequence`, `package`, `empty_session` or `scheduled_session`), `planning_edit_queue`, `planning_get_plan` and `planning_deep_catalog_status`. The ones that write are not offered to the AI.
