# Shared pipeline tools

This folder holds code that more than one pipeline (astrometry, photometry, spectroscopy, asteroid detection, stacking) depends on. Nothing here runs on its own. A pipeline's own `pipeline.py`, `runner.py` or `batch.py` calls it.

Terms are defined in the [glossary](../../../documentation/Glossary.md). This document also defines each term the first time it appears.

## Terms used here

- *Frame*: one camera exposure file. *Light* frames show the sky. *Dark*, *flat* and *bias* frames measure the camera itself (its heat signal, its pixel-to-pixel sensitivity and its fixed electronic offset) and are used to correct the lights. A *stack* is the image made by aligning and averaging many light frames.
- *Session*: the frames from one continuous run with the same setup. Each pipeline states its own grouping rule.
- *FITS*: the standard astronomy image file format. Its text header holds named cards (keywords) such as `DATE-OBS` and `INSTRUME`.
- *Plate solving*: working out where in the sky an image points by matching its stars to a reference star catalog. Its result is a *WCS* (World Coordinate System), the header formula that converts a pixel position to a sky position.
- *SIMBAD* is an online database of named astronomical objects. *Gaia DR3* is the European Space Agency's catalog of precise positions and brightnesses for over a billion stars.
- *Arcsecond* (arcsec): 1/3600 of a degree. *Magnitude*: the astronomer's brightness scale, where larger numbers are fainter.

This folder sits below the five pipelines, so nothing here imports a specific pipeline (`pipelines/<name>/`), `pipelines/tasks.py` or `pipelines/target_batch.py`. When shared code needs a pipeline's function or class, the caller passes it in. `astrometricslib/test/test_layer_boundaries.py` enforces this. Code with only one pipeline as its user lives in that pipeline.

## What each file is for

- `analysis_context.py` — the shared container a pipeline run passes between its own stages. It holds the loaded image, the detected sources, and the results found so far. It also holds, for each star of the Gaia refit, its peak over the sky noise (`gaia_fit_peak_over_noise`), which the expected position residual reads (partly measured; see [AST-21](../../../documentation/library_design/validation/astrometry.md#ast-21)). A detected source is a point of light the detector found in the image, with a position and a brightness.
- `frame_grouping.py`, `frame_optics.py` — sort a target's frames by camera, optic, and role (light/dark/flat/bias), and work out which physical telescope or lens took a given frame. `frame_grouping.frame_exposure_seconds` is the one reader of a frame record's exposure length, used by stacking, the frame measurements and the stack membership.
- `frame_scanning.py` — finds image files on disk and reads them into frame records. It skips the output of processing: a file whose name contains `_stacked`, `starless`, `starmask` or `processed`, or whose header has a positive `STACKCNT` (Siril writes it only on a stack, and keeps `IMAGETYP = Light Frame` on it). The sorter files such a stack under `others`, not under the lights. Each record stores the file's size and modification time, and a re-index with `refresh_headers` does not open a file that still matches them. `file_state_matches` is that one rule; the frame measurement job applies it to its own stamp.
- `registration_record.py` — writes and reads `<stack name>_registration_frames.json` beside a stack: Siril's transform for each frame, the frame paths in Siril's order and the columns and rows trimmed from the stack's edges. The stacking run writes it (`build_registration_record`, `write_registration_record`) and the astrometry run reads it (`read_registration_record`) to find the target on each raw frame. A stack made before the record existed has none, so a reader gets `None` and the stack must be stacked again.
- `quarantine_path.py` — the name of the `_excluded` folder where stacking moves frames with clouds or trailed stars, and the one test for "is this path inside it". Frame scanning skips that folder so moved frames do not rejoin the target.
- `previous_stack_path.py` — the name of the `_previous` folder where a restack keeps the stack it replaced. Frame scanning skips that folder so the old stack never counts as an input.
- `session_identification.py`, `target_sessions.py` — group a target's frames into observing sessions and work out which stars an image sequence contains.
  - **Star identifier.** `session_identification.py` takes the star identifier from its caller (the astrometry pipeline's `StarIdentifier`), typed as the `SessionStarIdentifier` protocol, which names the methods it calls.
  - **Saving a solve.** It also holds `write_wcs_to_fits_header`, which saves a solved WCS into a FITS header. It writes the SIP distortion terms (Simple Imaging Polynomial, a standard correction for lens distortion) with the sky map and deletes the sky-map keywords of any earlier solve first.
  - **Which header map is a solution.** A frame's own header map is reused only when the header marks it as plate solved (`fits_access.header_is_plate_solved`: both sky axes, and `PLTSOLVD` set true or SIP distortion terms). The map INDI writes from the mount's pointing is not one: it can sit about a minute of arc from the true position (design estimate; see [astrometry design estimates](../../../documentation/library_design/validation/astrometry.md#design-estimates), AST-D19). A caller that puts a solved stack's map on a frame passes `trust_image_wcs=True`; photometry borrows only the stack of the frame's own camera and focal length (`target_center_hint.resolve_solved_stack_wcs`).
  - **A wrong solution.** `plate_solution_problem` says a run's solution looks wrong when under 10% of its stars match a catalog star, or when the matched stars sit a median of more than `MAX_MEDIAN_CATALOG_OFFSET_FRACTION` (0.5) of the catalog match radius from their catalog positions. The radius is `CATALOG_MATCH_RADIUS_ARCSEC` as the run resolves it, so the limit follows the plate scale. A fixed limit in arcseconds could not fire, because no match sits farther than the radius; a wrong solution's chance matches have a median of about 0.71 of it. In a dense field chance matches alone can pass the 10% test, so the median test is what catches a wrong solution there (design estimate; see [astrometry design estimates](../../../documentation/library_design/validation/astrometry.md#design-estimates), AST-D19). A reused header map that fails either test is replaced by a fresh solve. A photometry session that fails logs a warning naming the session and its reference frame, and saves none of its stars.
  - **Fit quality.** When a frame is plate-solved during session identification, the result records the solver's fit residual RMS (root mean square of the leftover distances between fitted and reference star positions) in arcsec and its matched-star count. Both are `None` when the sky map came from the file's own header or the solver returned no statistics.
- `camera_passes.py` — plans which cameras a batch run should process, and which targets go to each camera pass.
- `analysis_configuration.py` — ties one analysis run to the camera and optic of the image it analyzes. A stack-based stage (astrometry, spectroscopy) reads the camera and optic from the stack's own header (`INSTRUME`, `FOCALLEN`), not from the target's first frame, which can come from another camera. A frame-based stage (photometry, spectral variation, asteroid search) takes the camera and optic of its stack (the imaging stack, or the spectral stack for spectral variation) and keeps only the frames of that camera and optic. Each other frame is left out, and the run reports it: a log warning and a line in the job's log (`1 frame from Nikon DSLR DSC D5300 left out: different camera than the analyzed stack (...)`), a rejected frame in the photometry quality summary, and a skipped frame in the spectral variation result. A target with stacks for several configurations is analyzed for the one recorded stack (`target.stacking.stacked_image`), so frames of the others are left out. With no stack, the camera and optic most of the frames share are used. Camera aliases from the camera profiles count as the same camera. `run_analysis_pipeline` builds the run's parameter context from this camera and optic (`equipment_parameter_context`).
- `angles.py` — angle helpers. `wrapped_ra_difference_deg(ra1, ra2)` subtracts two Right Ascensions (RA, the east-west sky coordinate, like longitude; its partner, declination or Dec, is the north-south coordinate, like latitude) and wraps the result into (-180°, 180°], so 359.9° and 0.1° are 0.2° apart. It accepts floats or arrays. Code that compares or searches around RA values calls it instead of subtracting, because RA wraps from 360° back to 0°. The asteroid detector and the astrometry star identifier use it.
- `catalog_star_identity.py` — decides whether two different catalog names refer to the same star. Two catalog rows within `SAME_STAR_POSITION_TOLERANCE_ARCSEC` (2 arcsec) of each other count as one star, or within `SAME_STAR_TOLERANCE_WITHOUT_GAIA_NUMBER_ARCSEC` (3 arcsec) when one row has no Gaia DR3 number, because a name-keyed row holds a SIMBAD position (measured; see [AST-11](../../../documentation/library_design/validation/astrometry.md#ast-11)). Two different Gaia numbers are never one star. It also holds `CATALOG_MATCH_RADIUS_ARCSEC` (10 arcsec), the largest distance between a detected star and a catalog entry for the two to count as one star (design estimate; see [astrometry design estimates](../../../documentation/library_design/validation/astrometry.md#design-estimates)). The astrometry star identifier and `star_recording.py` both use it.
- `catalog_star_identity.py` also holds the naming rules. `identity_rank` says which id a star is saved under: its Gaia DR3 number (`Gaia DR3 <source_id>`) first, then an HD, BD, CD or CPD name, then any other name. `display_name_rank` says which name a reader knows best: a proper, Bayer, Flamsteed or variable-star name first, then a bright-star catalog (HD, HR, HIP and the like), then other catalogs, then survey numbers, then Gaia numbers. `settle_names` gives a merged star its most familiar name and keeps the others as `aliases`. `POSITION_ONLY_SAME_STAR_RADIUS_ARCSEC` (3 arcsec) is how close a position-only (`FIELD_J`) star must be to another star to be the same star (measured; see [AST-22](../../../documentation/library_design/validation/astrometry.md#ast-22)).
- `star_recording.py` — the shared rule every pipeline uses to decide which stars are worth keeping, and how to save them to the star catalog.
  - **Only measured stars are saved.** A star record is kept only when it has a light curve or a spectrum (`catalog_access.holds_measurements`; the save step checks it too, so no caller can add an empty record). Photometry saves the stars it measured and spectroscopy the stars with a spectrum (`measured_only=True`). Astrometry and the viewer's Astrometry button never add a star: they only update the names, position and catalog facts of a star already saved. A star that was only detected and named is not stored; the names the overlay shows stay in each stack's `<stack>_identification.json`.
  - **The stack's named stars.** Astrometry writes the stars it named on a stack next to the stack (`solved_star_list.py`, `<stack>_solved_stars.json`). Spectroscopy reads them to name its zero-order stars, with the target's saved stars. The file carries the stack's stamp (`stack_sidecar.py`), so a list from before a restack is not read.
  - A named star found near a saved row of another catalog's name is saved as one row, under the better id by `identity_rank`, with the more familiar name. When a run finds both rows of such a pair already saved, it merges them into the row with the better id (`merge_cluster`).
  - A named star with a saved position-only row within 3 arcsec takes that row's data (the nearest row, and each row goes to one star only), and the position-only row is deleted after the save. Data is only added, never overwritten.
- `quality/notices.py` — builds the notice rows (warnings that are not gates) so a job can list them. `record_camera_profile` in `applied_camera_profile.py` stores the "camera has no profile" row when it is given the run's context.
- `applied_camera_profile.py` — records which camera profile (the `AppliedCameraProfile` model lives in `models/applied_camera_profile.py`) (sensor characteristics, saturation threshold) a pipeline run actually used, on that run's quality summary.
- `target_position.py` — gives a target the sky position of its object. It looks the target's name up in SIMBAD and writes that position. It falls back to a solved image's center only when the name does not resolve, and then marks the target `position_unverified`. The same fallback applies when the catalog position lies outside the solved image (plus a 15 arcmin margin) or when the id and common name disagree. It never changes a position that is already set. A target with a set position but no SIMBAD object type gets only that type (and a missing major axis) from the same lookup, once; `FILL_TYPE_ONLY` reports it, and a target that has a type is not looked up again. `scripts/backfill_target_object_types.py` still fills every target at once without running astrometry. It never gives one to a planet, the Moon, a comet or a calibration target. Positions are ICRS at epoch J2000. The astrometry runner and `scripts/audit_target_positions.py` use it.
- `target_center_hint.py` — turns a target's catalog RA and Dec into a starting position hint for plate solving.
- `target_camera_index.py` — summarizes each target's light frames per configured camera: how many frames each camera took and the time of the newest one. The user interface's target list uses it to filter by camera and to sort by the most recently imaged. A camera writes its name into FITS headers in its own spelling (for example `Nikon DSLR DSC D5300`), so the module matches names to the configured camera names through `camera_identity`, which reads each camera profile's alternate spellings. `TargetCatalog.query(detail="camera_index")` calls its `build_target_camera_index`. A frame from a camera that is not configured still counts toward a target's newest frame time, but not toward any camera.
- `target_overview.py` — builds the short target records that `TargetCatalog.query` returns. The list form has one row per target (name, position, frame counts, cameras, last night imaged, whether it has a stack). The single-target form groups the frames by night, filter, exposure and camera, and cuts the quality summaries down to flags and headline numbers. It only reads, so looking at a target never marks it as changed.
- `target_records.py` — reads and writes `Target` records in the catalog database. `PROCESSED_IMAGE_EXTENSIONS` lists the endings of a finished image (`.jpg`, `.jpeg`, `.png`, `.tiff`, `.tif`); `TargetCatalog.reindex_frames` makes such a file the target's processed image instead of a frame. A process keeps one object per target: a target handed out by `get` stays the object the catalog holds, so a job that edits it for minutes (a stack) still saves its edits. `list` reads the stored targets fresh and updates a held target in place only if it has no unsaved edits. The update keeps each held frame object (a frame whose path is still stored is refreshed in place, new paths are added, gone paths are dropped), so a stack that stamps the frames it holds does not lose its stamps to a refresh. A save writes only the targets that were touched and really changed since they were read or last saved, so a copy that was only looked at cannot overwrite another program's edit. `read_saved_target` reads one record straight from storage, to check what a save wrote. `save_quality_stamps` saves only the frames' measurement stamps, merged into the stored target under the storage lock (`merge_quality_stamps`), so a long measurement run can save its progress without overwriting other changes.
- `star_finding.py` — the DAOStarFinder core that `SourceDetector` and the frame measurement share. The roundness range is a parameter: the source detector keeps (-0.6, 0.6), the frame measurement keeps every roundness.
- `star_catalog_queries.py`, `star_analysis.py` — answer `StellarCatalog.query`. `find_star` tries the exact id first. For another spelling (spaces, underscores and capitals ignored) it uses a map of all star ids that it keeps until the star catalog is next written to, judged by the catalog's write count. Reading every id takes about half a second in a library of 300,000 stars, so the map is built once, not on every lookup.
  - **Paging in the database.** A plain listing (no selector, or a target, and an id or usefulness order, with no spectral class) is answered by the database. It counts the matches and reads one page, so only that page reaches Python. Every other query loads and filters the full listing, as before. The page and the count are the same either way. The database path uses `Butler.select_where` and `count_where` (see `../../foundation/storage/README.md`) through `catalog_access.py`.
  - **Selecting.** They pick stars by id, name, target, region or position. They filter by magnitude, spectra, photometry, a real catalog magnitude, spectral class or a search text. They hide single-frame photometry (brightness measurement) detections, whose ids end in `:Star_<n>`. They sort by id, by usefulness (spectra, then named stars, then photometry, then brightest first) or by spectrum match, and they page the result. They also count stars per target and per spectral class (the letter O, B, A, F, G, K or M that sorts stars from hottest to coolest).
  - **Catalog magnitudes.** A real catalog magnitude is a finite number of at least -2 that is not exactly 0 (`has_catalog_magnitude` in `models/stellar_source.py`). Smaller values are instrumental magnitudes from photometry, which are magnitudes on the camera's own uncalibrated scale. A value of 0 means the catalog gave none.
  - **Spectrum summary.** Spectroscopy classifies a star by comparing its spectrum with reference spectra of known type (the reference types). The distance between two spectra is a relative RMS: the root-mean-square difference as a fraction of the spectrum's average brightness. A value of 0.15 means a typical sample is 15% off. The per-star spectrum summary reports:
    - `own_type_percent_off`: how close the best reference type is (the relative RMS times 100);
    - `rms_gap_to_second_best`: the gap to the second-best reference, in relative RMS units (a difference of two RMS values, not a probability);
    - `rms_gap_to_next_class`: the same gap to the best reference of another spectral class;
    - `catalog_type_steps_apart`: how many subtype steps the measured type is from the catalog type.

    These are numbers only. The summary states no verdict, no confidence and no probability. Whether the fit is poor, a gap is too small or the types are too far apart is the quality advisory's statement (`review.get_advisory`), made from the same numbers and the limits `NO_GOOD_MATCH_RMS` (partly measured; see [SPE-16](../../../documentation/library_design/validation/spectroscopy.md#spe-16)) and `AMBIGUOUS_RMS_GAP` (measured; see [SPE-18](../../../documentation/library_design/validation/spectroscopy.md#spe-18)), or the spectrum's checkpoint 3 check on `DIFFERS_FROM_CATALOG_SUBTYPES` (partly measured; see [SPE-19](../../../documentation/library_design/validation/spectroscopy.md#spe-19)).
- `star_overlay.py` — places a target's stars in pixels on its stacked image, for labels drawn over it. It projects each star's sky position through the image's WCS and keeps the stars that land on the image. When the image has no WCS, it uses the pixel center saved when each star was detected. Star clusters and `Star_<n>` field detections get no label.
- `binned_sky_plane.py` — cuts an image into blocks, takes the median of each block, and fits a plane (a flat, tilted sheet) to the block medians, dropping the blocks far from it until the same blocks stay. The clipping is on both sides for the difference of two exposure groups (`stacking/processing/group_sky_matching.py`) and above only for one stack's sky (`stacking/post_processing/sky_plane.py`), where only a bright object lifts a block.
- `header_wcs.py` — reads the sky map (WCS, the World Coordinate System that turns pixels into right ascension and declination) from a FITS header, or `None` when the header has none, and gives an image's four corners on the sky with the lens-distortion (SIP) terms applied. Every step that reads a header's sky map uses it.
- `stack_sidecar.py` — saves a JSON file next to a stack with the stack's size and modification time (its stamp), writing it in one step, and reads it back only while the stack is unchanged. The detections, the star names and the solved star list kept next to a stack all use it, so none of them is read after a restack.
- `stack_preview_path.py` — the file names of the stretched JPEG and stretched FITS saved next to each stack, and the JPEG quality. Stacking writes these files (`stacking/post_processing/stack_preview.py`) and the image viewer looks for them. Both take the names from here so they cannot disagree.
- `simbad_object_types.py` — reads the object types (for example `V*` for a variable star) out of one row of a SIMBAD answer. The astrometry star identifier and the `scripts/backfill_simbad_object_types.py` script both use it, so both read an answer the same way.
- `star_kinds.py` — tells from a star id how the star can be looked up (Gaia DR3 id, a position-only `FIELD_J` id, and so on) and reads its stored position. The SIMBAD and variable-star backfill scripts share it.
- `gaia_star_colors.py` — gives the Gaia DR3 `BP - RP` colors and G magnitudes of the stars under an image, for the white-balance check of a color preview. It asks the ESA Gaia archive for each sky tile by its range of source IDs (a circle larger than about a degree timed out) and keeps each tile's answer in the stored catalog answers, so a tile asked for once is read from the disk.
- `variable_star_catalogs.py` — looks up stars in the AAVSO (American Association of Variable Star Observers) Variable Star Index (VSX). It asks VizieR (an online service hosting copies of many catalogs) once for each circle of sky of up to `FIELD_RADIUS_DEGREES` (1.5 degrees; design estimate; see [AST-12](../../../documentation/library_design/validation/astrometry.md#ast-12)), through the outside-service gateway (`outside_services.vizier_query_region`), which tries the server named by `[Catalogs] vizier_preferred_server` first and the other one second, limits the request rate and pauses VizieR after repeated trouble (see "Talking to outside services" in the drivers README). It then matches the stars to the returned entries on this computer (`match_to_catalog_rows`). An answer that reaches `FIELD_ROW_LIMIT` rows is refused, because VizieR cuts long answers off silently. When neither server answers, the error reaches the caller, nothing is stored and the star stays "unverified" (see `models/known_variability.py`). It asks the same way for Gaia DR3's variability classification (VizieR table `I/358/vclassre`, one class per classified variable and no score) and matches by Gaia DR3 source number, so a faint neighbor cannot be taken for the star (`gaia_flags_from_classes`): a listed star is stored as `VARIABLE:<class>`, an unlisted star with a Gaia number as `NO_GAIA_MATCH` (nothing about variability), and a star with no Gaia number is not asked. VizieR's main Gaia table could not be filtered by variable flag for a field in reasonable time. A VSX match must lie within `MATCH_RADIUS_ARCSEC` (3 arcsec; partly measured; see [AST-12](../../../documentation/library_design/validation/astrometry.md#ast-12)). This is tighter than the 10 arcsec `CATALOG_MATCH_RADIUS_ARCSEC` above because a wider radius lets a bright star match a faint neighbor. `vsx_entries_from_matches` also reads the brightness range, period and band that VSX lists for a typed variable into a `VsxEntry`. A "minimum" brighter than the maximum is not a magnitude, so it is dropped. The photometry target amplitude reads the stored range as its catalog value (design estimate; see [PHO-19](../../../documentation/library_design/validation/photometry.md#pho-19)). `scripts/backfill_variable_star_flags.py` uses it.
- `stored_variability.py` — fills the blank SIMBAD, VSX and Gaia DR3 answers of a session's stars from the library's stored catalog answers (`fill_known_variability`), so a star listed by any catalog stays out of the comparison set even when SIMBAD is down. It changes the stars in memory only. `count_listed_by_source` gives the counts by catalog that the photometry log shows. VSX and Gaia answers come through stored sky tiles (`query_vizier_field` now follows the rule in `drivers/catalog_cache.py`).
- `api_arguments.py` — checks the arguments of the public methods and holds the types and helpers they share (`TimeInput`, `StackKind`, `STACK_KINDS`, `make_frame_selection`). `resolve_target` turns a target id into its `Target` after reading the stored targets again, so a target another program changed is seen.
- `image_conversions.py`, `image_scaling.py` — convert images between formats and adjust brightness/contrast for on-screen display. The display stretch is Siril's autostretch: it takes the median and spread (MAD) of all pixels except exact zeros and NaNs, puts black 2.8 spreads below the median and white at full scale (1.0 for floats, 65535 for 16-bit data), and draws the median at 25% gray. A color image uses Siril's linked form, one set of numbers for all channels. The stacking preview and the bright-object test still use the sky measure (`measure_sky_background`), which ignores a galaxy that fills the frame. Every random sample in this file uses a fixed seed, so two renders of one image are identical. A stretched view of a stack uses the JPEG saved beside it. A frame, or a stack with no saved JPEG, has none; that is normal and not logged. A stack's `_processed.fits` is drawn as it is. A JPEG that exists but cannot be read is logged once per path. If a frame was moved into `_excluded` by the frame quarantine (whose records keep the original path), the viewer draws it from there.
- `provenance_recording.py` — the single call every pipeline makes to record its IVOA provenance. IVOA provenance is a record, in the International Virtual Observatory Alliance's standard form, of which run, at what version, produced a result (see `astrometricslib/models/provenance.py`).
- `quality/` — shared quality-measurement helpers (background level, saturation, per-frame statistics) that more than one pipeline's own quality checks build on. `quality/quality_metrics.py` and `quality/frame_statistics.py` measure star width (FWHM, full width at half maximum) only when the caller passes a measuring function in; the public API passes the astrometry pipeline's `measure_fwhm_from_data`. `quality/raw_frame_check.py` checks raw light frames that are not in the library yet: it measures stars, trails and the move since the previous frame, and flags frames that differ from their batch (see `QualityRecords.measure_frames(kind="raw_check")`). Each frame is flagged for any of these:
  - A star count below 0.5 times (`LOW_STAR_FRACTION`; partly measured; see [STK-01](../../../documentation/library_design/validation/stacking.md#stk-01) and [STK-34](../../../documentation/library_design/validation/stacking.md#stk-34)) or above 1.4 times (`HIGH_STAR_MULTIPLE`; design estimate; see [stacking design estimates](../../../documentation/library_design/validation/stacking.md#design-estimates)) the batch median. A count far below the median usually means cloud or a drift. A count far above it usually means extra bright regions that are not stars, such as a trail or a light leak.
  - A bright streak much longer than the batch's longest streak.
  - A faint straight trail, such as a satellite or aircraft, at least a quarter of the frame diagonal long (`TRAIL_MIN_DIAGONAL_FRACTION`, also an argument of `check_raw_frames`; (design estimate; see [stacking design estimates](../../../documentation/library_design/validation/stacking.md#design-estimates))). The detector averages the frame in blocks of `TRAIL_BLOCK_PIXELS` (4 by 4 pixels). It keeps blocks above `TRAIL_THRESHOLD_SIGMA` (3 noise units, where one noise unit is one standard deviation, σ, of the noise; (design estimate; see [stacking design estimates](../../../documentation/library_design/validation/stacking.md#design-estimates))) that are not inside stars. A region counts as a star when its smoothed peak passes `TRAIL_STAR_SIGMA` (60 noise units; (design estimate; see [stacking design estimates](../../../documentation/library_design/validation/stacking.md#design-estimates))). It then runs a line search (a Hough transform, which lets every bright block vote for the lines through it). The result lists the trail length in pixels (`line_trail_px`) and its angle in degrees (`line_trail_angle_deg`). The block size follows from the trail width: a trail about 4 pixels wide fills about one block, so averaging raises its signal-to-noise ratio about 4 times and shrinks the frame 16-fold, which also makes the line search fast. The star cut-off sits above the faint trail on purpose, so the mask does not hide the trail from the line search. The frames measured for the star counts and the trail are described in the register (partly measured; see [STK-34](../../../documentation/library_design/validation/stacking.md#stk-34)).
  - Stars much wider or less round than the batch's, a failed match to the previous frame's stars, or a large move since the previous frame.

  The check counts a pixel as saturated when it reaches the saturation level of the frame's camera profile (chosen from the `INSTRUME` header card). A 14-bit camera such as the Nikon D5300 clips near 16,383 ADU (analog-to-digital units, the camera's raw counts), so a fixed 65,000 would never trigger. The result records the level (`saturation_threshold_adu`) and where it came from (`saturation_threshold_source`). The check uses 65,000 only when no camera profile can be read. The level logic is `resolve_saturation_threshold` in `quality/saturation.py`. It takes the profile's `pixel_saturation_level_adu`, which is the saturation threshold capped at the clip ceiling. The spectrum check (`spectroscopy/pre_processing/spectral_frame_check.py`) uses the same function.

  The other `quality/` modules:
  - `background_measurement.py` — reads a frame from disk and measures its sky background level (a raw color mosaic on 2 x 2 super-pixels) and the fraction of saturated pixels. The decision whether the background changed too much during a stacking run lives in `stacking/pre_processing/background_homogeneity.py`.
  - `frame_quality_report.py` — builds the reports that `QualityRecords.measure_frames` returns for `kind="raw_check"` and `kind="input_quality"`. Each report also looks for slow drifts across the newest frames. Nothing is saved.
  - `frame_selection.py` — picks the frames a quality check measures, by filter, file-name range and time, for library frames and for a plain folder.
  - `frame_trends.py` — finds a slow, steady change in one number (sky level, star width) across recent frames, as from dew or drifting focus. It fits the median of all pairwise slopes (the Theil-Sen slope), so one bad frame cannot fake or hide a trend. It flags a trend when the fitted change, as a percentage of the starting level (`change_percent`), reaches the caller's threshold and at least 70% of the frame-to-frame steps go the same way (`STEADY_STEP_FRACTION`), with at least 4 frames (`MINIMUM_FRAMES`). Both limits are design estimates (see [stacking design estimates](../../../documentation/library_design/validation/stacking.md#design-estimates)).

For exact behavior, read the code.
