# API

This folder holds the library's front door: the classes that scripts, backend services and the MCP tools actually call. MCP (Model Context Protocol) tools are the adapters through which AI agents call the library. Each file wraps the pipelines and drivers underneath in a stateful, easy-to-use interface.

## Public layout

The library has a small public surface. Everything else is private.

| Import from | What it holds |
| :--- | :--- |
| `astrometricslib` (the root, 16 names) | `Astrometrics`, `AppConfiguration`, `get_configuration`, `configure_logging`, `configure_offline_iers` and `warm_earth_orientation_data`; the sub-API classes `TargetCatalog`, `StellarCatalog`, `ProcessingPipelines`, `CalibrationCatalog`, `QualityRecords` and `Visualization`; and the core records `Target`, `FrameRecord`, `StellarObject` and `FilterType`. |
| `astrometricslib.exceptions` | The errors a script catches, `ErrorInfo` with `to_error_info` and `error_from_info`, and `FITS_READ_ERRORS`. |
| `astrometricslib.reports` | The quality reports and quality row shapes that checks return, `CaptureSetting` and `observing_night_id`. |
| `astrometricslib.jobs` | `Jobs` (`astrometrics.jobs` is an instance of it), the job store and records, and the tools that run a function as a tracked background job. |
| `astrometricslib.drivers` | The data store and file tools that other apps share (`Butler`, `connect_db`, `file_lock`, `is_path_inside`, `resolve_mounted_path`, `get_simbad_driver`, `header_is_plate_solved` and the like). |
| `astrometricslib.parameters` | The tuned-parameter declaration (`TunedParameter` and its enums), `collect_parameters`, `resolve_parameter` and the provider protocols. |
| `astrometricslib._internal` | Everything else, in logical groups. |

The rules:

- **Only `astrometricslib` itself may import `_internal`.** `wayfindinglib`, the backend and the MCP servers use the root and the four public modules only. Tests of the libraries are the one exception.
- **A result model is private, and its fields are not.** A call returns a Pydantic model (a Python class with typed, validated fields) such as `TargetQueryResult` or `StackResult`. A caller reads the fields by name and does not import the class. The API reference page lists the fields of each result without an import path.
- **A caller reaches a sub-API through `Astrometrics`.** Build one `Astrometrics` and use `astrometrics.targets`, `astrometrics.processing` and the rest, so all of them read and write the same storage.
- **Old names have no alias.**

Terms are defined in the [glossary](../../documentation/Glossary.md). This document also defines each term the first time it appears.

A target is one sky object the library tracks, with its raw frames (single camera exposure files) and results. A stack is the image made by aligning and averaging many frames.

## What each file is for

The `Astrometrics` class in the package's `__init__.py` (the "root") builds one object per file below and exposes each as an attribute, such as `astrometrics.stars` or `astrometrics.processing`. Each of these objects is a sub-API.

Each sub-API checks its arguments and hands the work to `pipelines/`. Three rules hold for every sub-API:

- A method that takes a target accepts its id or the `Target`. An id that names no target raises `NotFoundError`.
- A method that offers variants picks one with `kind=` and adds optional sections with `include=`. It refuses an argument that the chosen variant does not use.
- A method that builds a new answer returns a Pydantic model (a Python class with typed, validated fields), for example `TargetQueryResult` or `StackResult`. It does not return a dictionary.
- A `limit` (and `offset`, `lines`, `include_frames`) outside its documented range raises `InvalidArgumentError`; it is never moved into range. Each method says what `None` means. The one check is `check_limit` in `pipelines/shared/api_arguments.py`.
- A pixel position a method returns is 1-based, as in FITS and DS9: the center of the first pixel is 1, 1. `StellarObject.star_data` is the exception: it is the star finder's own row, stored as found, and its `xcentroid` and `ycentroid` count from 0.

- A row carries the values a caller would otherwise import a helper for. These are worked out when read and are not saved, so the stored form does not change: `FrameRecord.is_spectral`, `Target.object_category`, `Target.ra_deg` and `Target.dec_deg`, and `TargetStackingResult.preview_path`. A limit a row reports is the limit in force now, not the one in force when the row was stored. Two limits sit on returned answers instead: `CalibrationQueryResult.dark_temperature_tolerance_c`, and `limits` on the `MetricSpec` of `frame.saturated_pixel_fraction` (the saturated-star blob size in pixels and the share of frames that makes an exposure length clipped).

### `targets.py`

`TargetCatalog` creates, reads, saves and deletes targets.

- `get(target, refresh=False, required=False)` returns a `Target` for code to work with, or `None`; with `required=True` an unknown id raises `NotFoundError`, and a `Target` is returned as it is. With `refresh=True` it first brings that one target up to date with storage (see `pipelines/shared/target_records.py`): nothing is read when the library write counter has not moved, one row is read when it has, and every target is read only when this catalog does not hold the target yet. Unsaved edits to a held target are kept. A lock keeps threads from refreshing at the same time. `refresh="storage"` reads the saved record straight from storage, by exact id, to check what a save wrote.
- `query` returns short records for people and AI clients. `detail="objects"` returns every `Target` in `objects` (`query(detail="objects", limit=None).objects` is the whole list; it skips its read the same way as `get`). `detail="cameras"` adds the cameras used. `detail="camera_index"` adds each target's frames per configured camera, built by `pipelines/shared/target_camera_index.py`. A target's stars are `stars.query(target_id=..., detail="objects", limit=None)`.
- `read_frame_header(path, target=None, as_cards=False)` reads the first header of a FITS file and returns it with typed values, or with `as_cards=True` as text cards (`key`, `value`, `comment`). With `target` the file must be one of the target's frames or stacks. A missing file raises `NotFoundError`. It reads no pixels. The backend and wayfindinglib use it instead of opening FITS files themselves.
- `select_frames` picks a target's timed light frames by filter, file name range, start time (ISO 8601 text, a `datetime` or an astropy `Time`) and count, oldest first. With a range or time bound `limit` keeps the first frames in it; otherwise it keeps the newest.
- `delete_images(paths, target=None)` deletes files and, with a target, their frame records and stored quality measurements (through `quality.forget`).
- `imaged_field_centers` lists the distinct sky positions imaged (`ra_deg`, `dec_deg` and the targets at each).
- `add_frames(paths, target, telescope=...)` moves new FITS files (folders to search, or single files) into the library and returns the new path of each file that was not there before. Light frames go under the target; dark, bias and flat frames go to the calibration folders. It does not update the frame records: call `reindex_frames` with the returned paths. `processing.calibration.add_frames(paths, telescope=...)` does the same for calibration files only and leaves light frames where they are.
- `sessions(target, night_date=None)` groups a target's frames into `TargetSession` records: one for each night (noon to noon, local time) and gain and offset setting. `night_date` keeps one night.
- `reindex_frames` brings frame records up to date with the files on disk:
  - Given `paths`, it adds only those files. A finished `.jpg`, `.png` or `.tiff` image becomes the target's processed image instead of a frame.
  - Given a target, it rescans that target's folder.
  - Given neither, it rescans every target folder and creates a target for each new folder.

### `stars.py`

`StellarCatalog` reads and changes the star records.

- `get` returns one star's full record.
- `get_spectrum(star_id)` returns a star's `SpectroscopyResult` from the star itself, or `None`. Older libraries also hold a copy of the star under an id ending in `::spectroscopy`. `get_spectrum` reads that copy when the star has no spectrum of its own, and accepts that id, so scripts never need to build or test for it.
- `query` answers every read about many stars. It selects by ids, name, target, sky region or position, with a cap on the size of the answer.
  - `detail` picks what comes back: ids, summaries, analysis records, full records, class counts, per-target counts, library statistics, or the stars placed in 1-based pixels (as in FITS and DS9) on a target's stacked image, or on any image named by `image_path` (`detail="overlay"`, built by `pipelines/shared/star_overlay.py`).
  - Filters cover magnitude (the astronomer's brightness scale, where larger numbers are fainter), whether a star has a spectrum or photometry, spectral class, and a search text. The spectral class is the letter of the star's type in the O, B, A, F, G, K, M sequence, hottest to coolest. A full type such as `G2V` counts as `G`.
  - `StellarObject.magnitude` is one field. It holds SIMBAD's V magnitude for a star SIMBAD names, Gaia's G magnitude for a star named from Gaia only, `None` when no catalog gave one, 0 on old records for "none given", and an instrumental magnitude (measured by an earlier version of this library's photometry, on its own uncalibrated scale, about -10 to -17) on old records. A filter on "real catalog magnitude" (`has_catalog_magnitude=True`) keeps the first two: a finite value of at least `BRIGHTEST_CATALOG_MAGNITUDE` (-2) that is not 0.
  - `order` sorts by id, by usefulness (stars with spectra first, then named stars, then stars with photometry, then brightest first), or by spectrum match (stars whose own spectrum best matches a reference spectrum first).
- Single-frame detections are hidden unless `include_unresolved=True`. Photometry (brightness measurement) saves each point source it finds in one frame under an id ending in `:Star_<n>`. These are working records, not catalog stars, so a normal query leaves them out.
- `dataset_version` counts the star catalog writes made by any program. The count is kept in the library database, so it also sees a write by a maintenance script and survives a restart. A cache of a whole-catalog answer compares it to the number it saw last, to know whether to rebuild. `astrometricslib.drivers.get_library_data_version` gives the counters of every kind of data (targets, quality, stars) for a cache that depends on more than the stars.
- Every other method on `StellarCatalog` changes star records. `create(star_id, ra_deg=None, dec_deg=None)` takes the position in ICRS degrees. `update(star_id, updates)` takes `StellarObject` field names and raises `InvalidArgumentError` for any other name, changing nothing.

### `processing.py` and `calibration.py`

`processing.py` holds `ProcessingPipelines`, and `calibration.py` holds its child `CalibrationCatalog`. The stacking methods of `ProcessingPipelines` are written in `_processing_stacking.py` and its preview methods in `_processing_preview.py`, as functions the class binds as its own methods. These two files are private: callers reach the methods through `astrometrics.processing`. `quality.py` holds `QualityRecords`, which is a sub-API of its own (see below), not a child of `ProcessingPipelines`.

`ProcessingPipelines` makes stacks and runs the analysis.

- `stack` chooses a target's frames and stacks them. It chooses by filter (the colored or clear glass in front of the camera that passes one band of light), file range, time window, camera and focal length (`focal_length_mm`), or takes an exact list. Frames from two cameras, or from one camera behind two optics, are never stacked together: the call names each camera or focal length with its frame count and asks for `camera_id` or `focal_length_mm`. An exact list is also refused, with `InvalidArgumentError`, when it mixes imaging and spectral frames; the message counts each kind, and nothing is stacked (the frame choice by `kind` never mixes them). The backend runs the same check, with `predict_stack(..., checks=False)`, when the Stack Frames or Check Frames click sends a frame list, so the click gets an error reply and no job is made.
- `predict_stack` says what a stack would do with its frames, without stacking (the app's Check Frames). It takes the same frame choices as `stack`, or an exact `frames` list, and returns a `StackPrediction`: how many frames would be stacked, the frames that would be set aside or kept with an uneven-sky warning (each with its kind and reason), and for each exposure group the darks, bias and flats it would use (count, folders, and the library's flags for a near match). The frame checks and the calibration choice are the ones the stack runs, so the two agree. Nothing is stacked, moved, stored or saved. The cloud and trailing check reads every frame, so a large target takes a while; `register_job=True` records the run as a diagnostics job. With `checks=False` it only chooses the frames: it reads no frame and returns the count, the camera and the first and last file (`checks_run` is `False`). It is the one stack preview. The backend serves it as the background job `processing:check_stack`.
- `remake_preview` makes a stack's preview image again without restacking. The result carries `preview_settings`, read from the record saved beside the stack (`<stack name>_preview_settings.json`), or `None` when the picture has no record.
- `list_preview_bright_objects` lists the nebulae and galaxies SIMBAD places inside a target's imaging stack, nearest the center first, using the stack's plate solution; it returns a `BrightObjectChoices` with `objects`, or no objects and a `message` (no stack, "Run Astrometry first to list objects in the frame", SIMBAD out of reach). SIMBAD's answer is kept in the library's stored catalog answers; `refresh=True` asks SIMBAD again (a stored answer still stands in if SIMBAD cannot be reached). `set_preview_bright_object` saves the target's choice of what the preview's masked stretch protects (`"auto"`, `"off"` or `"object"` with a SIMBAD name and position) as `Target.preview_bright_object`. It makes no picture: the choice is used the next time the target is stacked or `remake_preview` runs. The backend serves them as `processing:list_bright_objects` and `processing:set_bright_object`.
- `process_target` has two forms:
  - For one target, it runs the analysis stages (`astrometry`, `photometry`, `spectroscopy`, `spectral_variation` and `asteroids`) on the frames and stack the target already has. It does not stack.
    - Each stage takes its options as a plain dictionary. The asteroid search takes `asteroids={"moving_object_config": {"detection_threshold_sigma": 4.0}}`: the keys are the `[Processing.MovingObject]` setting names, a key left out keeps its default, and a key that names no setting raises `InvalidArgumentError`. The model behind the dictionary is private.
    - Astrometry is a hard prerequisite of photometry and spectroscopy. With `run_prerequisites=True` (the default), `process_target` adds astrometry to the run when its saved result is missing or older than the imaging stack. It solves the image in `astrometry={"path": ...}` when one is given, and the imaging stack otherwise. When it cannot run (no stack and no image) or it fails, photometry and spectroscopy are skipped and not run on a guess. The result lists the stages added in `prerequisites_run` and the skipped ones, with the reason `needs astrometry: ...`, in `stages_skipped`. Pass `run_prerequisites=False` only when astrometry has just run on this stack.
    - `spectral_variation` follows each star's spectrum across the raw spectral frames. It needs spectroscopy first, which `process_target` adds (with astrometry) when the saved spectroscopy result is missing, older than the spectral stack, or built from raw frames. It saves no stars, keeps its summary in `quality.spectroscopy_variation`, and skips a session of fewer than 2 frames with the reason in its result (`skipped_frames`). Its options are `frames` and `max_workers`. The main Analyze Target click does not run it.
  - For a list of targets, or for every target, it runs the full pipeline: stacking first, then the analysis stages. The full pipeline always solves the stack before photometry, so `run_prerequisites=False` is refused.
- A restack keeps the stack it replaces in a `_previous` folder. No public call deletes it or puts it back.
- `open_in_siril(file_path)` opens a FITS file in the Siril program's window, through the stacking driver's `open_in_viewer`. The app's "open in Siril" button uses it, so the backend never builds a Siril driver. A stacking driver with no window raises `ProcessingError`. It is not offered as an AI tool.
- `stop_stacking_programs()` stops every Siril process the library started and still runs, through the stacking driver's `stop_running_programs`. The backend's `Container.shutdown_resources()` calls it, because the backend's exit runs no `atexit` handlers and Siril runs in a session of its own. A Siril window a person opened by hand is not touched. It is not offered as an AI tool.
- `predict_stack_weights` forecasts a stack before it exists. Given the frames' exposure lengths (and, when known, their star widths, variances and group noises), it runs the stacker's own rules and returns a `StackWeightPrediction`: the weighting mode, the exposure group each frame lands in, and each frame's weight, or the reasons the weights are unknown. It reads and saves nothing.
- `stack_subset(pipelines, target, frames, label=...)` is not a method. It is an internal function (in `astrometricslib._internal.processing_scripts`, code in `script_calls.py`) that only the library's own scripts and tests call. It stacks exactly the given frames into the target's `_subsets` folder with the normal settings, and stores the result's noise, effective frame count and effective time. With `record_forecast_rows=True` it also stores the rows a library stack stores for the forecast check (one `stacking.frame_weight` for each frame on the frame's subject id plus `#<label>`, so the weights never hide the library stack's newest rows; the exposure-group rows on the subset's own group subjects; and a calibration record), so a subset such as the stack of all nights but the last (`label=EARLIER_NIGHTS_VARIANT`, a constant in `astrometricslib.reports`) can be the earlier member of the forecast check's pair. It never writes to the library stack's path, assigns nothing on the target and saves nothing. `measure_noise(target, kind="growth")`, the default kind, stacks the first night, the first two nights and so on (at most 4 subsets by default) and measures each result's noise in the library stack's sky apertures. It also runs the odd–even difference noise below, in the same lock, unless `include=[]` is given (`include=["night_contributions"]` adds the night contributions). `measure_noise(target, kind="night_contributions")` stacks the library stack's frames without each night in turn and stores the night's share of the weight and the noise without it. `measure_noise(target, kind="odd_even_difference")` stacks two disjoint halves of the library stack's frames on one registration reference, subtracts them and stores the noise of the difference beside the library stack's empty-aperture noise (the halves are deleted afterwards; the job refuses with a reason rather than guess). None of the three kinds starts by itself after a stack; a caller starts them (the app has the one RPC `processing:measure_noise`, which takes the same `kind`). They cost one stack per subset (the odd–even difference job costs about one library stack's time in all, two stacks of half the frames, plus the temporary disk space Siril needs for each: its converted and registered copies of the frames, deleted after each stack; the M 106 run in the comment in `siril_interface/imaging_stacker.py` measured 65 GB for 238 frames, about 0.27 GB a frame, so a half of 30 frames needs about 8 GB), run as background jobs of type `stacking`, and raise `NotFoundError` for a target with no stack. `measure_noise` returns the result of its kind: `NoiseGrowthResult`, `NightContributionResult` or `OddEvenDifferenceNoiseResult`; `stack_subset` returns `SubsetStackResult`. `maximum_steps` applies to `growth` only, `include` to `growth` only and `keep_halves` to `odd_even_difference` only; giving one with another kind raises `InvalidArgumentError`. See [subset stacks](../pipelines/stacking/README.md#subset-stacks).
- `restore_excluded_frames(pipelines, target, apply=True)` is not a method either. It is an internal function in the same module, used by `scripts/restore_excluded_frames.py`. It moves frames the stacker set aside back into the frames folder. The stacker sets a frame aside, into an `_excluded` folder, when clouds or trailed stars (stars smeared into short lines) make it unusable.
- `plate_solve` works out where a FITS frame (the standard astronomy image file) points, using the stars in it. It returns a `PlateSolution` (the image center in `ra_deg` and `dec_deg`, `pixel_scale_arcsec`, `rotation_deg`, the size, and the pixel-to-sky mapping, a WCS or World Coordinate System, as header cards in `wcs_header`), or `None`. The centering step in wayfindinglib uses its center to point the telescope exactly at a target.
- `identify_stack(path, progress=None, should_stop=None)` names every star the stack's own star finder detected, for the viewer's Astrometry button. It keeps the stack's plate solution when the header has `PLTSOLVD`, and otherwise solves the stack and writes the solution into it and its viewer copy. The detections are matched to the Gaia stars of the cache tiles under the stack and, when online, to SIMBAD, whose most familiar designation wins (proper name, Bayer, Flamsteed, HD, HIP, TYC, then `Gaia DR3 <id>`). Its `x` and `y` are 1-based pixels. Each star has a `kind`: `matched`, `unmatched` (`Unnamed star`) or `catalog_only` (a Gaia star one magnitude brighter than the predicted limit with no detection). Among names of one kind the alphabetically first is chosen, so the label does not change between runs, and the star's other SIMBAD names are its `aliases`. A star the library already has a record of (`Gaia DR3 <id>`) gains the names it lacks as aliases (`alias_records_updated` counts them); no record is created and nothing else in a record changes. Raw frames are refused. The result is saved next to the stack (`<stack>_identification.json`, layout version 4; a version 3 file, which held 0-based positions, is moved to 1-based pixels when read), and `get_stack_identification(path)` reads it while the stack is unchanged. The backend runs it as an analysis-type job (`analysis:identify_stack`, `analysis:get_stack_identification`).

`CalibrationCatalog` tracks the dark, bias and flat frames (the calibration frames that measure the camera itself; see `astrometricslib/_internal/drivers/README.md`).

- `query` reports counts, or how a target's light frames (frames of the sky) match the darks.
- `camera_profile(camera_id)` returns the stored `CameraProfile` for a camera, matched in any spelling the profile lists (case, spaces and punctuation are ignored). It carries the camera's saturation limits with their sources and its gain and read noise for each sensor setting. A missing or unlisted name gives the generic fallback profile (`is_generic_fallback` is `True`). The profile describes the camera model, not calibration frames, but the call sits here because it reads the same configuration and no other sub-API fits better.
- `reindex_frames("flat")` rescans one kind and reports what it found. `report.assessments` holds one `CalibrationSetHealth` (the record `assess` returns) for each set that gained frames. A new flat set is measured: enough frames, bright enough but not too bright, and a master flat (the combination of the set) that is not too noisy. A dark or bias set is not measured by the rescan; it is judged from the numbers `measure_frames` stored, so a new frame with no numbers yet shows checks that are `not_checked`, with the reason. The app starts `measure_frames` by itself after it ingests or downloads dark or bias frames; a script must call it.
- `assess(kind, ...)` judges the sets of one kind (`"dark"`, `"bias"` or `"flat"`) already in the library. It gives one record for each set, with one check per condition, each passed, failed or `not_checked` with the reason. A dark or bias set is judged from the numbers stored for each of its frames, so it needs `measure_frames` to have run. A flat set is measured when asked. A check with no reference (for example a bias level the camera profile does not hold) is `not_checked`, never judged against a default. Nothing is written.
- `measure_frames(kind=None, camera_id=None, force=False)` measures the dark and bias frames that are new or changed and stores their numbers. It runs as a background job, because a first pass over a large library takes a long time (about half a second per frame). It never changes a frame file.
- `measure_sensor_noise(camera_id, gain, offset, binning)` measures the camera's conversion gain (electrons per ADU, one step of the stored pixel value) and its read noise (the electronic noise added when a frame is read out) from the flat and bias frames in the library at exactly that setting. It pairs the frames in file-name order, so it needs at least 5 flat pairs and 3 bias pairs that share one setting, one flat exposure and one temperature. If it cannot measure, the result says why and holds no numbers. Reading never writes. With `save=True` a measured result goes into the camera profile in the configuration file, after a backup. The result's `provenance` sentence is stored as the value's source. Set `exposure_seconds`, `temperature_c`, `telescope` or `filter_name` to choose among flats of several kinds. It runs as a background job. Its result matched a hand measurement (measured; see [STK-35](../../documentation/library_design/validation/stacking.md#stk-35)).

### `quality.py`

`QualityRecords` is reached as `astrometrics.quality`. It is the start of every quality read, whether the numbers were stored by an earlier run or are measured now. Only `record_frame_measurements` and `forget` change stored data.

Stored reads:

- `query` reads the quality measurements that earlier runs saved in `astrometrics.db` and returns a `QualityQueryResult`: the `rows`, `total_matching`, `offset` and `truncated`. There is no limit unless `limit` is given; `limit` and `offset` page the answer. It filters by `metric`, `level` (`frame`, `stack` or `run`), `target_id`, `observing_night_id`, `camera_id` (exact camera name), `telescope` and `since`. It gives the newest row for each subject and metric unless `latest_only=False`, and `row_ids` returns exactly the rows a report cited. `variant` keeps only the rows about one subset stack, and `library_only=True` leaves subset-stack rows out (giving both raises `InvalidArgumentError`). A library with no quality table yet gives an empty list; the read opens the file read-only and creates no file and no table. A `metric` that is not registered raises `InvalidArgumentError`.
- `calibration_identities(run_ids, target_id)` reads which calibration each library stacking run used: the flat, bias, flat-bias (the bias removed from the flats, at the flats' own gain and offset) and dark masters (path, size, modification time), optic, camera, Siril version and stacking algorithm version. Two runs of a target whose records differ are confounded by a calibration change. A record made before schema version 6 has no flat-bias record (`None`), and the forecast check does not count that as a difference. An unmigrated or missing database gives an empty list.
- To tell whether two stacks' noise was measured in the same apertures, read the stack's `stacking.aperture_set_number` row with `query(metric="stacking.aperture_set_number", target_id=..., library_only=True)` and turn each row's `value` into text with `aperture_identity_from_number` (a private helper; `wayfindinglib` keeps a copy pinned by a test). Equal text means the same set; a not-measured row or a missing row means unknown. An odd–even difference run stores the same number as `stacking.odd_even_difference_aperture_set_number`.
- To test where the fixed-pattern noise sits, read the `stacking.odd_even_difference_aperture_record_count` row of the library stack: its reason holds the path of a JSON record (one entry per empty aperture with its position, its distance from the image center and from the target, and its values on the sum A + B and the difference A - B of the two half stacks), which `quality.get_aperture_record(path)` reads. It returns `None` for a missing, unreadable or other-version file. The row's four neighbors, `stacking.odd_even_difference_row_average_scatter_stack_unit`, `..._column_...`, `stacking.odd_even_sum_row_average_scatter_stack_unit` and `..._column_...`, give the line pattern.
- `metrics` lists the declared metrics, or with `name=` just that one, or with `checkpoint=` only those measured at that checkpoint. An unknown `name`, `checkpoint` or `detail` raises `InvalidArgumentError`. About 170 metrics are registered, so the default `detail="summary"` gives a short `MetricSummary` for each (name, unit, checkpoint, levels, purpose). `detail="full"` gives the whole `MetricSpec`, which adds the meaning, which way is better and how the number is estimated; pair it with `checkpoint=` or `name=`.

Recorded reads:

- `forget(subject_ids)` removes the stored measurements of frames that no longer exist, and returns how many it removed. It touches only frame measurements (a stack or run row is never removed), also removes a frame's weight rows inside subset stacks, ignores an id with no measurement, and creates no file in a library with no quality database. `targets.delete_images(paths, target=...)` calls it for the deleted frames of the target it is given, so deleting a frame, on a real night too, drops its numbers; without a `target` the numbers stay, because a frame is named by its target.
- `record_frame_measurements(target)` measures a target's light frames and stores the numbers in the quality database (read them with `query`). It reads each frame once and measures the stars' width and stretch, the sky and its noise in electrons, the read noise and the temperatures. A value it cannot measure is stored as `not_measured` with the reason. A frame whose file has not changed since its last measurement is skipped, so a second call measures nothing again. A frame that fails, for any reason, is counted and tried again next time. It never moves or changes a frame file. Only one run measures a target at a time, and one run reads frames at a time; a second call for the same target returns at once with `already_running` set. A sync measures only the frames it added, at about 11 s per frame. It runs as a background job of type `quality` and returns a `FrameMeasurementSummary`. A sync that adds frames starts it by itself. See [frame measurement](../pipelines/stacking/README.md#frame-measurement). The star measurements are a design estimate (see [AST-17](../../documentation/library_design/validation/astrometry.md#ast-17)).

Live checks:

- `measure_frames(target, kind=...)` measures a target's raw frames. A folder of frames goes to `measure_folder`, and the preview of which frames a stack would set aside is `processing.predict_stack`. A `limit` outside 1 to 300 (1 to 100 for `spectral`) raises `InvalidArgumentError`, as every `limit` of this sub-API does outside its documented range.
  - `kind="input_quality"` measures them one by one; `camera_id` is a filter.
  - `kind="raw_check"` checks a target's frames as a batch.
  - `kind="spectral"` measures a target's raw slitless-spectrum frames. These are frames taken through a grating with no slit, which spreads each star into a spectrum trail of colors. For each frame it reports:
    - where the zero order (the undispersed image of the star) sits;
    - the tilt and width of the spectrum trail, and the sky level;
    - every saturated patch, that is, pixels at the sensor's maximum value, where the true brightness is lost.

    Given `predict_exposure_seconds`, it scales the measured peaks to that exposure and says whether the spectrum would saturate ("clip") at that exposure. `exposure_seconds` and `predict_exposure_seconds` apply to this kind only; giving them with another kind raises `InvalidArgumentError`.
- `measure_detections(path)` is the astrometry finder of `blocks.find_stars` run on one file at the run's own settings, saved for reuse. It lists the stars the astrometry star finder detects in one image, found now from the pixels, so it works on every image without running the analysis again. It calls the run's function (`find_unique_stars`) but keeps close star pairs, which the plate-solving list drops (AST-D23, Measured): the kernel sized from the star width in the image, the merge of a star reported twice into one detection at its brightest report, and the averaged copy of a color image. Each detection has `x` and `y` (1-based pixels, as in `measure_star_profile`), `flux` and `merged` (true when two reports were merged). The result also has `detection_count`, `merged_count`, `kernel_fwhm_px`, `binned_on_color`, `star_width_px` (on the one star-width scale) with its `star_width_estimator`, and `aperture_radius_px`. The star width is measured on the image itself, as a run measures it, and sizes `aperture_radius_px`: the radius of the circle photometry measures each star in (`APERTURE_RADIUS_PX`), so the viewer can draw that circle. When no star can be measured, the active setup's typical width stands in and `star_width_px` is null. Nothing is stored. The viewer's Detections overlay calls it through `images:measure_detections`.
- `measure_folder(folder_path, limit=20, bias_level_adu=None, camera_id=None)` is the one method for a folder of frames. `camera_id` overrides the camera the headers name; it leaves no frame out. It measures any folder of `*.fits` frames with the same `frame.*` metrics that `record_frame_measurements` stores (star width in pixels and arcseconds, elongation, sky rate in electrons per second per pixel, sky noise, background, saturation) and returns the numbers and their medians. It stores nothing and moves nothing, and the folder need not be in the library, so it checks tonight's staging folder or frames a camera simulator drew (their header card `SYNTHETC` raises a notice). The sky rate needs the bias level of the camera setting: it comes from the calibration library, or from `bias_level_adu` when the library has none. A frame takes about 12 seconds.
- `choose_blink_pair(target, path)` picks what the viewer's Blink button compares for a flagged or set-aside frame: a typical frame of the same session (the batch the frame quarantine judges it in), and one reference star in both frames. The typical frame has the stored `frame.star_elongation` and `frame.sky_unevenness` closest to the session medians. The star is bright, isolated and unsaturated, near the frame center, picked with the candidate rules of the star-shape measurement. The result has `found`, `reason` (when nothing was found), `path`, `typical_path`, the star in each frame (`star_x`, `star_y`, `typical_star_x`, `typical_star_y`, 1-based pixels), `turned` (the typical frame is turned half a revolution, a meridian flip), `votes`, `session_frame_count` and the frame size (`width`, `height`). Nothing is stored. The File Browser and the frame status timeline reach it through `target:get_blink_pair`.
- `map_position(from_path, x, y, to_path)` finds where a 1-based pixel of one image is on another: through both images' plate solutions, else through a stack's registration record (frame to stack, stack to frame, two frames of one stack, or frames of two stacks through the stacks' plate solutions), else the same pixel as a guess. A stack turned by a quarter turn after stacking (the record's `quarter_turn_degrees`) is followed on its saved pixels. It returns a `PositionMapping` (`x`, `y`, `method`, `note`); a pixel it cannot follow (a frame Siril left out, a spectral stack) gives `method="none"` with the reason. It reads only headers and the records beside the stacks. The viewer reaches it through `images:map_position`.
- `match_frame_positions(path_a, path_b, points)` does the same job by the frames' stars instead, for two frames of one size with no plate solution or record. It says where positions of frame A lie in frame B. It matches the bright stars of the two frames the way the quarantine's pointing check does, trying B as it is and turned half a revolution. Each point comes back with `mapped_x`, `mapped_y` and `inside`, and the result says whether the frames matched, whether B is turned, and how many star pairs agreed. Nothing is stored.
- `frame_statuses(target)` gives each frame of a target its state for the File Browser's Status column: `included`, `flagged` (stacked, but its stars are stretched), `not_stacked` (taken after the newest stack file) or `set_aside`. The library finds the newest stack file itself (the imaging, spectral and saved-configuration stacks). A target that is not in the library raises `NotFoundError`, as for every per-target method here.
- `put_back_set_aside_frames(target, paths)` moves chosen frames out of a target's `_excluded` folders back to where they came from, then rescans the target so it lists them again. Each path must be a frame that `set_aside_frames` lists; a path elsewhere raises `InvalidArgumentError`. A frame whose old place is taken, or that has no `excluded_frames.json` entry, stays where it is and is left out of the returned list. The next stack may set a frame aside again.
- `measure_star_profile(path, x, y, radius_px=None, cut_angle_degrees=0.0, cut_half_length_px=None, search_radius_px=None)` measures one star at a 1-based pixel position (as in FITS and DS9). It refines the center to the brightness-weighted centroid, takes the sky from a ring outside the radius, lists every pixel within the radius with its distance and its value above the sky, fits a round Moffat curve and a round Gaussian curve (width in pixels and arcseconds, Moffat beta, peak; each width also names its `estimator` and gives `fwhm_on_scale_px`, the width on the one star-width scale), says whether the peak looks clipped, and reads a straight cut through the center. The cut angle is measured from +y (increasing row) toward +x (increasing column); 0 runs along a column and 90 along a row. A color image is averaged over its channels and the result says so. Left out, the radius and the cut length follow the star width. With `search_radius_px`, the position first moves to the brightest peak of the lightly smoothed image within that distance (at most 50 px), and the result says whether it moved (`snapped`, `snap_distance_px`). The result also says whether the profile looks like a star (`star_found`, with `not_a_star_reason`): a peak under 5 times the sky noise, a width under about 1 px, or a width over about 8 times the star width is not one, and the data are still returned. The result carries a `cutout` of sky-subtracted pixels around the center, so a caller can rebuild a cut at any angle (the recipe is in the model's docstring); the radius and cut length are limited to 100 px. The result also holds the ring around the star (`ring_*` fields): the ring radii (`ring_inner_px`, `ring_outer_px`) sized from the measured pixels, the 5 degree direction bins of the pixels kept (`ring_bin_angle_degrees`, `ring_bin_values`, `ring_bin_counts`), the Fourier terms of orders 1 to 8 (`ring_harmonics`: `amplitude` as a fraction of the ring's mean with `amplitude_error`, `amplitude_debiased`, `significance`, `significant` and `direction_degrees`, from +y toward +x as for the cut), and the neighbor stars left out (`ring_neighbors`, `ring_masked_neighbor_count`, `ring_masked_fraction`). The neighbors come from the astrometry run's star finder on a small box around the star. `peak_over_sky_noise` is the brightest pixel over the sky noise, not the signal-to-noise ratio of the star's light (`blocks.measure_aperture` gives that). Every angle in the result, including `star_elongation_angle_deg`, runs from +y toward +x, as the cut does; `star_elongation_position_angle_deg` gives the long axis on the sky (north toward east) when the image is plate solved. Nothing is stored. The viewer's star panel calls it through `images:measure_star_profile`.
- `measure_tuned_parameters(setup=None, only=None, save=False)` works out this library's tuned values (limits, thresholds, typical widths) from the setup's stored frames, stacks and spectra. It is a thin wrapper of the one tuning core, `astrometricslib.parameters.tune(packages, configuration, setup=, only=, save=, services=)`. Each tuner's value is checked against its allowed range and smallest sample. It returns a `TuningReport` of what would be set or moved, and what was skipped or refused. Nothing is saved unless `save=True`, which backs up the config first and writes each value with where it came from. The observatory values are tuned by `wayfinder.review.measure_tuned_parameters`; the Command Console recipe `tune_parameters` runs both.
- `measure_stack` measures a stack (star width, the share of rejected pixels, frame registration) and compares it with the previous stack or another stack file. The comparison reports the sky level, the noise in empty sky (the target report's `stacking.empty_aperture_noise_normalized`), the flatness and the star width, with one sentence for each and a reason for any number it could not measure.

Building blocks for scripts: `quality.blocks`, a `QualityBlocks` (in `_quality_building_blocks.py`). The Command Console preloads only `astrometrics` and `wayfinder`, so these methods give a script the library's own small measurements, each from its one home under `pipelines/`. An image argument is a FITS path or a pixel array (2-D, or color channels first). Positions are 1-based pixels, as in `measure_detections`. A raw color mosaic (a one-plane frame with a `BAYERPAT` card) is refused unless `debayer=True`; it is then measured as 2 by 2 color super-pixels (red, the mean of the two greens, blue), and positions and widths come back in the raw frame's pixels. Nothing is stored.

- `measure_sky(image, bias_adu=None, gain=None)` gives the empty sky's `level` and `noise` (one standard deviation), with large bright objects clipped out (`image_scaling.measure_sky_background`), or `None` when the sky cannot be measured. The numbers are raw ADU with the bias still in the level; with both `bias_adu` and `gain` they are electrons. The noise comes from differences of pixels four columns apart, so it reads low where neighbors share noise (a debayered, resampled or stacked image). A color image also gets one entry per channel.
- `find_stars(image, finder="astrometry", fwhm_px=None, threshold_sigma=None, isolation_px=None)` runs the astrometry run's finder (`find_unique_stars`, the default: a sky map, merged double reports, a color image searched on an averaged copy) or `finder="daofind"`, the plain shared finder on one sky level with every roundness kept. It returns the `stars`, brightest first, with each star's `flux`: the finder's sum of the sky-subtracted pixels inside its template's footprint, not the star's total light.
- `star_widths(image, positions=None)` gives one star width (full width at half maximum, in pixels) per color channel: the preview's channel-matching width (`star_width_match`). It names its estimator; no ratio to the one star-width scale is measured yet, so `widths_on_scale_px` is `None`. Without `positions` it uses the preview's own choice of bright, isolated, unsaturated stars.
- `measure_sky_gradient(image)` measures the sky's tilt across the frame as the preview does (`sky_plane`): the tilt as a share of the sky level, the limit, whether the preview would subtract the fitted plane, and the plane's terms.
- `measure_aperture(image, positions, radius_px=None, gain=None, read_noise_e=None, channel=None)` sums each circle and takes off the sky ring's clipped median (`frame_photometry.measure_aperture_photometry`), with each flux's 1σ uncertainty from the CCD noise equation. The gain and read noise come from the arguments, else the camera profile for the frame's setting or the header (`detector_noise`), else unit gain is assumed, and `noise_source` says which.
- `sky_corners(path)` gives a plate-solved image's four corners as `(ra, dec)` in degrees (`header_wcs`) with the header's `RADESYS` and `EQUINOX`, or `None` for an image with no plate solution (`header_is_plate_solved`).
- `solved_stars(stack_path)` reads the stars the astrometry run named on a stack, while the stack is unchanged since (`solved_star_list`).
- `robust_sigma(values)` and `sigma_clip(values, clip_sigma=..., maximum_passes=..., minimum_count=...)` are the library's robust spread (1.4826 times the median absolute deviation) and its clipping loop (`robust_statistics`).

The AI tools offer the image measurements as `quality_blocks_*` tools; `solved_stars`, `robust_sigma` and `sigma_clip` are for scripts only (see `mcp_servers/inventory/tool_dispositions.py`).

### `visualization.py`

`Visualization` draws images and charts.

- `render_fits` draws a frame, a stack or an array (`pixels`) as a PNG with a description (`kind="image"`), as a data URL for the app's viewer (`kind="data_url"`), or as a Matplotlib figure for scripts and notebooks (`kind="figure"`). In the Command Console the figure opens in a figure window; in a notebook it shows in the page. The brightness is the same for every kind: `stretch=True` is the app's automatic stretch, `stretch=False` a straight line from the darkest to the brightest pixel, and `center` with `width` a fixed range. `overlays` (none by default; `"detections"`, `"stars"` or both) marks the stars the astrometry run's star finder detects (from the stack's `_detections.json` file when it is still valid) and names the stack's stars from its `_identification.json` file, on the PNG and on the figure. Like Image Processing's Astrometry overlay, it names only stars with photometry in the library; with `target` and `path`, only that target's stars. The description or the title says why an overlay drew nothing. The overlay code is in `visualization/image_display.py`. The MCP tool offers the PNG and data-URL kinds and the overlays, not the figure.
- `plot(kind, ...)` draws one chart of a target or a star.

### `jobs.py`

`Jobs` is a read-only view of the job history (running and finished jobs, their log lines, stored results) and of the pipeline runs that produced a target's data. It opens the logs database read-only, so it cannot change it. `Jobs.query` returns a `JobQueryResult`, in which only the fields of the chosen `detail` are filled. The MCP tool `jobs_query` calls `Jobs.query`.

`detail="warnings"` answers the question "what warnings did this job detect?" and needs a `job_id`. A warning is a stored quality row of the job whose check failed (`check_outcome` is `failed`); it is listed with its pipeline, metric, subject, reason sentence, value, limit and validation register entry. A check that passed is not a warning. A check that could not run (`not_checked`) detected nothing, so it is only counted in `checks_not_run_count`. The answer also gives `measurement_count`, the number of rows the job stored, so three cases differ: an empty list with a nonzero count (the job was checked and nothing failed), a zero count (the job stored no rows, so there was nothing to check) and an unknown id (`NotFoundError`). Warnings that are not gates, such as frames moved to the excluded folder or a camera with no profile, are stored as notice rows (`<pipeline>.notice_*`) so that they appear here too. A row with no job id, such as one from a call with `register_job=False` outside any job or one backfilled from an older summary, belongs to no job and is listed for none. `detail="result"` and `detail="warnings"` also give `parameter_defaults`: one line for each parameter that used its default because no tuned or equipment value was set. The backend serves the same read as the RPC method `jobs:query`.

## Injecting drivers

`Astrometrics(config)` takes only the settings. It has no database or driver arguments, so a program always runs the built-in drivers over the database its settings name. Only a test swaps the database or a driver, and it does so through private code (`astrometricslib._internal.testing.astrometrics_with_drivers`). Nothing outside the library's tests and scripts may import that module.

A driver is the code that talks to one outside program or service. A test can swap any of them, for example to run with no network. The library uses five:

- a plate solver, which works out which part of the sky an image shows (built-in: Astrometry.net);
- a stacking program (built-in: Siril);
- the SIMBAD database of named astronomical objects (built-in: through astroquery, a Python package for querying astronomy services);
- Gaia DR3's low-resolution XP spectra, which the European Space Agency's Gaia satellite measured for its third data release (built-in: through astroquery, cached on disk);
- a source of interstellar reddening values (built-in: Gaia DR3 through astroquery).

Reddening is the color excess E(B-V) that dust adds to a star's light. B and V are two standard brightness bands, blue (about 4400 Å) and visual (about 5500 Å). E(B-V) is how much bigger the star's B − V magnitude difference is than it would be without dust. The spectroscopy pipeline uses it to correct a spectrum before it classifies the star, that is, before it decides the star's spectral type.

A test builds the root with the helper:

```python
from astrometricslib._internal.testing import astrometrics_with_drivers

astrometrics_with_drivers(config, catalog_access, *, plate_solve_driver=None, stacking_driver=None,
                          simbad_driver=None, gaia_xp_driver=None, reddening_driver=None)
```

A driver left out stays the built-in one. The helper puts the five into one `Drivers` object (`drivers/driver_set.py`) and gives it to `StellarCatalog` and `ProcessingPipelines`, which pass it to the pipelines as a `drivers=` keyword. The method signatures on the sub-APIs do not change.

A replacement subclasses `PlateSolveDriver`, `StackingDriver`, `SimbadDriver`, `GaiaXpDriver` or `ReddeningDriver` (from `astrometricslib._internal.drivers`; `StackSettings` and `StackRunResult`, which a stacking driver needs, are there too). A test can run a stage with a fake solver and no network:

```python
astrometrics = astrometrics_with_drivers(
    config, catalog_access, plate_solve_driver=MySolver(), simbad_driver=MySimbad()
)
astrometrics.processing.process_target("M 13", stages=["astrometry"])
```

### Where the drivers reach

- `processing.stack` uses the stacking driver.
- `processing.process_target` for one target:
  - gives the plate solver and SIMBAD driver to the astrometry, photometry and spectroscopy stages, and the Gaia XP and reddening drivers to the spectroscopy stage;
  - photometry gives them to every `StarIdentifier` it builds: the one for each session's reference frame and the one that solves a session's frame to match stars across sessions. The photometry workers (the frame-measuring pool) never build one, so they need no driver.
- `processing.plate_solve` and `processing.identify_stack` use the plate solver and SIMBAD driver.
- `processing.process_target` for a list of targets, or for every target, runs each target in its own worker process. A worker cannot receive a driver object, so the call raises `InvalidArgumentError` when any driver was given, instead of quietly using the built-in ones.

`test/test_driver_construction.py` fails when a pipeline module calls a built-in driver class directly, because such a pipeline would ignore the driver the caller chose. It also fails when a pipeline builds a class that falls back to an empty `Drivers()` (such as `StarIdentifier`) without a `drivers` argument, because that fallback builds the built-in drivers. `api/test/test_driver_injection.py` shows that photometry uses the fake plate solver and SIMBAD driver and touches no built-in one.

### Which frames a one-target run uses

`processing.process_target` for one target measures only the frames of one camera and one optic (one telescope or lens, identified by its focal length). It chooses them the way the batch run does:

- the camera: the first camera in the config's setups that has frames of the target, the primary camera first;
- the optic: the config's primary focal length (`[Observatory.Telescope] focal_length_mm`).

`camera_id` and `focal_length_mm` choose differently. Spectroscopy runs when that selection has spectral frames or the target has a spectral stack.

For exact behavior, read the code.
