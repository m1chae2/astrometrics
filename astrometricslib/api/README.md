# API

This folder holds the library's front door: the classes that scripts, backend services and the MCP tools actually call. MCP (Model Context Protocol) tools are the adapters through which AI agents call the library. Each file wraps the pipelines and drivers underneath in a stateful, easy-to-use interface.

## Public layout

The library has a small public surface. Everything else is private.

| Import from | What it holds |
| :--- | :--- |
| `astrometricslib` (the root) | `Astrometrics`, `AppConfiguration`, `get_configuration`, `configure_logging`, `configure_offline_iers` and `warm_earth_orientation_data`; the sub-API classes `TargetCatalog`, `TargetFrames`, `StellarCatalog`, `ProcessingPipelines`, `CalibrationCatalog`, `QualityRecords`, `Visualization` and `Observatories`; the core records `Target`, `FrameRecord`, `StellarObject` and `FilterType`; the equipment models; and the input models `CaptureSetting` and `JobSummary` (the job that `jobs.get_log` and `jobs.get_warnings` take). |
| `astrometricslib.exceptions` | The errors a script catches, `ErrorInfo` with `to_error_info` and `error_from_info`, `wrap_outside_error`, `MovedError` and `FITS_READ_ERRORS`. Each error says how it is shown (`report`: `status`, `error` or `notify`) and logged (`log_level`). |
| `astrometricslib.arguments` | The argument types and checks both libraries share: `TimeInput` with `to_epoch_seconds`, `Page`, `FrameChoice`, `observing_night_id`, `check_choice`, `check_include`, `check_limit` and `reject_unused_arguments`. |
| `astrometricslib.reports` | The quality reports and quality row shapes that checks return, and `CaptureSetting` (also at the root, as the input model of the calibration calls). |
| `astrometricslib.jobs` | `Jobs` (`astrometrics.jobs` is an instance of it), the job store and records, and the job context tools (`registered_job`, `running_as_job`, `get_current_job`, `report_started_jobs`, the `background_job` marker and the abandonment switch). `run_as_background_job` runs a slow call in a thread and answers with its result or its job id; the backend and the MCP servers both use it. |
| `astrometricslib.drivers` | The data store and file tools that other apps share (`Butler`, `connect_db`, `file_lock`, `is_path_inside`, `resolve_mounted_path`, `get_simbad_driver`, `header_is_plate_solved` and the like). |
| `astrometricslib.parameters` | The tuned-parameter declaration (`TunedParameter` and its enums), `collect_parameters`, `resolve_parameter` and the provider protocols. |
| `astrometricslib._internal` | Everything else, in logical groups. |

The rules:

- **Only `astrometricslib` itself may import `_internal`.** `wayfindinglib`, the backend and the MCP servers use the root and the public modules only. Tests of the libraries are the one exception.
- **A result model is private, and its fields are not.** A call returns a Pydantic model (a Python class with typed, validated fields) such as `ImageDeletionResult` or `StackResult`. A caller reads the fields by name and does not import the class. The API reference page lists the fields of each result without an import path.
- **A caller reaches a sub-API through `Astrometrics`.** Build one `Astrometrics` and use `astrometrics.targets`, `astrometrics.processing` and the rest, so all of them read and write the same storage.
- **Old names have no alias.**
- **Every public method follows the design rules.** The [public API design guide](../../documentation/library_design/Public_API_Design_Guide.md) sets the verbs, argument names, defaults, return types and depth of a public method, for both libraries. `test/test_public_surface.py` checks each method against them, with the rule code in `_internal/public_api_rules.py`. Known departures are listed in `test/public_api_rules_baseline.txt`; a change that fixes one deletes its line.

Terms are defined in the [glossary](../../documentation/Glossary.md). This document also defines each term the first time it appears.

A target is one sky object the library tracks, with its raw frames (single camera exposure files) and results. A stack is the image made by aligning and averaging many frames.

## What each file is for

The `Astrometrics` class in the package's `__init__.py` (the "root") builds one object per file below and exposes each as an attribute, such as `astrometrics.stars` or `astrometrics.processing`. Each of these objects is a sub-API.

Each sub-API checks its arguments and hands the work to `pipelines/`. Three rules hold for every sub-API:

- A method that takes a target accepts its id or the `Target`. An id that names no target raises `NotFoundError`.
- A method that offers variants picks one with `kind=` and adds optional sections with `include=`. It refuses an argument that the chosen variant does not use.
- A method that builds a new answer returns a Pydantic model (a Python class with typed, validated fields), for example `ImageDeletionResult` or `StackResult`. It does not return a dictionary.
- A `limit` (and `offset`, `lines`, `include_frames`) outside its documented range raises `InvalidArgumentError`; it is never moved into range. Each method says what `None` means. The one check is `check_limit` in `foundation/arguments.py` (public as `astrometricslib.arguments.check_limit`; wayfindinglib uses the same one).
- A pixel position a method returns is 1-based, as in FITS and DS9: the center of the first pixel is 1, 1. `StellarObject.star_data` is the exception: it is the star finder's own row, stored as found, and its `xcentroid` and `ycentroid` count from 0.

- A row carries the values a caller would otherwise import a helper for. These are worked out when read and are not saved, so the stored form does not change: `FrameRecord.is_spectral`, `Target.object_category`, `Target.ra_deg` and `Target.dec_deg`, and `TargetStackingResult.preview_path`. A limit a row reports is the limit in force now, not the one in force when the row was stored. Two limits sit on returned answers instead: `CalibrationQueryResult.dark_temperature_tolerance_c`, and `limits` on the `MetricSpec` of `frame.saturated_pixel_fraction` (the saturated-star blob size in pixels and the share of frames that makes an exposure length clipped).

### Jobs

Every pipeline run records a job, whoever starts it: a stack, a preview, an analysis stage, a measurement run. There is no switch to turn it off. A run inside a job that is already current joins it instead of listing the same work twice: the job of a larger run that called it, or a row the caller made and entered with `astrometricslib.jobs.running_as_job` (the backend does this for its own job rows). Reads, such as `stacking.predict` and `targets.measure_field_centers`, record none.

### `observatories.py`

`Observatories` is `Astrometrics.observatories`. Its `configurations` child (`ObservatoryConfigurations`) keeps every observatory configuration: one set of equipment (telescope, main camera, and optionally guide scope, guide camera, focuser, filter wheel and mount) used together over a range of dates. Each method is a thin wrapper of a function in `pipelines/shared/equipment.py`.

- `get(configuration_id)` reads one configuration, or `None`.
- `query(camera=, telescope=, time=, text=, limit=None, offset=0)` lists them, every match by default, as a `Page` (`items`, `total`, `next_offset`).
- `create(configuration)` stores a new one: any change of equipment is a new configuration. `update(configuration, **changes)` changes only the name, notes and dates, refuses a copy whose revision is no longer the stored one, and returns the saved configuration.
- `scan()` creates the configurations the settings and the frames imply and points each frame at its own. The first call of any method scans once by itself.

### `targets.py` and `_target_frames.py`

`TargetCatalog` creates, reads, changes and deletes targets. Each method names its owner function in `pipelines/shared/` (`target_records.py`, `target_overview.py`, `name_resolution.py`).

- `get(target_id, required=False)` returns a `Target` for code to work with, or `None`; with `required=True` an unknown id raises `NotFoundError`. It first brings that one target up to date with storage (see `pipelines/shared/target_records.py`): nothing is read when the library write counter has not moved, one row is read when it has, and every target is read only when this catalog does not hold the target yet. Unsaved edits to a held target are kept. A lock keeps threads from refreshing at the same time. A test reads a saved record straight from storage with `astrometricslib._internal.testing.read_saved_target`.
- `get_data_version(target=None)` gives an opaque text that changes when the target's stored record, quality measurements or calibration records change (with no target, when any target record is written), and `get_record_versions()` gives a `TargetRecordVersions` with an opaque text for each stored target record (a measurement does not change it). Both read no rows, so a cache can keep what it worked out while the texts stay the same; compare the texts, read nothing else into them.
- `create(name, from_catalog=False)` makes a target, or returns the one with that id. `add(target)` adds a `Target` object. Both save.
- `update(target, **changes)` sets fields, saves and returns the target. `processed_image=path` sets the finished picture (a `.jpg`, `.png` or `.tiff`). A typed `ra` or `dec` clears `position_unverified`. There is no public `save`: every write saves.
- `delete(target)` removes the target record; the frame files stay.
- `resolve(name)` returns a `Resolution` (`name`, `ra_deg`, `dec_deg`, `source` and the library's `target` or `star`): the library's targets first, then its stars, then SIMBAD. It returns `None` when no one knows the name.
- `query(text=, camera=, configuration=, ra_deg=, dec_deg=, radius_deg=, object_type=, order_by=, include_empty=False, limit=None, offset=0)` returns a `Page` of targets, every match by default, in stored order unless `order_by` is `"newest"`, `"name"` or `"separation"`. It reads what other programs saved and marks no target as changed. `query(include_empty=True)` is every target.
- `count_by_camera()` gives the light frames of each camera and the per-target camera index the app's target list uses (`pipelines/shared/target_camera_index.py`). `count_by_night()` gives how many targets have frames from each observing night.
- `measure_field_centers()` lists the distinct sky positions imaged (`ra_deg`, `dec_deg` and the targets at each).

`TargetFrames`, reached as `targets.frames`, works on a target's frame records (owners in `pipelines/shared/target_frames.py` and `pipelines/stacking/frame_status.py`). Each method takes the `Target` itself.

- `query(target, night=, since=, until=, filter_name=, first_file=, last_file=, configuration=, gain=, exposure_s=, status=, order_by=, limit=None, offset=0)` returns a `Page` of the target's timed light frames, oldest first. It is what a pipeline's `frames=` argument takes. `status` is the frame's state in the newest stack: `"included"`, `"flagged"`, `"not_stacked"` or `"set_aside"` (the files in the target's `_excluded` folders).
- `get_newest(target)` gives the light frame taken last.
- `add(target, paths, camera=None, configuration=None)` brings FITS files or folders into the library. A file not yet at `lights/<target>/<telescope>/<camera>` is sorted into place (light frames under the target, darks, biases and flats to the calibration folders); a file already there is indexed where it is. It points each frame at its observatory configuration, saves the target and returns the added records. A finished picture is refused: set it with `update(target, processed_image=path)`.
- `scan(target=None, prune_missing=False)` reads one target's folders, or every target folder (creating a target for each new folder), again; it reads the header of each listed frame whose file changed. Inside a job (`astrometricslib.jobs.running_as_job`) the job's progress counts the folders.
- `get_header(path)` reads the first FITS header with typed values, without the pixels. A client that must not read any file checks the path itself first (the backend does).
- `get_rotation(target, frame)` gives the quarter turn that shows a raw frame the same way round as the target's stack (display only).
- `get_nights(target, night=None)` groups the frames into `TargetSession` records: one for each night (noon to noon, local time) and gain and offset setting.
- `delete(target, frames)` deletes frame files, removes their records and removes their stored quality measurements. With `target=None` each frame's target comes from its `lights/<target>` folder.
- `get_statuses(target)` gives each frame its state for the File Browser's Status column: `included`, `flagged` (stacked, but its stars are stretched), `not_stacked` (taken after the newest stack file) or `set_aside`. `get_set_aside(target)` lists the set-aside frames with their kind and reason and says where the reason came from. `restore(target, frames)` moves chosen set-aside frames back and scans the target; a frame whose old place is taken, or that has no `excluded_frames.json` entry, stays where it is.

A stack recorded by camera and focal length (`stacking.stacks_by_configuration`) also records the observatory configuration its frames share (`configuration_id`). `pipelines/shared/analysis_configuration.find_configuration_stack` finds a target's stack of one configuration, matching an older record by camera and focal length.

### `stars.py`

`StellarCatalog` reads and changes the star records. Each method is a thin wrapper of one function in `pipelines/shared/star_catalog_queries.py`, or for the period searches in `pipelines/photometry/processing/star_periodicity.py`.

- `get_data_version()` gives an opaque text that changes on any write to the star catalog, whichever program made it, so a cache of a whole-catalog answer can keep it while the text stays the same.

- `get(star_id, include=None, required=False)` returns one star, or `None`; with `required=True` an unknown id raises `NotFoundError`. Spaces, underscores and capital letters may differ from the stored id.
- A star's light curve is most of its record, so `get` and `query` leave its points out unless asked with `include=["light_curves"]`. Such a star still says what is stored: `has_photometry`, the period results and the per-night summaries are there, and `light_curves_included` is `False`. The database removes the points before the record is read. A star read without its light curve cannot be saved as it is; `update` changes the stored record instead.
- `get_spectrum(star)` returns a star's `SpectroscopyResult`, or `None`. Older libraries also hold a copy of the star under an id ending in `::spectroscopy`. `get_spectrum` reads that copy when the star has no spectrum of its own, so scripts never need to build or test for it. Spectra are not an `include=` part.
- `query(...)` lists the stars that match some filters as a `Page` of `StellarObject` (`items`, `total`, `next_offset`), every match by default (`limit=None`).
  - Filters: `target=` (a `Target`), a sky circle (`ra_deg`, `dec_deg`, `radius_deg`), `magnitude_min` and `magnitude_max` (the astronomer's brightness scale, where larger numbers are fainter), `has_photometry`, `has_spectra`, `has_catalog_magnitude`, `spectral_class`, `variable` and `text` (a search of ids and names). The spectral class is the letter of the star's type in the O, B, A, F, G, K, M sequence, hottest to coolest. A full type such as `G2V` counts as `G`. `variable=True` keeps the stars SIMBAD, Gaia DR3 or VSX list as variable or suspected variable (`StellarObject.known_variability`).
  - `StellarObject.magnitude` is one field. It holds SIMBAD's V magnitude for a star SIMBAD names, Gaia's G magnitude for a star named from Gaia only, `None` when no catalog gave one, 0 on old records for "none given", and an instrumental magnitude (measured by an earlier version of this library's photometry, on its own uncalibrated scale, about -10 to -17) on old records. A filter on "real catalog magnitude" (`has_catalog_magnitude=True`) keeps the first two: a finite value of at least `BRIGHTEST_CATALOG_MAGNITUDE` (-2) that is not 0.
  - `order_by` sorts by id (the default), by usefulness (`"useful"`: stars with spectra first, then named stars, then stars with photometry, then brightest first), or by spectrum match (`"match"`: stars whose own spectrum best matches a reference spectrum first).
  - The filters run on the indexed columns. A plain listing (no circle, class or variability filter, in id or useful order) is counted and paged inside the database; only the stars of the page are read.
- Single-frame detections are hidden unless `include_unresolved=True`. Photometry (brightness measurement) saves each point source it finds in one frame under an id ending in `:Star_<n>`. These are working records, not catalog stars, so a normal query leaves them out.
- `count_by_class(target=None)` and `count_by_target()` count stars from the indexed columns, and `get_statistics()` gives the whole catalog's counts and coverage.
- `create(name, ra_deg, dec_deg, **fields)` records a new star (the position in ICRS degrees; a stored id raises `ConflictError`). The catalog keeps only measured stars, so a star given no light curve or spectrum is returned but not saved. `update(star, **changes)` takes `StellarObject` field names, raises `InvalidArgumentError` for any other name, changing nothing, and returns the saved star. `delete(star)` removes it.
- `measure_periodicity(star)` runs the period and transit searches on a star's light curve and returns a `PeriodicitySearch`, saving nothing. `record_periodicity(star)` runs them and saves the results on the star.
- A star overlay (the stars placed in 1-based pixels, as in FITS and DS9, on a target's stack or a named image) is `visualization.get_star_overlay(target)`, built by `pipelines/shared/star_overlay.py`.
- Removed names raise "moved to": `dataset_version` (a cache compares `stars.get_data_version()` instead), `find_or_create_by_position` (now private) and `analyze_periodicity` (`record_periodicity`).

### `processing.py`

`processing.py` holds `ProcessingPipelines`, which holds one object per pipeline. The objects are written in three private files: `StackingPipeline` in `_processing_stacking.py`, `EnhancementPipeline` in `_processing_preview.py`, and `AstrometryPipeline`, `PhotometryPipeline`, `SpectroscopyPipeline` and `AsteroidPipeline` in `_processing_analysis.py`. Callers reach them as `astrometrics.processing.stacking`, `.enhancement`, `.astrometry`, `.photometry`, `.spectroscopy` and `.asteroids`. `StackingPipeline` is also exported from the package root, for `predict_weights`. There is no call that runs every pipeline: a script, and the app's Analyze Target button, call each pipeline in turn. Each method takes a `Target` and names its owner function in `pipelines/`. `quality.py` holds `QualityRecords`, which is a sub-API of its own (see below).

- `stacking.run(target, frames=None, force=False, ...)` stacks a target's light frames. `frames=` is the `Page` that `targets.frames.query` returns, a list of frame records or a list of the target's frame paths; a page cut short is refused. Left out, every imaging light frame of the target. Spectroscopy frames are chosen with `filter_name="SPEC"`. The list is checked by `pipelines/shared/frame_choice.py`: frames from two cameras, or from one camera behind two optics, are refused with each group and its frame count, and so is a mix of imaging and spectral frames. `astrometricslib.arguments.check_frames(frames, target)` runs the same check without reading a frame; the backend runs it when the Stack Frames or Check Frames click sends a frame list, so the click gets an error reply and no job is made. The Siril overrides are `rejection_sigma`, `filter_wfwhm`, `filter_round`, `stack_weight` and `generate_rejmap` (`None` means the configured value). The run makes no picture. Owner: `pipelines/stacking/stack_request.stack_target`.
- `stacking.predict(target, frames=None)` says what a stack would do with its frames, without stacking (the app's Check Frames). It chooses the frames as `run` does and returns a `StackPrediction`: how many frames would be stacked, the frames that would be set aside or kept with an uneven-sky warning (each with its kind and reason), and for each exposure group the darks, bias and flats it would use (count, folders, and the library's flags for a near match). The frame checks and the calibration choice are the ones the stack runs, so the two agree. Nothing is stacked, moved, stored or saved. The cloud and trailing check reads every frame, so a large target takes a while. A prediction is a read and records no job of its own. The backend serves it as the background job `processing:check_stack`.
- `stacking.predict_weights(exposures_s, kind=...)` forecasts a stack before it exists. Given the frames' exposure lengths (and, when known, their star widths, variances and group noises), it runs the stacker's own rules and returns a `StackWeightPrediction`: the weighting mode, the exposure group each frame lands in, and each frame's weight, or the reasons the weights are unknown. It reads and saves nothing, so code without an `Astrometrics` calls it on the class, `StackingPipeline.predict_weights(...)`.
- `stacking.get_summary(target, kind="imaging")` reads the summary the stacking stage saved with a stack. `stacking.get_stack(target, configuration=None)` gives the target's stack of one observatory configuration (or its preferred stack), the record a pipeline's `stack=` argument takes.
- `enhancement.run(target, settings=None, stack=None, keep_previous=True, force=False)` makes a stack's preview picture without restacking. The app's Stack button runs it after `stacking.run`. `settings` is an `EnhancementSettings` (exported from the package root) whose values apply to this run only. A picture newer than its stack and made with the settings in force is kept unless `force` is set or `settings` are given (`kept_unchanged` in the result). The result carries `preview_settings`, read from the record saved beside the stack (`<stack name>_preview_settings.json`), or `None` when the picture has no record.
- `enhancement.get_bright_objects(target, force=False)` lists the nebulae and galaxies SIMBAD places inside a target's imaging stack, nearest the center first, using the stack's plate solution; it returns a `BrightObjectChoices` with `objects`, or no objects and a `message` (no stack, "Run Astrometry first to list objects in the frame", SIMBAD out of reach). SIMBAD's answer is kept in the library's stored catalog answers; `force=True` asks SIMBAD again. The choice of what the picture's masked stretch protects is the target field `preview_bright_object`, set with `targets.update(target, preview_bright_object=PreviewBrightObject(...))`. The backend serves the list and the choice as `processing:list_bright_objects` and `processing:set_bright_object`.
- `astrometry.run(target, stack=None)`, `photometry.run(target, frames=None, stack=None)`, `spectroscopy.run(target, stack=None, max_stars=None)`, `spectroscopy.record_variation(target, frames=None)` and `asteroids.run(target)` each run one analysis stage on the frames and stack the target already has (owners in `pipelines/pipeline_runs.py`, over `pipelines/tasks.run_target_stages`). Each run records one `analysis` job and holds a job slot. They return a `ProcessTargetResult`.
  - Astrometry is the core layer: photometry and spectroscopy only read its plate solution and never run it, so run `processing.astrometry.run(target)` first. Photometry needs a current, solved result for the stack it analyzes. Spectroscopy needs the solved imaging stack of the same camera and optic, else the spectral stack's own solution (`processing.astrometry.run(target, spectral_stack)`). Without one the stage is skipped and not run on a guess: `stages_skipped` holds the reason `needs astrometry: <why>; run processing.astrometry.run(target) first`, and the job lists it as a warning. Before issue 182 these calls ran astrometry themselves. Spectroscopy is still a prerequisite of the spectral variation: a run adds it, listed in `prerequisites_run`, when its saved result is missing or older than the spectral stack.
  - `stack=` names another configuration's stack (from `stacking.get_stack`) or an image path; the run analyzes it, and photometry measures the frames of its camera and optic. A photometry frame list from two cameras or optics is refused with the counts.
  - `record_variation` follows each star's spectrum across the raw spectral frames. It saves no stars, keeps its summary in `quality.spectroscopy_variation`, and skips a night of fewer than 2 frames with the reason in its result (`skipped_frames`).
  - The asteroid search is experimental and uses the configured `[Processing.MovingObject]` settings.
- The full pipeline for many targets at once (stack, then the analysis stages, one worker process per target) is the internal `pipelines/target_batch.process_targets_in_parallel`, which `scripts/run_all_target_processing.py` calls.
- A restack keeps the stack it replaces in a `_previous` folder. No public call deletes it or puts it back.
- Siril's window and the Siril runs the library started are reached through `astrometricslib.drivers.get_stacking_driver()` (`open_in_viewer(path)`, `stop_running_programs()`); the backend uses them for its "open in Siril" button and at shutdown.
- `stack_subset(pipelines, target, frames, label=...)` is not a method. It is an internal function (in `astrometricslib._internal.processing_scripts`, code in `script_calls.py`) that only the library's own scripts and tests call. It stacks exactly the given frames into the target's `_subsets` folder with the normal settings, and stores the result's noise, effective frame count and effective time. With `record_forecast_rows=True` it also stores the rows a library stack stores for the forecast check (one `stacking.frame_weight` for each frame on the frame's subject id plus `#<label>`, so the weights never hide the library stack's newest rows; the exposure-group rows on the subset's own group subjects; and a calibration record), so a subset such as the stack of all nights but the last (`label=EARLIER_NIGHTS_VARIANT`, a constant in `astrometricslib.reports`) can be the earlier member of the forecast check's pair. It never writes to the library stack's path, assigns nothing on the target and saves nothing. The noise records that stack subsets (`record_noise_growth`, `record_night_contributions`, `record_odd_even_noise`) are on `quality.stacks`; the app has the one RPC `processing:measure_noise`, which takes a `kind`. See [subset stacks](../pipelines/stacking/README.md#subset-stacks).
- `restore_excluded_frames(pipelines, target, apply=True)` is not a method either. It is an internal function in the same module, used by `scripts/restore_excluded_frames.py`. It moves frames the stacker set aside back into the frames folder. The stacker sets a frame aside, into an `_excluded` folder, when clouds or trailed stars (stars smeared into short lines) make it unusable.
- `astrometry.solve(path)` works out where a FITS frame (the standard astronomy image file) points, using the stars in it. It returns a `PlateSolution` (the image center in `ra_deg` and `dec_deg`, `pixel_scale_arcsec`, `rotation_deg`, the size, and the pixel-to-sky mapping, a WCS or World Coordinate System, as header cards in `wcs_header`), or `None`. The centering step in wayfindinglib uses its center to point the telescope exactly at a target.
- `astrometry.identify(path)` names every star the stack's own star finder detected, for the viewer's Astrometry button. It keeps the stack's plate solution when the header has `PLTSOLVD`, and otherwise solves the stack and writes the solution into it and its viewer copy. The detections are matched to the Gaia stars of the cache tiles under the stack and, when online, to SIMBAD, whose most familiar designation wins (proper name, Bayer, Flamsteed, HD, HIP, TYC, then `Gaia DR3 <id>`). Its `x` and `y` are 1-based pixels. Each star has a `kind`: `matched`, `unmatched` (`Unnamed star`) or `catalog_only` (a Gaia star one magnitude brighter than the predicted limit with no detection). Among names of one kind the alphabetically first is chosen, so the label does not change between runs, and the star's other SIMBAD names are its `aliases`. A star the library already has a record of (`Gaia DR3 <id>`) gains the names it lacks as aliases (`alias_records_updated` counts them). Raw frames are refused. Inside a job context (`astrometricslib.jobs.running_as_job`) it reports its progress to the job, and a run given up on stops before its next step. The result is saved next to the stack (`<stack>_identification.json`, layout version 4), and `astrometry.get_identification(path)` reads it while the stack is unchanged. The backend runs it as an analysis-type job (`analysis:identify_stack`, `analysis:get_stack_identification`).
- `astrometry.get_named_stars(path)` reads the stars an astrometry run named on a stack, while the stack is unchanged.
- Removed names raise "moved to": `stack`, `predict_stack`, `predict_stack_weights`, `stack_summary`, `find_stack_configuration`, `remake_preview`, `list_preview_bright_objects`, `set_preview_bright_object`, `process_target`, `plate_solve`, `identify_stack`, `get_stack_identification`, `acquire_job_slot`, `open_in_siril`, `stop_stacking_programs` and the three stage-name lists.

### `calibration.py`

`calibration.py` holds `CalibrationCatalog` (`astrometrics.calibration`) and its child `CalibrationFrames` (`astrometrics.calibration.frames`). They track the dark, bias and flat frames, the calibration frames that measure the camera itself (see `astrometricslib/_internal/drivers/README.md`). Each method is a thin wrapper; the work is in `pipelines/stacking/calibration_catalog.py` and, for the sensor noise, `pipelines/stacking/sensor_noise_run.py`. A `CaptureSetting` says which sets a call means: the camera is compared ignoring case, the gain as a number, the binning in its standard form (`2` is `"2x2"`), a dark's temperature by its temperature slot and its exposure within 0.05 s, and a flat's filter. A field left empty is not compared.

- `query(kind=None, setting=None)` returns a `Page` of `CalibrationSetCount` rows: how many frames the library holds of each kind, camera and setting. With a setting it also answers a plan made before any frame exists. It writes nothing.
- `match(frames)` groups light frames (frames of the sky) by camera, optic, filter, gain, offset and exposure, and runs the stacker's own dark, bias and flat selection for each group. It returns one `CalibrationMatch` per group, with each kind's count, the settings it fell back to and why nothing matched. It takes the `Page` a frame query returns or a list of frame records.
- `assess(kind, setting=None)` judges the sets of one kind (`"dark"`, `"bias"` or `"flat"`). It gives one `CalibrationSetHealth` for each set, with one check per condition, each passed, failed or `not_checked` with the reason. A dark or bias set is judged from the numbers stored for each of its frames, so it needs `frames.record` to have run. A flat set is measured when asked. A check with no reference (for example a bias level the camera profile does not hold) is `not_checked`, never judged against a default. Nothing is written.
- `get_profile(camera)` returns the stored `CameraProfile` of a `Camera`, matched by the camera's name and aliases in any spelling the profile lists (case, spaces and punctuation are ignored). It carries the camera's saturation limits with their sources and its gain and read noise for each sensor setting. `None`, or a camera with no profile, gives the generic fallback profile (`is_generic_fallback` is `True`).
- `measure_sensor_noise(camera, setting=None)` measures the camera's conversion gain (electrons per ADU, one step of the stored pixel value) and its read noise (the electronic noise added when a frame is read out) from the flat and bias frames in the library at exactly that setting. It needs at least 5 flat pairs and 3 bias pairs that share one setting, one flat exposure and one temperature. A gain, offset or binning the setting leaves out is filled when the library holds exactly one setting of the camera that fits. A left-out binning is otherwise `1x1`; a left-out gain or offset otherwise raises `InvalidArgumentError`, which lists the settings the library holds. If it cannot measure, the result says why and holds no numbers. It writes nothing. `record_sensor_noise(camera, setting=None)` measures the same way and writes a measured result into the camera profile in the configuration file, after a backup; the result's `provenance` sentence is stored as the value's source. Its result matched a hand measurement (measured; see [STK-35](../../documentation/library_design/validation/stacking.md#stk-35)).
- `frames.add(paths, telescope=None)` moves new FITS files into the calibration folders by their headers, rescans every kind and saves the index. `frames.scan(kind=None, prune_missing=False)` rescans and saves without moving files. Each returns one `CalibrationIngestReport` per kind, with the paths it added and one `CalibrationSetHealth` for each set that gained frames. A new flat set is measured. A dark or bias set is not measured by the rescan; it is judged from the numbers `frames.record` stored, so a new frame with no numbers yet shows checks that are `not_checked`, with the reason. The app starts `frames.record` by itself after it ingests or downloads dark or bias frames; a script must call it.
- `frames.record(kind=None, setting=None, force=False)` measures the dark and bias frames that are new or changed and stores their numbers. A first pass over a large library takes about half a second per frame. It never changes a frame file.

Each of `assess`, `measure_sensor_noise`, `record_sensor_noise` and `frames.record` records a `diagnostics` job.

### `quality.py`, `_quality_frames.py` and `_quality_building_blocks.py`

`QualityRecords` is reached as `astrometrics.quality`. It holds five objects: `records` (`QualityMeasurements`, in `quality.py`) reads what earlier runs stored; `frames` (`QualityFrames`) and `stacks` (`QualityStacks`), in `_quality_frames.py`, measure raw frames and stacks now and record their numbers; `detections` (`QualityDetections`) and `blocks` (`QualityBlocks`), in `_quality_building_blocks.py`, measure one image. Only `frames.record` and the three `stacks.record_*` methods change stored data. Frame state (statuses, the set-aside frames and putting them back) is on `targets.frames`, and `targets.frames.delete` removes a deleted frame's stored measurements. Each method names its owner function in its docstring.

Stored reads, `quality.records`:

- `query(metric=None, level=None, target=None, night=None, camera=None, telescope=None, since=None, until=None, latest_only=True, variant=None, library_only=False, limit=None, offset=0)` reads the quality measurements that earlier runs saved in `astrometrics.db` and returns a `Page` of `QualityMeasurement`. It returns every match unless `limit` is given. It gives the newest row for each subject and metric unless `latest_only=False`. `variant` keeps only the rows about one subset stack, and `library_only=True` leaves subset-stack rows out (giving both raises `InvalidArgumentError`). A library with no quality table yet gives an empty page; the read creates no file and no table. A `metric` that is not registered raises `InvalidArgumentError`.
- `get(row_id)` reads one row by its id, even when a newer row replaced it, so a report's citation always finds its row. `get_data_version(metric=None, level=None, target=None)` gives a short opaque text that changes whenever a row of that metric, level and target is added, removed or replaced, or a frame of the target moves to another target, and stays the same otherwise. It reads no rows, so a cache can keep what it worked out from `query` while the text is the same; compare the text, read nothing else into it. `get_paths(row_ids)` gives the frame or stack file behind each row, with a plain reason when there is none, and lists the ids no row has.
- `get_data_version()` with no filter changes on any write to the quality store (rows, capture settings, calibration records).
- `get_camera_data_version(camera=None, target=None, before_night=None)` gives an opaque text that changes when the measurements or calibration records of a camera change, or of every camera a target's measurements used; with `before_night` it counts only the nights before that one. `get_data_version(..., subject_ids=...)` covers one metric's frame rows of chosen frames. `quality.stacks.get_data_version()` covers the stack-level measurements of every target, the calibration records and the capture settings.
- `get_capture_settings(ids=None)` gives each stored capture setting with its id (`StoredCaptureSetting`: `id` and `setting`), the camera, telescope, filter, exposure, gain, offset and binning a row's `capture_setting_id` points at.
- `get_calibration_identities(target=None, run_ids=None)` reads which calibration each library stacking run used: the flat, bias, flat-bias (the bias removed from the flats, at the flats' own gain and offset) and dark masters (path, size, modification time), optic, camera, Siril version and stacking algorithm version. Two runs of a target whose records differ are confounded by a calibration change. A record made before schema version 6 has no flat-bias record (`None`), and the forecast check does not count that as a difference. An unmigrated or missing database gives an empty list.
- To tell whether two stacks' noise was measured in the same apertures, read the stack's `stacking.aperture_set_number` row with `records.query(metric="stacking.aperture_set_number", target=target, library_only=True)` and turn each row's `value` into text with `aperture_identity_from_number` (a private helper; `wayfindinglib` keeps a copy pinned by a test). Equal text means the same set; a not-measured row or a missing row means unknown. An odd–even difference run stores the same number as `stacking.odd_even_difference_aperture_set_number`.
- To test where the fixed-pattern noise sits, read the `stacking.odd_even_difference_aperture_record_count` row of the library stack: its reason holds the path of a JSON record (one entry per empty aperture with its position, its distance from the image center and from the target, and its values on the sum A + B and the difference A - B of the two half stacks), which `quality.stacks.get_aperture_record(path)` reads. It returns `None` for a missing, unreadable or other-version file. The row's four neighbors, `stacking.odd_even_difference_row_average_scatter_stack_unit`, `..._column_...`, `stacking.odd_even_sum_row_average_scatter_stack_unit` and `..._column_...`, give the line pattern.
- `get_metrics(checkpoint=None)` lists the whole declaration (`MetricSpec`) of every metric, or of those measured at one checkpoint; `get_metric(name)` gives one, and an unknown name raises `NotFoundError`.

Frames, `quality.frames`:

- `measure(frames, include=None, trend_frames=None, trend_threshold_pct=None, bias_level_adu=None, predict_exposure_s=None)` measures raw frames and stores nothing. `frames` is a frame query's page, frame records, or paths of files in the library or not (the camera comes from each header). It works out from the filters whether the frames are imaging or spectrum frames and refuses a mix. Imaging frames get the batch check (`checks`): star count, width, roundness and trailing, sky level, saturation and the jump from the frame before, with the frames that stand out flagged and the slow drifts across the newest frames; the sky level is trended only when every frame has one exposure length. The check's widths are its own second-moment estimate (`fwhm_estimator`), which has no ratio to the one star-width scale, and `fwhm_not_on_scale_reason` says so. With `include=["metrics"]` imaging frames also get the `frame.*` metric set that `record` stores (`metrics`: star width in pixels and arcseconds, elongation, sky rate in electrons per second per pixel, sky noise, background, saturation), about 12 s a frame; each star width names its estimator and is given on the one star-width scale where it has a ratio. The sky metrics need the bias level of each frame's setting, from the calibration library's bias frames or `bias_level_adu`. Spectrum frames get the spectrum check (`spectral`): the zero order, the tilt and width of the spectrum trail, the sky level and every saturated patch, grouped by exposure length and by pier side; with `predict_exposure_s` it scales the peaks to that exposure and says whether the spectrum would clip. Which frames a stack would set aside is `processing`'s stack prediction.
- `record(target, frames=None)` measures a target's light frames (or the ones given, as a frame query's page, frame records or paths) and stores the numbers in the quality database (read them with `records.query`). It reads each frame once and measures the stars' width and stretch, the sky and its noise in electrons, the read noise and the temperatures. A value it cannot measure is stored as `not_measured` with the reason. A frame whose file has not changed since its last measurement is skipped, so a second call measures nothing again. A frame that fails, for any reason, is counted and tried again next time. It never moves or changes a frame file. Only one run measures a target at a time, and one run reads frames at a time; a second call for the same target returns at once with `already_running` set. A sync measures only the frames it added, at about 11 s per frame. It runs as a background job of type `quality` and returns a `FrameMeasurementSummary`. A sync that adds frames starts it by itself. See [frame measurement](../pipelines/stacking/README.md#frame-measurement). The star measurements are a design estimate (see [AST-17](../../documentation/library_design/validation/astrometry.md#ast-17)).
- `get_blink_partner(target, path)` picks what the viewer's Blink button compares for a flagged or set-aside frame: a typical frame of the same session (the batch the frame quarantine judges it in), and one reference star in both frames. The typical frame has the stored `frame.star_elongation` and `frame.sky_unevenness` closest to the session medians. The star is bright, isolated and unsaturated, near the frame center, picked with the candidate rules of the star-shape measurement. The result has `found`, `reason` (when nothing was found), `path`, `typical_path`, the star in each frame (`star_x`, `star_y`, `typical_star_x`, `typical_star_y`, 1-based pixels), `turned` (the typical frame is turned half a revolution, a meridian flip), `votes`, `session_frame_count` and the frame size (`width`, `height`). Nothing is stored. The File Browser and the frame status timeline reach it through `target:get_blink_pair`.
- `map_positions(from_path, to_path, points=None)` finds where 1-based positions of one image lie on another (the center of the first image when `points` is left out): through both images' plate solutions, else through a stack's registration record (frame to stack, stack to frame, two frames of one stack, or frames of two stacks through the stacks' plate solutions), else, for two frames of one size, by matching their bright stars the way the quarantine's pointing check does (trying the second as it is and turned half a revolution), else the same pixel as a guess. A stack turned by a quarter turn after stacking is followed on its saved pixels. It returns `MappedPositions`: `method`, `note` and one point per position with `mapped_x`, `mapped_y` and `inside`; a position it cannot follow (a frame Siril left out, a spectral stack) has no mapped position and `method="none"`. Only star matching reads pixels. The viewer reaches it through `images:map_position`.

Stacks, `quality.stacks`:

- `measure(target_or_path, stack=None, include=None, compare_to=None)` measures a stack (star width, the share of rejected pixels, frame registration) and compares it with the previous stack or another stack file. A target's main imaging stack is measured unless `stack` names another of its stacks, such as its spectral stack (whose empty-sky noise is then not measured). The star width names its estimator (`fwhm_estimator`, `"stack Gaussian"`) and gives `fwhm_on_scale_px`, the width on the one star-width scale; each compared stack's measurements do the same. The registration rows carry Siril's own width (`registration_fwhm_estimator`), which has no ratio to that scale. The comparison reports the sky level, the noise in empty sky (the target report's `stacking.empty_aperture_noise_normalized`), the flatness and the star width, with one sentence for each and a reason for any number it could not measure.
- `get_aperture_record(path)` reads the per-aperture record the odd–even difference job wrote beside a stack, or gives `None`.
- `record_noise_growth(target, maximum_steps=None, include=None)`, `record_night_contributions(target)` and `record_odd_even_noise(target, keep_halves=False)` stack parts of the library stack into the target's `_subsets` folder and store the noise of each result (see [subset stacks](../pipelines/stacking/README.md#subset-stacks)). `include` adds `"night_contributions"` and `"odd_even_difference"` to the growth job, under the same lock. They run as background jobs of type `stacking`, cost one stack per subset, and raise `NotFoundError` for a target with no stack. The app's one RPC, `processing:measure_noise`, takes a `kind` and includes the odd–even difference in the growth series by default.

One image, `quality.detections`:

- `measure_profile(path, position, radius_px=None, cut_angle_deg=0.0, cut_half_length_px=None, search_radius_px=None)` measures one star at a 1-based pixel position `(x, y)` (as in FITS and DS9). It refines the center to the brightness-weighted centroid, takes the sky from a ring outside the radius, lists every pixel within the radius with its distance and its value above the sky, fits a round Moffat curve and a round Gaussian curve (width in pixels and arcseconds, Moffat beta, peak; each width also names its `estimator` and gives `fwhm_on_scale_px`, the width on the one star-width scale), says whether the peak looks clipped, and reads a straight cut through the center. The cut angle is measured from +y (increasing row) toward +x (increasing column); 0 runs along a column and 90 along a row. A color image is averaged over its channels and the result says so. Left out, the radius and the cut length follow the star width. With `search_radius_px`, the position first moves to the brightest peak of the lightly smoothed image within that distance (at most 50 px), and the result says whether it moved (`snapped`, `snap_distance_px`). The result also says whether the profile looks like a star (`star_found`, with `not_a_star_reason`): a peak under 5 times the sky noise, a width under about 1 px, or a width over about 8 times the star width is not one, and the data are still returned. The result carries a `cutout` of sky-subtracted pixels around the center, so a caller can rebuild a cut at any angle (the recipe is in the model's docstring); the radius and cut length are limited to 100 px. The result also holds the ring around the star (`ring_*` fields): the ring radii (`ring_inner_px`, `ring_outer_px`) sized from the measured pixels, the 5 degree direction bins of the pixels kept (`ring_bin_angle_deg`, `ring_bin_values`, `ring_bin_counts`), the Fourier terms of orders 1 to 8 (`ring_harmonics`: `amplitude` as a fraction of the ring's mean with `amplitude_error`, `amplitude_debiased`, `significance`, `significant` and `direction_deg`, from +y toward +x as for the cut), and the neighbor stars left out (`ring_neighbors`, `ring_masked_neighbor_count`, `ring_masked_fraction`). The neighbors come from the astrometry run's star finder on a small box around the star. `peak_over_sky_noise` is the brightest pixel over the sky noise, not the signal-to-noise ratio of the star's light (`blocks.measure_aperture` gives that). Every angle in the result, including `star_elongation_angle_deg`, runs from +y toward +x, as the cut does; `star_elongation_position_angle_deg` gives the long axis on the sky (north toward east) when the image is plate solved. Nothing is stored. The viewer's star panel calls it through `images:measure_star_profile`.
- `measure_detections(path)` is the astrometry finder of `blocks.measure_stars` run on one file at the run's own settings, saved for reuse. It lists the stars the astrometry star finder detects in one image, found now from the pixels, so it works on every image without running the analysis again. It calls the run's function (`find_unique_stars`) but keeps close star pairs, which the plate-solving list drops (AST-D23, Measured): the kernel sized from the star width in the image, the merge of a star reported twice into one detection at its brightest report, and the averaged copy of a color image. Each detection has `x` and `y` (1-based pixels, as in `measure_profile`), `flux` and `merged` (true when two reports were merged). The result also has `detection_count`, `merged_count`, `kernel_fwhm_px`, `binned_on_color`, `star_width_px` (on the one star-width scale) with its `star_width_estimator`, and `aperture_radius_px`. The star width is measured on the image itself, as a run measures it, and sizes `aperture_radius_px`: the radius of the circle photometry measures each star in (`APERTURE_RADIUS_PX`), so the viewer can draw that circle. When no star can be measured, the active setup's typical width stands in and `star_width_px` is null. Nothing is stored. The viewer's Detections overlay calls it through `images:measure_detections`.
- `measure_widths(image, positions=None)` gives one star width (full width at half maximum, in pixels) per color channel: the preview's channel-matching width (`star_width_match`). It names its estimator. These widths are for comparing the color channels of one image with each other, not one image with another; `measure_profile` gives widths on the one star-width scale. Without `positions` it uses the preview's own choice of bright, isolated, unsaturated stars.

Building blocks for scripts, `quality.blocks`. The Command Console preloads only `astrometrics` and `wayfinder`, so these methods give a script the library's own small measurements, each from its one home under `pipelines/` (the owners are in `pipelines/stacking/building_blocks.py`). An image argument is a FITS path, a frame record or a pixel array (2-D, or color channels first). Positions are 1-based pixels, as in `detections.measure_detections`. A raw color mosaic (a one-plane frame with a `BAYERPAT` card) is refused unless `debayer=True`; it is then measured as 2 by 2 color super-pixels (red, the mean of the two greens, blue), and positions and widths come back in the raw frame's pixels. Nothing is stored.

- `measure_sky(image, bias_adu=None, gain=None)` gives the empty sky's `level` and `noise` (one standard deviation), with large bright objects clipped out (`image_scaling.measure_sky_background`), or `None` when the sky cannot be measured. The numbers are raw ADU with the bias still in the level; with both `bias_adu` and `gain` they are electrons. The noise comes from differences of pixels four columns apart, so it reads low where neighbors share noise (a debayered, resampled or stacked image). A color image also gets one entry per channel.
- `measure_stars(image, finder="astrometry", fwhm_px=None, threshold_sigma=None, isolation_px=None)` runs the astrometry run's finder (`find_unique_stars`, the default: a sky map, merged double reports, a color image searched on an averaged copy) or `finder="daofind"`, the plain shared finder on one sky level with every roundness kept. It returns the `stars`, brightest first, with each star's `flux`: the finder's sum of the sky-subtracted pixels inside its template's footprint, not the star's total light.
- `measure_sky_gradient(image)` measures the sky's tilt across the frame as the preview does (`sky_plane`): the tilt as a share of the sky level, the limit, whether the preview would subtract the fitted plane, and the plane's terms.
- `measure_aperture(image, positions, radius_px=None, gain=None, read_noise_e=None, channel=None)` sums each circle and takes off the sky ring's clipped median (`frame_photometry.measure_aperture_photometry`), with each flux's 1σ uncertainty from the CCD noise equation. The gain and read noise come from the arguments, else the camera profile for the frame's setting or the header (`detector_noise`), else unit gain is assumed, and `noise_source` says which.
- `measure_sky_corners(path)` gives a plate-solved image's four corners as `(ra, dec)` in degrees (`header_wcs`) with the header's `RADESYS` and `EQUINOX`, or `None` for an image with no plate solution (`header_is_plate_solved`).
- `measure_robust_sigma(values)` and `measure_clipped_values(values, clip_sigma=3.0, maximum_passes=5, minimum_count=3)` are the library's robust spread (1.4826 times the median absolute deviation) and its clipping loop (`robust_statistics`).

The stars the astrometry run named on a stack are read with `processing`'s astrometry child. The tuned values of both libraries are worked out by `astrometricslib.parameters.tune(astrometrics, wayfinder)`. The AI tools offer the image measurements as `quality_blocks_*` and `quality_detections_*` tools; `measure_robust_sigma` and `measure_clipped_values` are for scripts only (see `mcp_servers/inventory/tool_dispositions.py`).

### `visualization.py`

`Visualization` draws images and charts. An image is a path, a frame record or an array of pixels. Each method is a thin wrapper of one owner.

- `render(image, stretch=True, brightness=None, crop=None, max_dimensions=None)` draws a frame, a stack or an array as a `RenderedImage`: the bytes of a PNG, or of the JPEG the enhancement stage saved beside a stack (used for a stretched view of the whole stack while it is current), with the brightness range shown (`black`, `white`), the sizes and the crop. A notebook shows it as a picture; a client that needs text, such as the app's viewer, builds the data URL itself. `stretch=True` is the app's automatic stretch, `stretch=False` a straight line from the darkest to the brightest pixel, and `brightness=(black, white)` a fixed range. `crop=(x_px, y_px, size_px)` zooms on one place, its center counted from 1. Owner: `pipelines/shared/image_conversions.render_image`.
- `render_newest()` draws the newest FITS file anywhere in the frames folder (target and calibration frames alike), or gives `None`. Owner: `image_conversions.render_newest_capture`.
- `plot_image(image, overlays=None, crop=None, stretch=True, brightness=None)` draws one image as a Matplotlib figure at full resolution, with axes counting pixels from 1. In the Command Console the figure opens in a figure window; in a notebook it shows in the page. `overlays` (`"detections"`, `"stars"` or both) marks the stars the astrometry run's star finder detects (from the stack's `_detections.json` file when it is still valid) and names the stack's stars from its `_identification.json` file. Like Image Processing's Astrometry overlay, it names only stars with photometry in the library. The title says why an overlay drew nothing. Owner: `visualization/image_display.plot_image`.
- `plot_target(target, star=None)`, `plot_star(star)`, `plot_astrometry(target)`, `plot_photometry(target, star=None)`, `plot_spectroscopy(target, star=None)`, `plot_focus(target)` and `plot_asteroids(target)` draw the charts of a target's or a star's results; `star` picks the star shown first. Owners: `visualization/helpers.py` and `visualization/focus_plots.py`, which read a target's stars from storage with the star query owner.
- `get_star_overlay(target, image=None, limit=None)` places a target's catalog stars in 1-based pixels on its stack, or on a named image, and returns a `StarOverlay` (the stars, and the reason when the image has no plate solution). Its owner is `pipelines/shared/star_overlay.py`. The backend serves it as `astronomy:get_overlay_stars`.
- `get_sky_picture(target)` says where a target's stack picture lies on the sky (a `SkyPicturePlacement`: the picture and a 17 x 17 grid of sky positions), or gives `None`. The owner, `visualization/sky_placement.get_sky_picture`, keeps each answer until the stretched stack or the picture changes. The backend serves it as `planetarium:get_stack_pictures`.

The MCP tools offer each method; `visualization_render` draws 1200 pixels on its longest side unless asked, and `visualization_get_sky_picture` is not offered.

### `jobs.py`

`Jobs` is a read-only view of the job history (running and finished jobs, their log lines, stored results), of the warnings a job detected and of the pipeline runs that produced a target's data. It opens the logs database read-only, so it cannot change it. Each method is a thin wrapper of one owner in `pipelines/shared/job_history.py`, and each answers in full: every match, whole messages and whole log lines.

- `get(job_id, required=False)` reads one job as a `JobSummary`, with its stored input and output numbers and its log file.
- `query(target_id=, job_type=, status=, active=False, until=, include=None, limit=None, offset=0)` lists jobs, newest first, as a `Page`. `until` pages back through the history by creation time; `include=["metrics"]` adds each job's stored numbers. The filter is `target_id`, the field the job holds, because a job that works on no single target records a name such as `calibration`.
- `get_log(job, lines=50)` reads the last log lines of a job as a `JobLog` (the lines and the total).
- `get_warnings(job)` answers "what warnings did this job detect?" as `JobWarnings`. A warning is a stored quality row of the job whose check failed (`check_outcome` is `failed`); it is listed with its pipeline, metric, subject, reason sentence, value, limit and validation register entry. A check that passed is not a warning. A check that could not run (`not_checked`) detected nothing, so it is only counted in `checks_not_run_count`. The answer also gives `measurement_count`, the number of rows the job stored, so an empty list with a nonzero count (the job was checked and nothing failed) differs from a zero count (the job stored no rows). Warnings that are not gates, such as frames moved to the excluded folder or a camera with no profile, are stored as notice rows (`<pipeline>.notice_*`) so that they appear here too. A row with no job id belongs to no job and is listed for none. `parameter_defaults` lists each parameter that used its default because no tuned or equipment value was set.
- `get_lineage(target)` lists the pipeline runs that produced a target's data.

The backend serves the app's one RPC method `jobs:query` from these methods (`backend/services/processing/job_history_service.py`), keeping its `detail` choice, short default answers and caps. The MCP tools `jobs_get`, `jobs_query` (20 jobs unless asked, at most 50, without the stored numbers), `jobs_get_log` (at most 200 lines), `jobs_get_warnings` and `jobs_get_lineage` follow the methods.

## Injecting drivers

`Astrometrics(config)` takes only the settings. It has no database or driver arguments, so a program always runs the built-in drivers over the database its settings name. Only a test swaps the database or a driver, and it does so through private code (`astrometricslib._internal.testing.astrometrics_with_drivers`). Nothing outside the library's tests and scripts may import that module.

A driver is the code that talks to one outside program or service. A test can swap any of them, for example to run with no network. The library uses five:

- a plate solver, which works out which part of the sky an image shows (built-in: Astrometry.net);
- a stacking program (built-in: Siril);
- the SIMBAD database of named astronomical objects (built-in: through astroquery, a Python package for querying astronomy services);
- Gaia DR3's low-resolution XP spectra, which the European Space Agency's Gaia satellite measured for its third data release (built-in: through astroquery, cached on disk);
- a source of interstellar reddening values (built-in: Gaia DR3 through astroquery).

Reddening is the color excess E(B-V) that dust adds to a star's light. B and V are two standard brightness bands, blue (about 4400 Å) and visual (about 5500 Å). E(B-V) is how much bigger the star's B − V magnitude difference is than it would be without dust. The spectroscopy pipeline uses it to correct a spectrum before it classifies the star, that is, before it decides the star's spectral type.

A test builds the root with the helper:

```python
from astrometricslib._internal.testing import astrometrics_with_drivers

astrometrics_with_drivers(config, catalog_access, *, plate_solve_driver=None, stacking_driver=None,
                          simbad_driver=None, gaia_xp_driver=None, reddening_driver=None)
```

A driver left out stays the built-in one. The helper puts the five into one `Drivers` object (`drivers/driver_set.py`) and gives it to `StellarCatalog` and `ProcessingPipelines`, which pass it to the pipelines as a `drivers=` keyword. The method signatures on the sub-APIs do not change.

A replacement subclasses `PlateSolveDriver`, `StackingDriver`, `SimbadDriver`, `GaiaXpDriver` or `ReddeningDriver` (from `astrometricslib._internal.drivers`; `StackSettings` and `StackRunResult`, which a stacking driver needs, are there too). A test can run a stage with a fake solver and no network:

```python
astrometrics = astrometrics_with_drivers(
    config, catalog_access, plate_solve_driver=MySolver(), simbad_driver=MySimbad()
)
astrometrics.processing.astrometry.run(astrometrics.targets.get("M 13"))
```

### Where the drivers reach

- `processing.stacking.run` uses the stacking driver.
- The analysis pipelines (`processing.astrometry.run`, `photometry.run`, `spectroscopy.run`, `spectroscopy.record_variation`):
  - give the plate solver and SIMBAD driver to the astrometry, photometry and spectroscopy stages, and the Gaia XP and reddening drivers to the spectroscopy stage;
  - photometry gives them to every `StarIdentifier` it builds: the one for each session's reference frame and the one that solves a session's frame to match stars across sessions. The photometry workers (the frame-measuring pool) never build one, so they need no driver.
- `processing.astrometry.solve` and `processing.astrometry.identify` use the plate solver and SIMBAD driver.
- The many-target batch (`pipelines/target_batch.py`) runs each target in its own worker process, which builds the built-in drivers.

`test/test_driver_construction.py` fails when a pipeline module calls a built-in driver class directly, because such a pipeline would ignore the driver the caller chose. It also fails when a pipeline builds a class that falls back to an empty `Drivers()` (such as `StarIdentifier`) without a `drivers` argument, because that fallback builds the built-in drivers. `api/test/test_driver_injection.py` shows that photometry uses the fake plate solver and SIMBAD driver and touches no built-in one.

### Which frames a one-target run uses

`processing.photometry.run` measures only the frames of one camera and one optic (one telescope or lens, identified by its focal length): those of the stack it analyzes. With no stack it chooses them the way the batch run does:

- the camera: the first camera in the config's setups that has frames of the target, the primary camera first;
- the optic: the config's primary focal length (`[Observatory.Telescope] focal_length_mm`).

`stack=` (another configuration's stack) or `frames=` choose differently. Spectroscopy runs when that selection has spectral frames or the target has a spectral stack.

For exact behavior, read the code.
