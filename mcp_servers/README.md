# MCP servers

This folder holds the Python MCP (Model Context Protocol) servers. An MCP server lets an AI agent call a program's functions directly instead of only reading its source. The servers here use only the public names of `astrometricslib` and `wayfindinglib`; the libraries and the backend know nothing about MCP. The front end's server (`astrometrics-ui`) is written in TypeScript and lives in `ui/mcp/`.

The servers need version 2 of the MCP SDK, the `mcp` package. It is an optional extra in `pyproject.toml`, so the libraries and the backend install and run without it. `build/linux/setup_venv.sh` installs the project with the extra, and with the `dev` extra for the development tools (`pip install -e ".[mcp,dev]"`). Run the servers' tests with `build/linux/run_tests.sh mcp_servers`.

## What each folder is for

- `common/` — code every server shares.
  - `reflection.py` — reads the public methods of a facade such as `Astrometrics` at startup and turns each one into a tool, so tools are not listed by hand. Methods whose names start with `delete` are skipped on purpose (`WITHHELD_METHOD_PREFIXES`), so an AI client cannot delete catalog records; deleting is done in the app, which asks the person first.
  - `tool_registry.py` — holds a server's tools and sends an incoming tool call to the right method. Every Python server with a registry uses this one class. Two options cover the differences: `sandbox_paths` refuses path arguments outside the library folders (the library servers turn it on), and `remediation` adds a recovery hint to a failed call's error (the backend server uses it).
  - `profile.py` — the rules for which tools a client may use. A profile limits tools by class and disposition. See "Which tools the server offers" below. It is the only definition of the rules: `build/mcp/generate_client_configs.py` copies its constants into `ui/mcp/src/profileRules.ts` for the TypeScript server, and a test fails when that file is out of date.
  - `tool_errors.py` — turns an error raised by a tool into a reply the client can read.
  - `app_job_tools.py` — `APP_JOB_TOOLS`, the tools that start work the app must run as its own job, each with the backend RPC method its button calls. See "Tools that start a job in the app" below.
  - `server.py` — the loop that serves one client over standard input and output. Every Python server's `__main__.py` builds its tools and calls `run_server`. Before it runs a tool, the loop checks the call's arguments against the tool's JSON Schema (the description of the arguments a tool accepts) and refuses a call that does not match. It also turns a tool that raises an exception into an error result the client can read. Version 2 of the MCP SDK leaves both jobs to the server. The loop imports only the MCP package and `jsonschema`, which the MCP package itself needs, so the gap server can use it.
- `astrometrics_core/` — the `astrometricslib-core` server. Run it with `python -m mcp_servers.astrometrics_core`. `definition.py` builds its registry from `Astrometrics`, and `tool_manifest.json` is the reviewed list of its tools with a class, category and disposition for each.
- `wayfinding_core/` — the `wayfindinglib-core` server, built from `Wayfinder` in the same way. Run it with `python -m mcp_servers.wayfinding_core`. Its own README describes its tools.
- `backend/` — the `astrometrics-backend` server. Run it with `python -m mcp_servers.backend`. Its tools reach the running backend over HTTP, including the tools that start a job in the app. See its README.
- `gaps/` — the `astrometrics-gaps` server, where an AI reports what its tools cannot do. Run it with `python -m mcp_servers.gaps`. See its README.
- `inventory/` — the tool inventory and the table of decisions about each tool (`tool_dispositions.py`). It writes every server's `tool_manifest.json`. See its README.
- `devtools/contract_validator.py` — a tool that checks a pydantic model's serialization contract (its field names, aliases, and JSON shape). It catches a model that would not survive a round trip through the MCP protocol. The `astrometricslib-core` server offers it.

## Which tools the server offers

When the server starts, it removes every tool that the manifest does not allow for the profile. There is one profile, `investigator`, and no setting chooses another. Writing scripts and running the project's tests are part of an investigation, so the profile offers tools that look things up or calculate, tools that run the project's tests and builds (class `develop`), and `terminal_add_script` (class `author`), which lets an AI add a new script to the Command Console's My scripts list for the person to review and run. The AI cannot run the script, and the tool never replaces an existing one. `terminal_get_recent_runs` (class `observe`) is its read-only partner: it returns what the person's recent Command Console runs printed (`stdout`, `stderr`) and the figures they drew, as images. Its other writes are bringing frames from the telescope into the library (class `ingest`) and stacking a target's frames the way the app does (class `process`). It offers no tool that changes other data (`change-data`), commands a device (`actuate`, `safe-stop`), or runs any code the AI chooses (`unrestricted`). `electron_run_python` and `backend_call_rpc` stay withheld.

The rules fail closed:

1. A tool that is missing from the manifest, or has no decision, is not offered. A new public method stays hidden until someone adds a row for it to `inventory/tool_dispositions.py`. Until then `inventory/test/test_served_tools.py` fails: it checks that the offered tools are exactly the reflected public methods minus the ones the table says not to offer.
2. A missing or unreadable manifest withholds every tool.
3. A tool with an `interim_block` is hidden until its known problem is fixed.

Only tools marked `keep` are offered. A call to any other tool is refused, and the refusal quotes the decision's note, for example "Replaced by target_query".

Do not edit `tool_manifest.json` by hand. `python -m mcp_servers.inventory --write-runtime-manifests` writes it from the reviewed decisions. `inventory/test/test_served_tools.py` fails when a committed manifest differs from a fresh run. The AI clients' settings and the investigator agent (`.claude/agents/investigator.md`) list the allowed tools too: `build/mcp/generate_client_configs.py` writes them from the manifests. A pre-commit hook runs it whenever a manifest changes, and the commit fails until you stage the files it rewrote.

## How a tool call reaches a method

A client sends only JSON: names, ids, numbers, dictionaries and plain strings. `reflection.py` passes these arguments to the method unchanged. The library methods accept them directly:

1. A `target` argument takes a target id. The library (`resolve_target` in `pipelines/shared/api_arguments.py`) reads the stored targets again and looks the id up, so frames brought in by another program, such as a frame sync, show up at once. An unknown id raises `NotFoundError` with a message that names it.
2. A time argument (`time`, `since`, `until`) takes an ISO 8601 string, which the method converts.
3. A sky position takes a `{"ra_deg": ..., "dec_deg": ...}` dictionary, which the method converts.

`reflection.py` adds one argument itself. A method marked with `@background_job` is slow, so the server calls it with `register_job=True` in a background thread (`run_as_background_job` from `astrometricslib`). The method records its own job in the logs database, the job list the app shows. If the call finishes within the method's grace period, the reply is `{"jobId", "result"}`; otherwise it is the job id to poll. The job's `output_metrics["result"]` holds the result once the work ends. These jobs run in the MCP server's process, so the app lists them but cannot stop them. The backend reads the job list every two seconds, so such a job shows in the app while it runs.

`reflection.py` leaves out the tools in `APP_JOB_TOOLS`. The `astrometrics-backend` server serves them instead.

## Tools that start a job in the app

Eight tools start slow work that writes to the library or change a job or a choice in the app: `processing_stack`, `processing_analyze`, `processing_cancel`, `processing_enhance`, `processing_identify_stack`, `processing_remake_preview`, `observatory_remote_sync_frames` and `observatory_remote_sync_logs`. When the person starts the same work in the app, the backend runs it as a job. The job shows in the job list with its progress and log, the screens show it running, and the app's Cancel button reaches it where the app has one.

So that a job the AI starts is the same job, these tools are served by the `astrometrics-backend` server (`backend/app_jobs.py`), not by the library servers. Each one calls the backend RPC method that the app's button calls (`APP_JOB_TOOLS` in `common/app_job_tools.py`):

| Tool | RPC method | Job in the job list | Cancel in the app |
|---|---|---|---|
| `processing_stack` | `processing:stack` | `stacking` for the target | Cancel in Image Processing |
| `processing_analyze` | `analysis:analyze_image` | `analysis` for the target | Cancel of the analysis |
| `processing_cancel` | `processing:cancel` or `analysis:cancel` | The target's `stacking` or `analysis` job, found with `jobs:query` | Same as the Cancel button; a cancelled `preview` job puts the old pictures back |
| `processing_enhance` | `processing:list_bright_objects` and `processing:set_bright_object` | None (saves the target's Enhance choice) | None |
| `processing_identify_stack` | `analysis:identify_stack` | `analysis` for the target | Cancel of the analysis |
| `processing_remake_preview` | `processing:remake_preview` | `preview` for the target | None, as in the app |
| `observatory_remote_sync_frames` | `telescope:sync` | `remote_sync` for the target | None, as in the app |
| `observatory_remote_sync_logs` | `telescope:sync_logs` | `remote_sync` named `logs` | None, as in the app |

The tools need the running backend. When it is not running, a call fails with "Could not connect to the backend". Nothing runs in the MCP process instead, because that job would not be the app's job. `processing_stack` with no `frames` lets the backend choose the frames with the library's own frame choice, and checks the choice with a plan before the job starts. A frame sync names one target, or Bias, Dark or Flat; copying every folder, chosen files or a local folder is not offered. Both syncs take `dry_run`, which reports the plan and records no job. Since a frame or log sync started in the app is now recorded as a `remote_sync` job too, the person's own syncs show in the job list as well.

For exact behavior, read the code — the code is always the source of truth.

## Tools for judging a night

These tools answer the questions that come up during and after a night of imaging:

- `visualization_render_fits` returns a real image of a frame or stack, with a stretch. A crop (`crop_center_x`, `crop_center_y`, `crop_size`) zooms on one place so trailing can be judged by eye. `overlays` (`["detections", "stars"]`) marks the detected stars and names the stars that have photometry. The library's `kind="figure"` and its `pixels` and `figsize` arguments are not offered (`CLIENT_LIMITS` in `astrometrics_core/definition.py`). It replaces the older tools that returned the picture as base64 text, which the reply limit cut in half.
- `quality_measure_frames` measures frames. It picks them by filter, file range (a bare number such as `013` means frame 013) and time, and leaves out spectroscopy frames unless asked. The code that picks frames is `pipelines/shared/quality/frame_selection.py`. The answer also has `trends`: it looks at the newest `trend_frames` frames and flags a steady drift in star width, star count or sky level when it passes `trend_threshold_percent` (code in `pipelines/shared/quality/frame_trends.py`). For `input_quality`, the sky is trended as the stored sky rate per second, and as the raw background only when every frame in the window has the same exposure, so a longer exposure is not read as a brighter sky (code in `pipelines/shared/quality/frame_quality_report.py`).
- `review_frame_guiding` (wayfindinglib) cuts the stored guide-log samples to each frame's exposure window. It reports the guide error inside each window and lists the frames well above the group's median. With `include=["quality"]` each row also carries the frame's star count, star width, roundness, trail length, sky level and quality flags, so image quality and guide error sit in one table (about a second a frame, at most 60 frames).
- `review_get_live_session_status` (wayfindinglib) reads tonight's Ekos and KStars logs. With `include` it adds sections of the Ekos record, such as `autofocus_runs` (with each focus curve and whether the fit succeeded), `aborted_captures`, `guide_state_events`, `mount_state_events`, `align_events` and `mount_positions` (declination, altitude, azimuth, pier side), so the cause of a flag can be read. The log records when a capture aborted but not why; the reason has to be read from the guider and mount events around that time.
- `quality_measure_frames` with `kind="spectral"` measures a target's raw spectrum frames: the zero-order position, the streak's tilt and width, the sky, the peaks of the zero order and the spectrum, and every saturated patch with its distance along the spectrum from the zero order (a clipped zero order is normal; clipped spectrum pixels lose data). `predict_exposure_seconds` scales the peaks to another exposure and says whether the spectrum would clip there. The summary groups frames by exposure length and by pier side (median, smallest and largest tilt), which answers whether the tilt depends on the side of the pier. The code is `pipelines/spectroscopy/pre_processing/spectral_frame_check.py`. The default kind reports `spectral_light_frames_in_target` next to `light_frames_in_target`, which counts imaging frames only.
- `quality_query` reads the quality measurements that earlier runs stored (the newest for each frame, stack or run and metric by default). It filters by metric, level, target, observing night, camera, telescope and time. It writes nothing, and an empty library gives an empty list. `quality_metrics` lists the declared metrics (or one, with `name`; or one checkpoint's, with `checkpoint`). The default `detail="summary"` gives unit, checkpoint, levels and purpose, which keeps the reply under the size limit; `detail="full"` adds the meaning, which way is better and how each is estimated. Both are reflected from `Astrometrics.quality`, together with the live checks above, which were `diagnostics_*` before. `quality_set_aside_frames` lists the frames lying in a target's `_excluded` folders. For each frame it gives the kind and reason and says whether they came from a stored quality row, from the folder's `excluded_frames.json` file, or from nothing but the folder. It moves and writes nothing.
- `planning_get_visibility` with an `end_time` also lists `sun_events` under `night`: when the Sun reaches sunset, civil, nautical and astronomical twilight, interpolated between time steps.
- A frame sync (`observatory_remote_sync_frames`) writes log lines and a `N of M frames transferred` progress message into its `remote_sync` job while it runs, so `jobs_query` and the app's job list show it moving.
- `app_status` (backend) now reports the live app: `telescope` (RA/Dec, Alt/Az, tracking or parked, ambient temperature and humidity, camera temperature and state, focuser, filter, and the mount's pier side and tracking switches read from its INDI properties), `guiding` (running, RMS, the newest 20 samples), `indi_devices`, and `indi_properties` for one `device`. It asks the backend, which holds the hardware connection. `observatory_mount_status`, `observatory_imaging_status` and `observatory_safety_status` are blocked because the MCP process has no hardware connection: their device sections would return `0`, `[]` and `unknown`, or open the connection with a device command.
- `target_query` reads targets in short records: one row per target (frame counts, cameras, last night imaged, stack flags), or with `detail=full` one target with its frames grouped by night, filter, exposure and camera and its quality summaries condensed. It covers what `target_get` and `target_list` returned, whose answers overflowed the 40,000 character reply. `detail=cameras` lists the cameras used and `detail=camera_index` each target's frames per configured camera. `target_imaged_field_centers` lists the imaged sky positions.
- `star_query` has `spectral_class`, `search`, `has_photometry`, `has_catalog_magnitude`, `order`, `detail=class_counts`, `detail=target_counts`, `detail=overlay` (a target's stars placed in pixels on its stacked image) and `detail=analysis` (the old `full`). Single-frame photometry detections (ids ending in `:Star_<n>`) are hidden unless `include_unresolved` is true. An analysis record holds the star's own spectral type and how well it matched, the closest reference types, the absorption features and emission lines found, and the cycle and repeating-dip verdicts, about 2 KB per star, with no raw arrays. With `spectral_class` the best-matched stars come first. The code is `astrometricslib/pipelines/shared/star_analysis.py`. `star_get` returns one star's full record.
- `planning_query_sources` (library targets and stars near a point, or SIMBAD and online catalog stars, brightest first, capped, with the total) and `planning_lookup_coordinates` (a position) replace `planning_find_sources`, `planning_get_sources`, `planning_get_library_star_summaries`, `planning_get_online_catalog_sources` and `planning_resolve_target_coordinates`, which returned whole target records.
- `visualization_plot` draws one chart (`kind` is `dashboard`, `star`, `astrometry`, `photometry`, `spectroscopy`, `focus` or `asteroids`) and returns a PNG image with the panel titles, not the text `Figure(1600x900)`.
- Slow read tools run as background jobs: `quality_measure_frames`, `quality_measure_stack`, `calibration_assess`, `review_query`, `target_imaged_field_centers` and `planning_get_deep_catalog_status` (when it estimates the catalog size). A call that finishes within 20 seconds returns `{"jobId", "result"}`; a slower one returns a job id to follow with `jobs_query` (`detail=result` gives the answer). These jobs appear in the app's job history with the type `diagnostics`.
- `quality_record_frame_measurements` is withheld from every profile. It measures a target's light frames and writes the numbers into the quality database, and it stamps each measured frame on the target record (only the stamps are saved, so other changes to the target are not overwritten). Only one run measures a target at a time. It never changes a frame file. The AI reads the stored numbers with `quality_query`. The app serves the same call as the RPC `quality:record_frame_measurements`.
- `processing_measure_noise` is withheld from every profile. It stacks some of a target's frames into the target's `_subsets` folder (never over the library stack, its previews or its records) and writes the noise of each result into the quality database. `processing_measure_noise` takes `kind`: `growth` (the noise against the frame count), `night_contributions`, or `odd_even_difference` (it stacks two halves of a target's frames, about one library stack's time in all, subtracts them, writes the noise of the difference and deletes the halves; the growth kind runs it as well unless told not to). None starts by itself after a stack. It costs one stack for each subset, so it takes minutes. The AI reads the stored numbers with `quality_query`. The app serves `processing_measure_noise` as the RPC `processing:measure_noise`.
- `calibration_measure_sensor_noise` is withheld from every profile. It measures a camera setting's gain and read noise, and with `save` on it writes the camera profile in the configuration file. The app serves the same call as the RPC `calibration:measure_sensor_noise`.
- `processing_remake_preview` (served by `astrometrics-backend`) makes a target's preview picture again (GraXpert, Siril stretch, Cosmic Clarity, star toning) from the stack that is already there, so a changed post-processing setting shows up without a restack. `denoise`, `denoise_strength`, `star_toning` and the StarNet choices (`starnet`, `star_strength`, `star_stretch`) apply to that run only and are never written to the configuration. The old pictures are copied into a `_previous_preview` folder beside the stack first (one earlier set is kept) and are put back if the run fails. A run that ends within two seconds answers with its result, which lists the steps that ran and says whether the stack file was left unchanged; a longer one answers with the job to follow. Class `process`; it writes only the preview JPEG, the processed FITS and the target's processed-image pointer. A target stacked with several cameras or optics has one stack for each; `camera_id` and `focal_length_mm` (as in `processing_analyze`) remake that configuration's own pictures (such as `..._Nikon_DSLR_DSC_D5300_300mm_preview.jpg`) instead of the main stack's. An unknown or ambiguous configuration, or one given with `kind` spectral, is refused. The main stack and the target's processed-image pointer stay as they were. The code is `pipelines/stacking/post_processing/preview_remake.py`; the overrides are `PreviewSettings` in `preview_settings.py`.
- `processing_stack` (served by `astrometrics-backend`) stacks a target with the app's Stack button job. `kind` is `imaging` or `spectral` (they are never mixed), and `filter_name`, `first_file`, `last_file`, `since`, `until`, `camera_id` and `focal_length_mm` choose the frames (a target with two cameras or two optics needs one of them). `plan_only` lists the chosen frames without stacking. Its class is `process`: it runs the app's own stage, so bad frames are set aside (never deleted), one previous stack is kept, and the target is saved. `frames` stacks an exact list of frame paths instead. `force`, `denoise`, `denoise_strength` and `star_toning` apply to that run. Siril's own options (rejection, filters, weights, output file) are not offered. The reply is the job id; `processing_stack_summary` reads the new stack once the job ends.
- `processing_analyze` (served by `astrometrics-backend`) starts the Analyze Target button's analysis job. With no `stages` the backend analyzes both stacks (photometry and spectroscopy) or the one stack the target has; with `stages` each stage uses its stack. The backend refuses a stage that has no stack to work on. A target stacked with several cameras or optics has one stack for each; `camera_id` and `focal_length_mm` (as in `processing_stack`) analyze that configuration's stack and its frames instead of the main stack. An unknown or ambiguous configuration is refused with the target's list. Spectral stacks exist only for the main configuration, so another configuration gets astrometry and photometry. The target keeps one result per stage, so the run replaces the saved astrometry and photometry results of the main stack.
- `processing_cancel` (served by `astrometrics-backend`) cancels a target's running or waiting job as the Cancel button does: `processing:cancel` for stacking, `analysis:cancel` for analysis. It finds the job with `jobs:query` (`job_id`, or the target's active jobs, narrowed by `job_type`). With neither, it cancels the one kind that runs and refuses when two kinds run. A cancelled picture remake puts the old pictures back. The reply gives `cancelled`, `job_type`, `job_ids` and `reason`.
- `processing_enhance` (served by `astrometrics-backend`) reads or sets the Final Stack's Enhance choice. Without `choice` it returns the saved choice and the objects SIMBAD places in the stack's frame, or the reason none can be listed (such as: run Astrometry first). With `choice` set to `target`, `nothing` or an object name from that list, it saves it. The choice is used at the next stack or Post Process Target; no picture is made. An unknown name is refused with the list. The library tools `processing_list_preview_bright_objects` and `processing_set_preview_bright_object` stay withheld.
- `processing_identify_stack` (served by `astrometrics-backend`) names the stars of a target's stack with the Astrometry button's analysis job. `stack_path` defaults to the target's current imaging stack. `processing_get_stack_identification` reads the names.
- `processing_stack_summary` gives one short answer for a target's stack. `observatory_remote_frame_status` counts a target's frames on the telescope, on the drive and in the library. `jobs_query` marks a job idle for over an hour as `looks_stale`.
- `planning_get_visibility` (wayfindinglib) says where objects are at one moment: altitude, azimuth, rise, set and transit, and with `include=["meridian"]` the hour angle and flip status. With an `end_time` it builds a night table for up to 30 objects: horizon clearance (with blocked sky ranges such as trees), meridian crossings, and the Sun and Moon. Without `objects` it covers every library target, highest first.
- The other planning tools follow `Wayfinder.planning`: `planning_get_tonight_advice`, `planning_get_calibration_advice`, `planning_calculate_panels` and `planning_create_mosaic`, `planning_create_sequence`, `planning_create_package`, `planning_create_session`, the queue calls (`planning_add_to_queue`, `planning_reorder_queue`, `planning_remove_from_queue`, `planning_set_entry_exposures`, `planning_add_checklist_items`, `planning_set_framing`), the package calls (`planning_update_package`, `planning_reopen_package`, `planning_dismiss_package`, `planning_undismiss_package`), `planning_refresh_suggestions` (updates the suggested packages and the checklist from the quality rules), `planning_tick_checklist_item`, `planning_get_plan`, `planning_query_plans`, `planning_get_package_for_target` and `planning_get_deep_catalog_status`. The ones that write are not offered to the AI.
- `review_get_advisory` (in `Wayfinder.review`; `kind` is `quality` or `result`) judges data and results that exist. `planning_get_tonight_advice` and `planning_get_calibration_advice` recommend what to do next (they were `kind="tonight"` and `kind="calibration"` of the old call). For `review_get_advisory`, `kind="quality"` gives a target's dataset report: a summary for each capture setting, statements in priority order, a starting point when the target has no frames, and the check of earlier forecasts. `planning_get_tonight_advice` ranks targets by the noise cut one clock hour would give, with a separate list for each use. `kind="result"` says how far to trust one star's spectrum class or period. Every statement names its evidence, its limits and a confidence from the validation register, and none advises new hardware. The library returns whole statements. The tool registry shortens a long reply by trimming each statement's evidence, keeping the references furthest beyond the limit first, before its own character cut. A "take N more" count appears only after one of that target's forecast checks agreed.
- `review_query` has the kinds `night_quality` (a night review with a loss account for each target), `nights` (which nights have guiding, capture and sky data) and `target_changes` (the slews that moved the mount to a new library target). `planning_get_plan` reads one stored night plan with its checklist, framing and revision, `planning_query_plans` lists sessions, packages or the suggestion log, and `planning_get_package_for_target` reads a target's package. the queue and package calls, `planning_refresh_suggestions` and `planning_tick_checklist_item` write the plan and the package library, so the AI is not offered them.
- `quality_set_aside_frames` lists the frames in a target's `_excluded` folders with the reason and where the reason came from. It moves and writes nothing.
- In monitor mode (every capability delegated) every motion, capture and stop command is refused, including `guiding:stop` and `telescope:alignment_stop`. Changing a device setting stays allowed.
