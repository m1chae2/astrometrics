# Shared pipeline tools

This folder holds code that more than one pipeline (astrometry, photometry, spectroscopy, asteroid detection, stacking) depends on. Nothing here runs on its own. A pipeline's own `pipeline.py`, `runner.py` or `batch.py` calls it.

Terms are defined in the [glossary](../../../documentation/Glossary.md). This document also defines each term the first time it appears.

## Terms used here

- *Frame*: one camera exposure file. *Light* frames show the sky. *Dark*, *flat* and *bias* frames measure the camera itself (its heat signal, its pixel-to-pixel sensitivity and its fixed electronic offset) and are used to correct the lights. A *stack* is the image made by aligning and averaging many light frames.
- *Session*: the frames from one continuous run with the same setup. Each pipeline states its own grouping rule.
- *FITS*: the standard astronomy image file format. Its text header holds named cards (keywords) such as `DATE-OBS` and `INSTRUME`.
- *Plate solving*: working out where in the sky an image points by matching its stars to a reference star catalog. Its result is a *WCS* (World Coordinate System), the header formula that converts a pixel position to a sky position.
- *SIMBAD* is an online database of named astronomical objects. *Gaia DR3* is the European Space Agency's catalog of precise positions and brightnesses for over a billion stars.
- *Arcsecond* (arcsec): 1/3600 of a degree. *Magnitude*: the astronomer's brightness scale, where larger numbers are fainter.

This folder sits below the five pipelines, so nothing here imports a specific pipeline (`pipelines/<name>/`), `pipelines/tasks.py` or `pipelines/target_batch.py`. When shared code needs a pipeline's function or class, the caller passes it in. `astrometricslib/test/test_layer_boundaries.py` enforces this. Code with only one pipeline as its user lives in that pipeline.

## What each file is for

- `analysis_context.py` — the shared container a pipeline run passes between its own stages. It holds the loaded image, the detected sources, and the results found so far. A detected source is a point of light the detector found in the image, with a position and a brightness.
- `frame_grouping.py`, `frame_optics.py` — sort a target's frames by camera, optic, and role (light/dark/flat/bias), and work out which physical telescope or lens took a given frame.
- `frame_scanning.py` — finds image files on disk and reads them into frame records. It skips the output of processing: a file whose name contains `_stacked`, `starless`, `starmask` or `processed`, or whose header has a positive `STACKCNT` (Siril writes it only on a stack, and keeps `IMAGETYP = Light Frame` on it). The sorter files such a stack under `others`, not under the lights. Each record stores the file's size and modification time, and a re-index with `refresh_headers` does not open a file that still matches them.
- `quarantine_path.py` — the name of the `_excluded` folder where stacking moves frames with clouds or trailed stars, and the one test for "is this path inside it". Frame scanning skips that folder so moved frames do not rejoin the target.
- `previous_stack_path.py` — the name of the `_previous` folder where a restack keeps the stack it replaced. Frame scanning skips that folder so the old stack never counts as an input.
- `session_identification.py`, `target_sessions.py` — group a target's frames into observing sessions and work out which stars an image sequence contains.
  - **Star identifier.** `session_identification.py` takes the star identifier from its caller (the astrometry pipeline's `StarIdentifier`), typed as the `SessionStarIdentifier` protocol, which names the methods it calls.
  - **Saving a solve.** It also holds `write_wcs_to_fits_header`, which saves a solved WCS into a FITS header. It writes the SIP distortion terms (Simple Imaging Polynomial, a standard correction for lens distortion) with the sky map and deletes the sky-map keywords of any earlier solve first.
  - **Fit quality.** When a frame is plate-solved during session identification, the result records the solver's fit residual RMS (root mean square of the leftover distances between fitted and reference star positions) in arcsec and its matched-star count. Both are `None` when the sky map came from the file's own header or the solver returned no statistics.
- `camera_passes.py` — plans which cameras a batch run should process, and which targets go to each camera pass.
- `angles.py` — angle helpers. `wrapped_ra_difference_deg(ra1, ra2)` subtracts two Right Ascensions (RA, the east-west sky coordinate, like longitude; its partner, declination or Dec, is the north-south coordinate, like latitude) and wraps the result into (-180°, 180°], so 359.9° and 0.1° are 0.2° apart. It accepts floats or arrays. Code that compares or searches around RA values calls it instead of subtracting, because RA wraps from 360° back to 0°. The asteroid detector and the astrometry star identifier use it.
- `catalog_star_identity.py` — decides whether two different catalog names refer to the same star. Two catalog rows within `SAME_STAR_POSITION_TOLERANCE_ARCSEC` (2 arcsec) of each other count as one star (measured; see [AST-11](../../../documentation/library_design/validation/astrometry.md#ast-11)). It also holds `CATALOG_MATCH_RADIUS_ARCSEC` (10 arcsec), the largest distance between a detected star and a catalog entry for the two to count as one star (design estimate; see [astrometry design estimates](../../../documentation/library_design/validation/astrometry.md#design-estimates)). The astrometry star identifier and `star_recording.py` both use it.
- `star_recording.py` — the shared rule every pipeline uses to decide which stars are worth keeping, and how to save them to the star catalog.
- `applied_camera_profile.py` — records which camera profile (sensor characteristics, saturation threshold) a pipeline run actually used, on that run's quality summary.
- `target_center_hint.py` — turns a target's catalog RA and Dec into a starting position hint for plate solving.
- `target_camera_index.py` — summarizes each target's light frames per configured camera: how many frames each camera took and the time of the newest one. The user interface's target list uses it to filter by camera and to sort by the most recently imaged. A camera writes its name into FITS headers in its own spelling (for example `Nikon DSLR DSC D5300`), so the module matches names to the configured camera names through `camera_identity`, which reads each camera profile's alternate spellings. `TargetCatalog.query(detail="camera_index")` calls its `build_target_camera_index`. A frame from a camera that is not configured still counts toward a target's newest frame time, but not toward any camera.
- `target_overview.py` — builds the short target records that `TargetCatalog.query` returns. The list form has one row per target (name, position, frame counts, cameras, last night imaged, whether it has a stack). The single-target form groups the frames by night, filter, exposure and camera, and cuts the quality summaries down to flags and headline numbers. It only reads, so looking at a target never marks it as changed.
- `target_records.py` — reads and writes `Target` records in the catalog database. `PROCESSED_IMAGE_EXTENSIONS` lists the endings of a finished image (`.jpg`, `.jpeg`, `.png`, `.tiff`, `.tif`); `TargetCatalog.reindex_frames` makes such a file the target's processed image instead of a frame. A process keeps one object per target: a target handed out by `get` stays the object the catalog holds, so a job that edits it for minutes (a stack) still saves its edits. `list` reads the stored targets fresh and updates a held target in place only if it has no unsaved edits. A save writes only the targets that were touched and really changed since they were read or last saved, so a copy that was only looked at cannot overwrite another program's edit. `read_saved_target` reads one record straight from storage, to check what a save wrote.
- `star_catalog_queries.py`, `star_analysis.py` — answer `StellarCatalog.query`.
  - **Selecting.** They pick stars by id, name, target, region or position. They filter by magnitude, spectra, photometry, a real catalog magnitude, spectral class or a search text. They hide single-frame photometry (brightness measurement) detections, whose ids end in `:Star_<n>`. They sort by id, by usefulness (spectra, then named stars, then photometry, then brightest first) or by spectrum match, and they page the result. They also count stars per target and per spectral class (the letter O, B, A, F, G, K or M that sorts stars from hottest to coolest).
  - **Catalog magnitudes.** A real catalog magnitude is a finite number of at least -2 that is not exactly 0 (`has_catalog_magnitude` in `models/stellar_source.py`). Smaller values are instrumental magnitudes from photometry, which are magnitudes on the camera's own uncalibrated scale. A value of 0 means the catalog gave none.
  - **Spectrum summary.** Spectroscopy classifies a star by comparing its spectrum with reference spectra of known type (the reference types). The distance between two spectra is a relative RMS: the root-mean-square difference as a fraction of the spectrum's average brightness. A value of 0.15 means a typical sample is 15% off. The per-star spectrum summary reports:
    - `own_type_percent_off`: how close the best reference type is (the relative RMS times 100);
    - `rms_gap_to_second_best`: the gap to the second-best reference, in relative RMS units (a difference of two RMS values, not a probability), and `is_ambiguous` when that gap is below `AMBIGUOUS_RMS_GAP`;
    - `rms_gap_to_next_class` and `is_class_ambiguous`: the same test against the best reference of another spectral class;
    - `no_good_match` and `differs_from_catalog`.

    The flags use three limits from `models/stellar_source.py`: `NO_GOOD_MATCH_RMS` for `no_good_match` (partly measured; see [SPE-16](../../../documentation/library_design/validation/spectroscopy.md#spe-16)), `AMBIGUOUS_RMS_GAP` for both ambiguity flags (measured; see [SPE-18](../../../documentation/library_design/validation/spectroscopy.md#spe-18)), and `DIFFERS_FROM_CATALOG_SUBTYPES` for `differs_from_catalog` (partly measured; see [SPE-19](../../../documentation/library_design/validation/spectroscopy.md#spe-19)). The summary has no confidence or probability field.
- `star_overlay.py` — places a target's stars in pixels on its stacked image, for labels drawn over it. It projects each star's sky position through the image's WCS and keeps the stars that land on the image. When the image has no WCS, it uses the pixel center saved when each star was detected. Star clusters and `Star_<n>` field detections get no label.
- `stack_preview_path.py` — the file names of the stretched JPEG and stretched FITS saved next to each stack, and the JPEG quality. Stacking writes these files (`stacking/post_processing/stack_preview.py`) and the image viewer looks for them. Both take the names from here so they cannot disagree.
- `simbad_object_types.py` — reads the object types (for example `V*` for a variable star) out of one row of a SIMBAD answer. The astrometry star identifier and the `scripts/backfill_simbad_object_types.py` script both use it, so both read an answer the same way.
- `star_kinds.py` — tells from a star id how the star can be looked up (Gaia DR3 id, a position-only `FIELD_J` id, and so on) and reads its stored position. The SIMBAD and variable-star backfill scripts share it.
- `variable_star_catalogs.py` — looks up stars in the AAVSO (American Association of Variable Star Observers) Variable Star Index (VSX) and in Gaia DR3 through CDS XMatch, a service that matches a whole table of positions in one request. A match must lie within `MATCH_RADIUS_ARCSEC` (3 arcsec; partly measured; see [AST-12](../../../documentation/library_design/validation/astrometry.md#ast-12)). This is tighter than the 10 arcsec `CATALOG_MATCH_RADIUS_ARCSEC` above because a wider radius lets a bright star match a faint neighbor. A Gaia match is ignored when its G magnitude (the brightness Gaia measures in its own broad color band) differs from the star's by more than `MAXIMUM_MAGNITUDE_DIFFERENCE` (2.0; partly measured; see [AST-12](../../../documentation/library_design/validation/astrometry.md#ast-12)). G differs from the usual visual magnitude by one magnitude or a little more for very red stars, so a larger difference means a different object. `scripts/backfill_variable_star_flags.py` uses it.
- `api_arguments.py` — checks the arguments of the public methods and holds the types and helpers they share (`TimeInput`, `StackKind`, `STACK_KINDS`, `make_frame_selection`). `resolve_target` turns a target id into its `Target` after reading the stored targets again, so a target another program changed is seen.
- `image_conversions.py`, `image_scaling.py` — convert images between formats and adjust brightness/contrast for on-screen display. For a big frame, the display stretch measures the sky from a sample of the pixels (`measure_sky(..., sample_pixels=True)`), which gives the same image in a fraction of the time. Every random sample in this file uses a fixed seed, so two renders of one image are identical.
- `provenance_recording.py`, `staleness.py` — the single call every pipeline makes to record its IVOA provenance, and the matching check for whether an already-saved result still reflects the pipeline's current version. IVOA provenance is a record, in the International Virtual Observatory Alliance's standard form, of which run, at what version, produced a result (see `astrometricslib/models/provenance.py`).
- `quality/` — shared quality-measurement helpers (background level, saturation, detection confidence, per-frame statistics) that more than one pipeline's own quality checks build on. `quality/quality_metrics.py` and `quality/frame_statistics.py` measure star width (FWHM, full width at half maximum) only when the caller passes a measuring function in; the public API passes the astrometry pipeline's `measure_fwhm_from_data`. `quality/raw_frame_check.py` checks raw light frames that are not in the library yet: it measures stars, trails and the move since the previous frame, and flags frames that differ from their batch (see `QualityDiagnostics.frame_quality(kind="raw_check")`). Each frame is flagged for any of these:
  - A star count below 0.5 times (`LOW_STAR_FRACTION`; partly measured; see [STK-01](../../../documentation/library_design/validation/stacking.md#stk-01) and [STK-34](../../../documentation/library_design/validation/stacking.md#stk-34)) or above 1.4 times (`HIGH_STAR_MULTIPLE`; design estimate; see [stacking design estimates](../../../documentation/library_design/validation/stacking.md#design-estimates)) the batch median. A count far below the median usually means cloud or a drift. A count far above it usually means extra bright regions that are not stars, such as a trail or a light leak.
  - A bright streak much longer than the batch's longest streak.
  - A faint straight trail, such as a satellite or aircraft, at least a quarter of the frame diagonal long (`TRAIL_MIN_DIAGONAL_FRACTION`, also an argument of `check_raw_frames`; (design estimate; see [stacking design estimates](../../../documentation/library_design/validation/stacking.md#design-estimates))). The detector averages the frame in blocks of `TRAIL_BLOCK_PIXELS` (4 by 4 pixels). It keeps blocks above `TRAIL_THRESHOLD_SIGMA` (3 noise units, where one noise unit is one standard deviation, σ, of the noise; (design estimate; see [stacking design estimates](../../../documentation/library_design/validation/stacking.md#design-estimates))) that are not inside stars. A region counts as a star when its smoothed peak passes `TRAIL_STAR_SIGMA` (60 noise units; (design estimate; see [stacking design estimates](../../../documentation/library_design/validation/stacking.md#design-estimates))). It then runs a line search (a Hough transform, which lets every bright block vote for the lines through it). The result lists the trail length in pixels (`line_trail_px`) and its angle in degrees (`line_trail_angle_deg`). The block size follows from the trail width: a trail about 4 pixels wide fills about one block, so averaging raises its signal-to-noise ratio about 4 times and shrinks the frame 16-fold, which also makes the line search fast. The star cut-off sits above the faint trail on purpose, so the mask does not hide the trail from the line search. The frames measured for the star counts and the trail are described in the register (partly measured; see [STK-34](../../../documentation/library_design/validation/stacking.md#stk-34)).
  - Stars much wider or less round than the batch's, a failed match to the previous frame's stars, or a large move since the previous frame.

  The check counts a pixel as saturated when it reaches the saturation level of the frame's camera profile (chosen from the `INSTRUME` header card). A 14-bit camera such as the Nikon D5300 clips near 16,383 ADU (analog-to-digital units, the camera's raw counts), so a fixed 65,000 would never trigger. The result records the level (`saturation_threshold_adu`) and where it came from (`saturation_threshold_source`). The check uses 65,000 only when no camera profile can be read. The level logic is `resolve_saturation_threshold` in `quality/saturation.py`. It takes the saturation level from the camera profile, and falls back to the profile's clip ceiling when the profile's threshold sits above it. The spectrum check (`spectroscopy/pre_processing/spectral_frame_check.py`) uses the same function.

  The other `quality/` modules:
  - `background_measurement.py` — reads a frame from disk and measures its sky background level and the fraction of saturated pixels. The decision whether the background changed too much during a stacking run lives in `stacking/pre_processing/background_homogeneity.py`.
  - `detection_confidence.py` — `significance_to_confidence` turns a signal-to-noise ratio (the signal divided by the noise's standard deviation) into a confidence score from 0 to 1 that levels off as the signal grows. The curve is a chosen shape, not a calibrated detection probability. A higher value means a stronger detection.
  - `frame_quality_report.py` — builds the reports that `QualityDiagnostics.frame_quality` returns for `kind="raw_check"` and `kind="input_quality"`. Each report also looks for slow drifts across the newest frames. Nothing is saved.
  - `frame_selection.py` — picks the frames a quality check measures, by filter, file-name range and time, for library frames and for a plain folder.
  - `frame_trends.py` — finds a slow, steady change in one number (sky level, star width) across recent frames, as from dew or drifting focus. It fits the median of all pairwise slopes (the Theil-Sen slope), so one bad frame cannot fake or hide a trend. It flags a trend when the fitted change, as a percentage of the starting level (`change_percent`), reaches the caller's threshold and at least 70% of the frame-to-frame steps go the same way (`STEADY_STEP_FRACTION`), with at least 4 frames (`MINIMUM_FRAMES`). Both limits are design estimates (see [stacking design estimates](../../../documentation/library_design/validation/stacking.md#design-estimates)).

For exact behavior, read the code.
