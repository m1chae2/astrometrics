# Simulated observatory

This folder holds a telescope that is "on" without a telescope. The app uses it for its **Simulated** observatory source (Settings, Observatory). The technical performance measure (TPM) harness in `build/tpm/` uses the same pieces, and also plays back a past night (`--observatory replay`). Every piece runs on this computer.

| Module | What it does |
| --- | --- |
| `observatory.py` | `SimulatedObservatory` makes the folders and settings, checks them, and starts and stops the stand-ins. It is also a program: `python -m simulator.observatory start` or `stop`. `prepare_offline_world` builds a world with no telescope at all. |
| `library_copy.py` | A temporary, copy-on-write view of your real library for the app: database copies (SQLite online backup) and a `fuse-overlayfs` overlay of the frames and stacks. |
| `supervisor.py` | Runs one stand-in and ends it, with its children, when the process that started it ends. |
| `mock_phd2.py` | The stand-in PHD2. It plays PHD2's event stream from a guide log. The TPM runs and the replay always use it, so their baselines repeat. The interactive simulation mode uses it only when the real PHD2 cannot run. |
| `phd2_launch.py` | Prepares and starts the real PHD2 for the interactive simulation mode: finds the program, picks an instance number with free ports, writes the profile, builds the environment (`HOME` in the stand-in home) and the command. See "The guider". |
| `guiding_operator.py` | The operator step for guiding: brings the PHD2 the launcher started to guiding, once. |
| `exposure_driver.py` | Connects the INDI simulators, sets their properties (the geometry from `device_settings.py` and the fitted values from `fit_results.json`), delivers real frames when it knows the backend's port, follows the mount to the nearest library target, and files frames into the stand-in telescope computer's picture folder. It takes the exposures itself in the TPM harness (`--capture driver`, never while the mount slews) and only files the frames the app takes in the launcher's session (`--capture app`). |
| `fit/` | Reads what the recorded nights say about the equipment (through the libraries' public API) and turns it into INDI simulator properties and PHD2 controller settings. See "Fitted settings". |
| `frame_source.py` | Delivers a real frame in place of a drawn one. See "Real frames". |
| `replay_driver.py`, `night_replay.py` | Harness only: play back a past night from the real library and logs (read only). Copied frames carry `ORIGIN = 'ASTROMETRICS-SIMULATOR'`. |
| `guide_log_replay.py`, `guide_log_sample.txt` | Turn a guide log into PHD2 events and paced log lines. |
| `observatory_guard.py` | Refuses settings that point beyond this computer or at a real library folder. |
| `simulated_calibration.py` | `record_simulated_calibrations` records a guider calibration (the simulator's own values) and a focus model for the simulator, so the library's rules let capture, focus and guiding through. |
| `launch.py` | The launcher: `python -m simulator.launch`. Builds the world, runs the backend as its child, plays the operator step, guards the connections and tears the world down. See "The launcher". |
| `source_choice.py` | Re-exports the saved observatory source choice and the shared launch names from the launcher contract (`backend.public_interface`, the one backend module the layer imports), and adds the names only the layer uses. |
| `real_folders.py` | `real_folders` finds the user's real settings file and library folders (through the `ASTROMETRICS_REAL_*` variables), and `RealFolders.protected_paths` lists the folders the guards refuse to use. It reads the library folders through `library_folders`, which follows the app's own path rules. |
| `errors.py` | `GuardError` and `SimulationUnavailableError`, the layer's two errors (both `ConfigurationError`). |
| `connection_guard.py` | Lists the TCP and UDP sockets of a process and its children that go beyond this computer. The launcher and the TPM seal guard use it. It needs `ss`. |
| `path_guard.py` | Finds and moves the stored absolute paths in a copy of the library that point outside the copy. The library copy, `build/agent_tools/copy_path_guard.py` and the TPM real snapshot share it. |
| `rpc_client.py` | Calls the backend's `/api/rpc` and `/api/ready` on 127.0.0.1. The launcher and the TPM scripts use it. |
| `settings.py` | The settings text that points the app at the stand-ins, or at nothing (offline), and the list of endpoint keys a world changes (`endpoint_keys`). |
| `device_settings.py` | Turns the world's settings into INDI simulator properties: the cameras' sensor size and pixel size, the focal length and aperture, and the main camera's gain and pedestal (the offset setting is kept for the header). The exposure driver sets them after it connects the simulators. |
| `standin_ssh.sh` | An `ssh` stand-in that runs the command in the stand-in home folder. With `ASTROMETRICS_STANDIN_SSH_MODE=refuse` it refuses every connection. |

## The launcher

`python -m simulator.launch` starts the backend for you in the world the saved Observatory source names. `build/linux/run_backend.sh` always runs it (see `build/linux/README.md`). The backend builds no world: it reports the launch (`[Launch]` in the settings) and, when you change the source, saves the choice and exits with code 75. The backend owns the choice file code (`backend/launch_contract.py`, public through `backend/public_interface.py`); `source_choice.py` re-exports it. Started without the launcher (the TPM harness, Electron's own start in the packaged app), the backend runs on the real telescope or the world its environment names and cannot change its source.

A session goes like this:

1. **Choice.** The launcher reads `observatory_source.json` from your real settings folder (`source_choice.py`).
2. **Real choice.** It runs the backend as a child with your environment, plus `ASTROMETRICS_LAUNCHER=1`. It builds no world. If no other launcher holds the simulator folder, it first removes what a crashed session left there.
3. **Simulated choice.** It takes an exclusive, non-blocking `flock` on `<simulator folder>/launcher.lock` and holds it until the world is gone. If another process holds it, the launcher touches nothing, says so, and exits with code 73. Then it builds the world (`SimulatedObservatory.prepare`: the database copies and the overlay), fits the simulators to your recorded nights on the copy in a short process (`python -m simulator.fit`, see "Fitted settings"), starts the stand-ins (the exposure driver gets the backend's port and the results file and `--capture app`; first the stand-in picture and camera staging folders are emptied, so the session starts like a new night) and waits until they are up, works out the calibration records in a short process (`python -m simulator.simulated_calibration`) while nothing else uses the copy (it records the fitted guide rate, see "Fitted settings"), and runs the backend with the world's `ASTROMETRICS_CONFIG`, `XDG_*` folders and `PATH` (the ssh stand-in). The backend also gets `ASTROMETRICS_OBSERVATORY_SOURCE=simulated`, `ASTROMETRICS_SIMULATOR_ROOT` and the `ASTROMETRICS_REAL_*` folders, so it still finds your real choice file. It also gets `ASTROMETRICS_LAUNCH_MISSING_PROGRAMS`, so the settings control can say what the simulator lacks. It also gets `ASTROMETRICS_LAUNCH_NOTES` (statuses such as a missing star catalog, which never stop a source change). The backend never starts or stops anything of the world.
4. **Failure.** If the world cannot be built or started, the launcher builds the offline world (no telescope, a refusing `ssh`) in the same folder and runs the backend on it. The reason reaches the backend in `ASTROMETRICS_OBSERVATORY_SOURCE_ERROR`, so `observatory:get_source` reports `SIMULATOR FAILED` and the reason.
5. **Operator step.** When `/api/ready` answers, the launcher calls the backend's RPC methods in this order: `target:create` for the pointed target if the library lacks it, `observatory:record_guider_calibration`, `observatory:record_focus_model` and `observatory:enter_controller_mode` with `shadow_first=true`. Each log line starts with `OPERATOR STEP`, and the log lists the capabilities that are on and the ones that stay off with their reasons. A failed call is logged and the step goes on. The step runs only for a simulated world. It goes away when the app can command PHD2 and the camera itself. With the real PHD2 the step ends with a second part, the guiding step (see "The guider"), which runs after the app has taken command.
6. **Connection guard.** Every 5 seconds the launcher lists the TCP and UDP sockets of the backend and its children (`ss -tunp`). A socket whose peer is beyond this computer stops the backend, tears the world down and ends the launcher with code 70. A `--lan` backend with a phone connected would trigger it. The guard fails closed: if the check itself fails (for example `ss` is missing or exits with an error) three times in a row, the session ends the same way. One failure is only logged. The guard sees a connection after it exists, so it ends the session but does not stop the first packet. What prevents traffic is the offline switch (`[Launch] offline = true`, which every outgoing client in the libraries honors) and the settings checks in `observatory_guard.py`. As a backstop the launcher also sets `ASTROMETRICS_OFFLINE=1` in the backend's environment.
7. **Ending.** When the backend exits, the launcher stops the stand-ins, removes the library copy, releases the lock and exits. Exit code 75 means "the Observatory source changed": the launcher reads the choice again and starts the next session, after the old world is gone. Any other code ends the launcher with that code. SIGTERM or SIGINT stops the backend first (SIGKILL after 30 s), then tears down, and exits with 0.

Two limits. `observatory:get_source` shows `commands: null`, `running: false` and `library_copy: {}`, because the backend does not know about the stand-ins; the log has the operator step's result. Each world's INDI server has its own socket (see "What a world holds"), so it can run next to another INDI server on the same computer.

## The guider

Who plays PHD2 depends on the job:

| Job | Guider | Why |
| --- | --- | --- |
| Interactive simulation mode (`python -m simulator.launch`) | The real PHD2 (`phd2` on the PATH, else `~/.local/bin/phd2`) | The app's guiding status and guide graph come from real PHD2 and its genuine guide log. |
| TPM runs, replay | The stand-in (`mock_phd2.py`) | The baselines replay one recorded guide log, so they repeat. `python -m simulator.observatory start` uses the stand-in unless you pass `--guider phd2`. |

`ASTROMETRICS_SIMULATOR_GUIDER=mock` makes the launcher use the stand-in even when PHD2 is installed. If PHD2 is not installed, has no display (`xvfb-run`, else `DISPLAY`), has no free instance, or does not open its port in 90 seconds, the stand-in plays and the world keeps a note such as `PHD2 (guiding program): the stand-in guider plays PHD2 (phd2 is not installed)`. The launcher passes it in `ASTROMETRICS_LAUNCH_NOTES`. It is a status, not an error.

How the real PHD2 is started (`phd2_launch.py`):

- **Instance and ports.** PHD2 instance `i` listens for events and commands on port `4399 + i` and uses `4299 + i` too. The launcher takes the first instance from 2 up whose two ports are free. Instance 1 (port 4400) is never used, because that is the usual port of a real PHD2. The world's `Observatory.Guiding.phd2_port` is the event port.
- **`HOME`.** PHD2 runs with `HOME` set to the stand-in telescope computer's home (`<world>/standin/home`), and the `XDG_*` folders under it. It never reads or writes your `~/.PHDGuidingV2`, `~/.phd2` or `~/PHD2`. `write_profile` refuses a home outside the world. PHD2's guide log lands in `<stand-in home>/PHD2`, one of the folders the app's log download searches.
- **Display.** `WAYLAND_DISPLAY` and `DBUS_SESSION_BUS_ADDRESS` are unset, `GDK_BACKEND` is `x11`, and `GSETTINGS_BACKEND` is `memory`. The app has full control of the simulated telescope, so PHD2's window must not open on your desktop: PHD2 runs under `xvfb-run -a`, which gives it a hidden virtual display, even when you have a `DISPLAY`. Only when `xvfb-run` is not installed does PHD2 use your `DISPLAY`, and the world keeps the note `PHD2 (guiding program): xvfb-run is not installed, so its window opens on your display`.
- **Profile.** Before PHD2 starts, the launcher writes its settings file (`.PHDGuidingV2-instanceN`). The profile uses PHD2's INDI camera and INDI mount, pointed at the world's INDI server (`127.0.0.1` and its port), the devices `Guide Simulator` and `Telescope Simulator`, the active guide scope's focal length and the secondary camera's pixel size. Its name, `Astrometrics simulator N`, is how the guiding step recognizes this PHD2.
- **Calibration step.** PHD2's default calibration step (750 ms) cannot reach its 25 pixel calibration distance in the 60 steps PHD2 allows when the guide rate is low: at the fitted 3.2 arcsec/s and 6.39 arcsec per pixel, 61 steps moved the star only 19.3 pixels, and the log said "RA Calibration Failed: star did not move enough". The profile therefore sets `CalibrationDuration` (key `/profile/1/scope/CalibrationDuration`) from `calibration_step_milliseconds`, the formula of PHD2's own calibration step calculator (`CalstepDialog::GetCalibrationStepSize`, `src/calstep_dialog.cpp`): distance times pixel scale divided by the guide rate gives the time to cross the distance; divide by 12 steps (PHD2's default aim, far under the limit of 60) and by the cosine of the declination (the world points at 36.46 degrees), keep at least 6 steps, and round up to 50 ms. The guide rate is the fitted `GUIDE_RATE_WE` times 15 arcsec/s, or 7.5 without a fit. At 3.172 arcsec/s that is 5250 ms.
- **Guide controller settings.** `SimulatedObservatory` and `Launcher` take an optional `controller_settings` mapping: `aggressiveness`, `minimum_move`, `hysteresis` and `exposure_seconds`. They go into the profile (right ascension uses PHD2's Hysteresis algorithm, declination its Resist Switch algorithm; hysteresis applies to right ascension only). A key left out keeps PHD2's default, and `None` means all defaults. The launcher takes them from the fit (the controller settings in the newest PHD2 run's log header), unless the caller gave some. PHD2 recomputes its minimum move itself when a calibration ends (`guide_algorithm.cpp`, the "smart default"), so the value in the profile does not stay: the real log of the live test states 0.277 pixel where the profile said 0.4. Aggressiveness and hysteresis stay as written.
- **No replay.** With the real PHD2 the exposure driver gets no `--guide-log`, so it starts no log writer and creates no guide log in the Ekos folder. PHD2 writes a genuine one, and a replay would count the guiding twice.

The guiding step (`guiding_operator.run_guiding_step`) runs once, after the operator step has put the app in controller mode. It opens a command session on the PHD2 port (the library's one PHD2 client, `wayfindinglib.drivers.PHD2Client`), checks the profile name is the one written, checks PHD2 is `Stopped`, waits until the simulated mount tracks and has stopped slewing, then connects the equipment, loops, finds a star and guides. PHD2 calibrates first because it has no calibration yet. A PHD2 with another profile, or one that is already looping or guiding, is left alone. This is also why it never guides again after the app slews the mount: it runs once, and the app owns guiding after that. The star the guide camera draws is at least 3.5 pixels wide: a sky-sized star is under one pixel at 6.4 arcsec per pixel, and PHD2 filters such a star out as a hot pixel (a live run with real GSC stars: a 2.4 pixel star was "Star lost - low HFD" during calibration, a 3.5 pixel star gave a half-flux diameter of 2.2 pixels and a signal-to-noise ratio of 62). The steps run inside the launcher process, so they run with the world's offline identity (`guiding_operator.offline_identity` sets `ASTROMETRICS_OFFLINE=1` and the world's settings file for the length of the step and restores them), and the PHD2 client's local-host check never reads your real settings. A missing star (the `gsc` catalog draws the field's stars), a mount that does not track or a calibration that fails gives a `WARNING` line that starts with `OPERATOR STEP`, never an error.

The live test `test_phd2_live.py` starts a world's INDI server and the real PHD2 in a temporary folder (on its own virtual display), runs the guiding step, reads real guide steps with the public client and parses PHD2's guide log with the app's parser. It is skipped when PHD2, the INDI programs or a display are missing, or when `ASTROMETRICS_FAST_TEST=1`.

## Fitted settings

The INDI simulators start with made-up numbers. The fit step fits them to your recorded nights. At each simulator start, after the library copy is built and before the stand-ins start, the launcher runs `python -m simulator.fit` in a short process. The process reads the copy through the libraries' public API (never your real folders: `check_library_is_simulators` refuses a library that is not inside the world), converts each measurement and writes one file, `<world>/fit_results.json`. The exposure driver reads the same file after it connects the simulators, so each property equals the value in the file. A new night changes the copy, so it changes the library fingerprint in the file and the values at the next start.

**Where each value comes from.** For each row the best source wins, in this order: the newest real record, a fit to the recorded history, the performance envelope, then the simulator's default. A row without data falls back one step: where the table says "zero" the property is written as zero, where it says "default" nothing is written. A reply the library marks `truncated` is not used: the guiding-run list is asked for again with fewer runs (50, then 20, then 5), and if every reply is cut the row falls back. When the pointing is below the horizon at the start, the sky rate is predicted on the meridian at the same declination, and the note says so. A call that fails is a note in the file, never an error.

| Row | INDI property | Public call | Conversion | Without data |
| --- | --- | --- | --- | --- |
| Guide rate | mount `GUIDE_RATE_WE`, `GUIDE_RATE_NS` (0 to 1) | `control.guiding.query_calibrations`, else the newest run in `review.query(kind="guiding_runs")` | Dec speed in arcsec/s divided by 15 (one unit is 15 arcsec/s in the INDI telescope simulator, not 15.04); the Dec speed is used on both axes, because a log's right ascension speed includes cos(dec) | default (0.5) |
| Periodic error | main `SIM_PEPERIOD` (0 to 60 s), `SIM_PEMAX` (0 to 6000 arcsec); guide `SIM_PE_PERIOD` (0 to 1000 s), `SIM_PE_MAX` (0 to 100 arcsec) | `review.measure_unguided_mount_error` (pooled period and amplitude are medians over the runs) | zero to peak amplitude divided by cos(dec); a period above the main simulator's 60 s is clamped and the amplitude scaled by the same fraction, to keep the peak speed | zero |
| Random and drift | guide `SIM_RA_RAND`, `SIM_DEC_RAND` (arcsec, uniform from minus to plus), `SIM_RA_DRIFT`, `SIM_DEC_DRIFT` (arcsec/s), all within -2 to 2 | the same measurement, using medians over the runs, so a few wild runs do not set the disturbance | drift: the median signed drift per minute divided by 60; random: the median change between two frames divided by sqrt(2) (the size of a jitter that is new every frame, which is what the driver adds) times sqrt(3); right ascension divided by cos(dec) | default |
| Polar error | both cameras `SIM_POLAR` (arcmin), `SIM_POLARDRIFT` | `control.mount.get_polar_alignment` | total error divided by 60; the drift element is the constant 1 | zero |
| Go-to offset | mount `MOUNT_MODEL` `MM_IH` (right ascension) and `MM_ID` (declination), in arcminutes; `MM_CH`, `MM_NP`, `MM_MA`, `MM_ME` are always 0 | `review.query_alignment_records(session_id="all")`: the first solve of each target session | median signed offset (solved minus commanded) in arcsec; right ascension divided by cos(dec) of the solve; divided by 60; times the sign in `MOUNT_MODEL_SIGNS` (`fit/fitting.py`) | zero (fewer than 5 first attempts) |
| Dec backlash | mount `DEC_BACKLASH` (0 to 5000 ms) | `review.measure_guiding_spectrum` | as estimated | zero |
| Guide controller | the PHD2 profile | `review.query(kind="guiding_runs")` | aggressiveness, hysteresis, minimum move, exposure of the newest PHD2 run | PHD2's defaults |
| Seeing | main `SIM_FOCUSING.SIM_SEEING` (arcsec FWHM); guide `SIM_SEEING` | `review.get_performance_envelope` (median star width) | main: as is; guide: its profile `exp(-1.4 d^2 / s^2)` has a width of 1.41 s, and never narrower than a star 3.5 guide pixels wide (`GUIDE_MINIMUM_STAR_FWHM_PIXELS`), which the geometry step also sets when there is no fit | default |
| Sky glow | main `SIM_SKYGLOW` (magnitudes) | `review.get_sky_rate_prediction` | solved from the driver's flux formula, see below | default |
| Noise, bias, maximum | main `SIM_NOISE`, `SIM_MAXVAL`, `CCD_OFFSET`; guide `SIM_NOISE`, `SIM_MAXVAL`, `SIM_BIAS` | the camera profile in the settings | see below | default |
| Focus drift | none | `review.measure_focus_temperature_coefficient` | recorded only | not settable |
| Download time | none | none | recorded only | not applied |

**Sky glow, noise and seeing are solved, not tuned.** `simulator/fit/driver_model.py` inverts the drivers' formulas, which it quotes with their source lines: the sky is `flux(1.3 * glow) * (1 + sqrt(gain)) * vignetting`, so the glow for a wanted sky rate in ADU per second per pixel (the median over the frame) is found in one step, for the main simulator and, with its own constants, for the guide simulator. The noise is a whole number from 0 to N-1, so N is chosen with an RMS of sqrt((N^2 - 1) / 12) closest to the camera's read noise, and the bias is the real bias level minus the mean of the noise, (N - 1) / 2, so frames sit at the real bias level. The camera simulator draws a star with the width you set only after the focuser reports a position (it keeps 3.5 arcsec until then), so the exposure driver sets the best-focus position to the focuser's position and moves the focuser one step.

**Go-to offset.** The mount normally lands exactly where it is told, so the app's alignment (plate solve, sync, slew again) would have nothing to fix. The telescope simulator has a `MOUNT_MODEL` property that makes it point a little away from the position it reports; the camera simulators draw the true position. The fit simulates one constant offset. It reads every recorded plate solve on all nights, keeps the first solve of each target session (a gap of more than two hours starts a new session), which is the error before any correction, and takes the median signed offset on each axis. The record's right ascension offset is a distance on the sky, so it is divided by cos(dec) first. The file notes the count, the median absolute deviation and the typical error size. If the median is much smaller than the typical error, the errors scatter in direction: the systematic part is small, and the scatter is not simulated. With fewer than 5 first attempts every term is zero, and the file says why.

The terms are in arcminutes, not degrees. This was measured on the running INDI 2.2.5 simulator on 2026-11-08: `MM_IH` = 1 moved the true pointing by exactly one arcminute of hour angle (0.001111 h), and all zeros gave no offset. Values of 60 were accepted without clamping, and the fit clamps at 120. The sign of `MM_IH` was measured the same day: with `MM_IH` = +1 the true right ascension was lower than the reported one (13.515409 h against 13.516520 h at M 51) and declination was unchanged, so `MM_IH` is minus the median right ascension offset. The sign of `MM_ID` is not measured: it is plus the median declination offset by analogy, and the live check decides (each sign is a named constant). The app's own pointing model is not used. Its hour angle is computed from right ascension alone, not from sidereal time, so the polar and flexure terms are fitted against a made-up angle, and its index and cone terms can cancel each other. The cameras' `SIM_POLAR` comes only from the polar alignment record, so no polar error is counted twice.

**What the INDI simulators do not do.** Their periodic-error phase cannot be set: the main camera simulator counts from its start and the guide camera simulator from its first frame (and again after 30 s idle), so the two never share a phase. The polar error is a fixed offset in declination, with no drift in time. Nothing couples focus to temperature. The drivers add no photon noise. The random terms measured from guide logs include the guide star's measurement noise, so they are upper bounds. The library has no sky measurement for the guide camera, so its glow stays at the default. A star width measured on the main camera (with its blur from guiding and focus) stands in for the guide camera's.

**The results file.** For every value it holds the row, the INDI device, property and element, the unit, the value written, the value before clamping and the clamp note, the source kind, the public call and its parameters, the nights used, the date and a sentence about the measurement, plus the conversion, the library fingerprint (size and modification time of each copied database), the camera facts used and the notes about calls that gave nothing. A value with `applied` false is a record only. Open it to see why the simulator behaves as it does.

**Checks.** `test_fit.py` tests each conversion, the fallback order, the clamping, the results file, the truncated-reply refusal and the reading of the file with synthetic measurements. `test_fit_live.py` starts a world, reads every applied property back with `indi_getprop` and compares it with the file, then measures a few short simulated frames with the library's unstored folder measurement (`quality.measure_folder`, with the simulator's bias level as the pedestal) and checks that the sky rate and the star width land within a stated tolerance of the targets. It is skipped when the INDI programs are missing or `ASTROMETRICS_FAST_TEST=1`.

## What a world holds

Each world is one folder (`~/.local/share/astrometrics-simulator` for the app). Besides the library copy it holds these things for the INDI side:

- **Its own INDI socket.** `indiserver` is started with `-u <world>/indiserver.sock` (`indi_socket_name`). INDI's local socket is an abstract socket, not a file, and a name can be about 100 bytes at most, so a long folder name gets a short name made from a hash of the folder. Two worlds, or a world and the INDI server of a real night on the same computer, no longer share `@/tmp/indiserver`. The app and the helper tools (`indi_setprop`, `indi_getprop`) use TCP (`host:port`), so they are not affected.
- **Its own home folder.** `indiserver` and the drivers it starts run with `HOME=<world>/indi_home` (`indi_home`). The simulators load and save their configuration in `<world>/indi_home/.indi`, never in your `~/.indi`. The simulators start from their defaults each time the world is built, and the exposure driver sets what matters.
- **Your telescope settings.** The world's settings file keeps your real `Observatory.Telescope`, `Observatory.RemoteTransfer` and `Observatory.Guiding` sections, with every key (focal length, focal ratio, ...). It changes only the endpoint keys (`settings.endpoint_keys`): the telescope host (`127.0.0.1`), `indi_port`, `remote_pictures_path` (the stand-in's picture folder) and `allow_commands = true`; the PHD2 location (`local`) and `phd2_port`; and `auto_download = true`. These are the locked keys of the launch identity (`auto_download` is not locked). If your settings lack a section, the made-up telescope (405 mm, f/5.4) fills it.
- **Your sensors and optics in the simulators.** The frames match the real telescope in geometry (sensor size, pixel size, focal length, aperture), gain and offset labels, filter names and the set temperature. They do not match it in sky brightness, noise, star width or star brightness: those come from INDI's defaults. The INDI sky is about 0.003 ADU/s/pixel, the real one about 6.8. INDI's noise is uniform over 0 to 9 ADU with no shot noise, the real camera's is 4.88 ADU of read noise plus Poisson noise. INDI's seeing is 3.5 arcsec, the real 3.7 to 4.5 arcsec. Stars are several magnitudes too faint. So noise, signal-to-noise and depth checks are not valid on INDI-drawn frames until the fitted settings are in (see "Fitted settings"; they bring the sky, the noise and the star width close to your recorded nights, but the drivers still draw no photon noise). After the exposure driver connects the simulators, it sets (and reads back) the main camera simulator's `SIM_XRES`, `SIM_YRES`, `SIM_XSIZE` and `SIM_YSIZE` from the primary camera's profile, the guide camera simulator's from the secondary camera's profile, and both simulators' `SCOPE_INFO` (focal length and aperture) from `Observatory.Telescope` and the active guide scope. The main camera's `CCD_GAIN` comes from the first bias level (else the first noise measurement) in the primary camera's profile. INDI's `CCD_OFFSET` is not a camera offset: the CCD simulator uses it as the pixel value of an empty frame. So the value sent is the camera profile's bias level in ADU for that gain and offset (about 395 ADU for gain 0, offset 10), and the log warns and sends the offset itself when no bias level is recorded. The header `OFFSET` keeps the camera setting. A property that does not take is named in the driver's log; the simulator keeps running with its own value. The INDI 2.2.5 telescope simulator has no focal-length property, so the camera simulators' own `SCOPE_INFO` is the one that counts.
- **The real camera's name.** The CCD simulator writes `INSTRUME = CCD Simulator` into its frames. The world's copy of the primary camera's profile lists that name in `name_aliases`, so the frames file under your camera (the same `record_name`, so the same bias and noise records). Your own settings file is not changed. The simulator writes a `GAIN` header but no `OFFSET` header, so the exposure driver has the camera save each frame into `<stand-in>/camera_staging/...`, adds `OFFSET` (the camera offset setting, not the pedestal sent to INDI) and `SYNTHETC = T` (a general flag that the frame was drawn by a camera simulator) to the header, and renames the file into the picture folder in one step (`stamp_offset`). Only the header changes, never the pixels, and a keyword already in the header is left as it is. Real frames the simulator delivers "as if taken now" (the night replay) are copied unchanged and carry no `SYNTHETC`. The library's frame measurement adds a warning to a frame with `SYNTHETC` true: its noise, sky and depth values do not describe a real sky. The filter wheel simulator's slot names (`FILTER_NAME`) are set from `[Observatory.Filters]` (`available`, else `owned`), and the camera simulator is linked to that wheel (`ACTIVE_FILTER`), so frames' `FILTER` header reads your names. The wheel has 8 slots that cannot change: a longer list is cut at 8, and later slots keep the simulator's names after a shorter one. The CCD simulator's cooler target (`CCD_TEMPERATURE`; the driver has no cooler switch) is the `temperature_c` recorded with the primary camera's first bias level (else its noise measurement), and the operator waits until the sensor is within 1 degree before the first exposure (the simulator cools about half a degree per second, so -10 C takes about 20 s). The exposure time is still the operator's.
- **The star catalog.** The CCD and guide simulators draw stars by running the `gsc` program, which reads the catalog data named by `GSCDAT`. When `gsc` is installed, the world sets `GSCDAT` for the INDI server (the data folder of the package, or a `GSCDAT` you set). Install it with `sudo apt install gsc` (the `gsc-data` package comes with it; about 240 MB to download, 300 MB on disk). Without it the world still starts and the simulated frames have no stars. The launcher passes the note `gsc (star catalog): stars are not drawn` in `ASTROMETRICS_LAUNCH_NOTES`, and the settings page shows it under the Observatory source while the simulator runs. It is a status, not an error, and it does not stop a change of source. The PHD2 contract recorder (`build/tpm/record_phd2_contract.py`, which drives PHD2 with the library's own client and writes the profile with `phd2_launch`) keeps its own made-up star lattice (`FAKE_GSC`) so its recording does not depend on the catalog.

## The library copy

- The databases are copied at switch time and at every launch of the app in a simulator source, one thread per database, so the copy takes about as long as the biggest database. Each table is scanned once to fix its paths (the copy time is in `observatory:get_source`, `library_copy`). The report's `bytes` are the final sizes of the copies, measured after the paths are rewritten and the write-ahead log is merged into the file. Paths inside the copies that name your real frames or stacks folder point at the overlay. `calibration_frames.json`, which also holds absolute paths, is rewritten the same way. After that, `path_guard.py` moves any stored path that is still outside the world (for example an old stacks folder that is on no list) to `<simulator folder>/outside/<original path>`, and then checks the copies again. If a path still leads outside, the build stops and the launcher uses the offline world. At the end, teardown removes the whole `library` folder of the world once both overlays are unmounted; it removes nothing while one is still mounted.
- The overlay's lower layer is your real folder (read only). Every write lands in `<root>/overlay/upper`. A stacks folder inside the library shares the library's overlay; a separate one gets its own.
- Leaving the mode, or stopping the app, unmounts the overlay and deletes the upper layer and the copies, only inside the simulator folder. A start in Real mode removes what a crash left (the launcher does it, while it holds the lock).

## Real frames

When the mount points at a target you have already imaged, the exposure driver can deliver one of your real frames in place of the frame the camera simulator drew (`frame_source.py`). The app then downloads, measures and stacks it like any other new frame, so the processing runs on real data. The launcher gives the driver the backend's port (`--backend-port`; the launcher knows it before the backend starts). Without it (for example `python -m simulator.observatory start`, which has no backend), every frame is the simulator's. The sky starts at M 13, and with the port the driver follows the mount: before each exposure it reads the mount's position and, when the mount has moved more than 0.05 degree, files the frames under the library target nearest to it within 1 degree (the app's own rule, `TelescopeService._infer_target_at_coordinates`), so the app finds them in the folder it downloads and real frames of that target are delivered. It gets the targets from the backend (`target:get_targets`, kept for 5 minutes, and asked again after 30 seconds when nothing was found), never from the database file. With no target nearby, the frame is filed under the position (for example `RA 16h41m Dec +36d28m`) and stays the simulator's. A lookup that fails is a status: one line on the error output, and the current target stays. Without the port the target never changes.

**Who takes the exposures.** With `--capture driver` (the default, and what the TPM harness, `python -m simulator.observatory start` and the replay use) the driver sets `CCD_EXPOSURE` itself, one frame after another, and waits first until the mount's `EQUATORIAL_EOD_COORD` state is not `Busy`, so no frame is taken during a slew. With `--capture app` (the launcher) the driver sets no exposure. The app's Start Capture runs the library's own capture path, which only sets `CCD_EXPOSURE` on the same camera and changes no upload setting, so the frames land in the staging folder the driver set. The driver sets the camera's upload mode to both, so a client that asks for images, such as a centering frame, also receives them. The driver watches that folder, checks the mount position every 2 seconds (so the file name prefix is right before the next exposure), and files each finished frame as in driver mode: the same real frame or stamped simulator frame, and the same statistics. The ready file and the wait for the cooler work in both modes.

- **What matches.** A real light frame of the target with the same camera, filter, gain, offset and binning as the simulated capture. The camera is the library's own name for it (its folder), and a filter matches by the library filter it stands for, so `L` from the wheel matches `Luminance` in a real header. Frames a camera simulator drew in an earlier run of the world (`SYNTHETC`, or `INSTRUME` of a simulator) are never used. Frames of the requested exposure are used first. SPEC frames are delivered like any other. A target with no matching frame gets the simulator's frame.
- **Order.** The frames come in the order they were taken, one per exposure. A cursor per target and setting starts again at the first frame after the last.
- **One copy only.** The source finds the frames through the running backend (`target:get_files`, `images:get_fits_header`) and never opens the library files or databases. It copies the chosen frame to `<stand-in>/frame_source_cache` (`night_replay.copy_frame`, a real copy that refuses your real folders), then calls `images:delete` for the library frame. In the overlay this hides the file and leaves your real file as it was. The backend removes the frame's record and its stored measurements (`quality.forget`). The cached copy is what a later round delivers after the cursor wraps.
- **Header.** `DATE-OBS`, `DATE-END` and `MJD-OBS` are the simulated time, as if the frame were taken now. The real values are kept in `ODATEOBS`, `ODATEEND` and `OMJDOBS`. `AIRMASS`, `OBJCTALT`, `OBJCTAZ` and `OBJCTHA` move to `OAIRMASS`, `OOBJALT`, `OOBJAZ` and `OOBJHA`, so the app works them out again. `FOCPOS`, `FOCTEMP`, `CCD-TEMP` and `PIERSIDE` stay. `ORIGIN` keeps the real frame's own value (or stays absent if the real frame had none): the copy stamps `ASTROMETRICS-SIMULATOR`, and the source puts the real value back, because the simulator leaves `ORIGIN` alone. `SIMDELIV = T` says the simulator delivered the frame. The frame is real, so it has no `SYNTHETC`.
- **Where it goes.** The delivered file is written to the picture folder under the name the simulator's frame would have had, in one step, so a transfer never sees half a file.
- **If something fails.** A backend that does not answer, or that does not delete the frame, is a status: the simulator's frame is kept and the log has one line. Time-dependent results from these frames stay in the throwaway library, which is deleted when you leave the mode.

## Design rules

- **A layer around the app.** `simulator/` sits around the backend and the libraries. The core (`astrometricslib`, `wayfindinglib`, `backend`, `mcp_servers`) never imports it, and an import-linter contract checks that. The simulator uses only the libraries' public names and `backend.public_interface`. A change to the core for the simulator must also help a second real observatory or a real night. A measurement that also describes a real night is made in the core and reached through its public API. The simulator only turns it into settings.
- **The backend owns the launcher contract.** The source choice, its file and the restart exit code live in `backend/launch_contract.py` and are declared in `backend/public_interface.py`. That is the one backend module the simulator may import.
- **Nothing leaves the computer.** In simulation mode the app sends no submissions (such as an asteroid report to the Minor Planet Center), makes no online catalog or name lookups (SIMBAD, online Gaia) and does no online plate solving. It talks only to the stand-ins on this computer, and lookups use the local catalogs copied into the world. The connection guard checks this.
- **Drawn frames are marked.** A frame a camera simulator draws carries the `SYNTHETC` header keyword, and the quality measurements of such a frame carry a warning that its noise, sky and depth values do not describe a real sky. A real frame delivered "as if taken now" does not carry it (see "Real frames").
- **The RPC host check is the only access rule.** The backend checks the host of each RPC call. It asks for no session token, so in LAN mode any device on the network can send RPC calls (a session-token requirement was closed as not planned, issue #158).
- **One time zone.** The observing night follows the computer's time zone. The app assumes the computer and the telescope share a time zone (issue #159, closed).
- **Open test-bed work** (the simulator as an integration test bed) is tracked in issue #160.

## Safety

- Commands are allowed for the simulated telescope (`allow_commands = "true"` in `SIMULATED_TELESCOPE_SETTINGS`), because the devices are stand-ins on this computer. When the simulator is up, the launcher's operator step puts the app in controller mode through the RPC (`control.safety.enter_controller_mode(shadow_first=True)`: the correction capabilities are first moved to SHADOWED, the step the rules need). The library's rules still apply. Before the hook takes control it calls `record_simulated_calibrations`, which saves a guider calibration and a focus model into the simulator's own wayfinding library (a copy of yours, made at each start), so every capability can become AUTHORITATIVE. The guider calibration holds the simulator's own values, not your real camera's: the plate scale of the active guide train, a camera angle of 0 (the guide simulator's `SIM_ROTATION`, which nothing changes) and the mount simulator's guide rate (7.5 arcsec/s, half of 15, unless the fit set another `GUIDE_RATE`; the calibration then holds the fitted rate). The focus model is your newest real focus model in the library copy, copied under the active equipment names, or else the focuser simulator's behavior (no backlash). Its thermal coefficient of 0 is a placeholder until the fitted settings, so autofocus sees no temperature drift to follow. The records are redone at every start, so a new real focus model is picked up. Each record's `source_note` starts with `Simulator:` and names its source. The function refuses to run unless the wayfinding library is inside the simulator folder and is not one of your real folders, and it only reads the library it is given. The log lists what stays off; the backend does not report it (`commands` is `null`). The operator step never runs for the real telescope or the offline world, which keep monitor mode. The offline settings keep `allow_commands = "false"`.

- Every settings file the layer writes carries a read-only `[Launch]` section (the launch identity, see `astrometricslib/foundation/launch_identity.py`). A simulated observatory says `label = "SIMULATOR"`, `live_hardware = false`, `disposable_library = true`, `offline = true`, and locks the endpoint keys (`Observatory.Telescope` host, INDI port, picture folder and `allow_commands`; `Observatory.Guiding` PHD2 port and location; the image, frames, stacks and wayfinding folders). The offline world says `SIMULATOR FAILED`, with no hardware and `offline = true`. The backend only reports it (`launch` in `observatory:get_source`). The libraries honor `offline = true` in every outgoing client, and the settings service refuses a save that changes a locked key (`SIMULATED_LOCKED_KEYS`, `launch_section_text`, `with_launch_section` in `settings.py`).
- The INDI server and the stand-in PHD2 use free ports on this computer, never 5000, 4400 or 7624.
- `SimulatedObservatory.prepare` refuses a settings file with a host other than `127.0.0.1` or `localhost`, another port, a picture folder outside the stand-in home, any other IP address in the file, or an image library, frames, stacks or wayfinding folder that is outside the simulator folder or is one of your real folders.
- The app checks every settings save against the same rules while a simulator runs (`check_settings_update`).
- If the simulator cannot start, the app runs offline: no telescope, no PHD2, no downloads. It never falls back to the real telescope.
- Every process starts through `supervisor.py`, so none outlives the app, even after a crash. The harness starts them with the same program.

For how the app switches source, read `backend/observatory_source.py` and `backend/services/observatory/observatory_source_service.py` (the backend's side: report, save, exit 75) and `launch.py` (the launcher). For the harness, read `build/tpm/README.md`.
