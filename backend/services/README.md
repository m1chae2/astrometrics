# Backend services

This folder holds the backend's services. A service is a Python class that keeps some state or does some work for the app. The RPC route (`/api/rpc`) calls a service method for each request. A service never imports the container (`backend/container.py`) or the routers. The container builds the services and passes each one what it needs. `Container.shutdown_resources()` stops them when the backend stops: the maintenance thread, the observatory control, and every Siril process (through the library's `processing.stop_stacking_programs()`; the backend's exit runs no `atexit` handlers).

Terms are defined in the [glossary](../../documentation/Glossary.md). This file also explains each term when it first appears.

## Folders

- `analysis/` runs the analysis jobs.
- `data/` serves targets, stars, images and the deletion archive. `image_service.py` also answers `images:map_position` (`from_path`, `x`, `y`, `to_path`, with 1-based pixels): where a pixel of one image is on another, so the viewer's Star profile panel can follow a measured star when the image changes. The work is in `position_mapping.py`. It tries three ways in order and returns `{x, y, method, note}`. First, "sky": both images have a plate solution, as the library's `astrometricslib.drivers.header_is_plate_solved` decides (both sky axes, and `PLTSOLVD` true or SIP terms; capture-program pointing cards alone do not count, and a `PLTSOLVD` of `F` is false). Second, "stack alignment": a stack's `<stack name>_registration_frames.json` holds the 3 x 3 transform Siril saved for each frame (frame onto the stack's reference grid, with Siril's y axis `height - 1 - row` and pixels counted from 0) and the `crop_offset` trimmed from the stack afterwards. It links a frame to its stack, a stack to a frame and two frames of one stack. When the two images belong to different stacks it is chained through the stacks and the sky ("stack alignment + sky"). Third, "same pixel", a guess that the note says is a guess. When no way applies, `x` and `y` are `null` and `method` is "none" (for example, Siril left that frame out of the stack). Both paths must be inside the library, frames, stacks or scratch folders. The direction and origin were checked on the M 31 ASI 533MM stack: the 40 brightest stars of a frame land within 2 pixels of a stack star, and the stack's stars land on the frame's, in both directions (`backend/tests/test_map_position.py`, skipped when the files are missing). `image_service.py` also answers `images:measure_detections` (`path`): the stars the astrometry run's star finder detects in one image (`quality.measure_detections`), with `x` and `y` in 1-based pixels, `flux` and `merged`, the count, the kernel width, the image's measured star width and the photometry circle radius. The path must be inside the library, frames, stacks or scratch folders. A stack's stretched `_processed` picture is searched on the linear stack beside it when the two are the same size, since the astrometry run searches the stack and the stretch changes the noise. The answer is kept for the file's path, modified time and size (8 images), so the viewer's Detections overlay is quick to turn on again. `target_service.py` also answers `target:get_frame_statuses` (`target_id`) for the File Browser's Status column: one entry per frame with `state` (`included`, `flagged` for a frame in the stack whose stars the star-shape review finds stretched far more than the others, with its `elongation`, `not_stacked` for a frame taken after the newest stack file was written or when there is no stack, or `set_aside`), and for a set-aside frame its `kind`, `reason` (the stacker's words), `date`, `exposure`, `originalPath` and whether it is `restorable`, plus the review's `typicalElongation`. The library's `quality.frame_statuses` decides each state; the service gives it the newest stack file's time and the wayfinder review's standout frames (none when the review cannot be made). Set-aside frames are listed from the `_excluded` folders because the target's own frame list does not hold them. `target:put_back_frames` (`target_id`, `paths`) moves chosen set-aside frames back through `quality.put_back_set_aside_frames` and answers `{restored}`.
- `infrastructure/` holds shared plumbing: settings, sockets, the scripting terminal (saving a user script sends the `scripts:changed` event so open consoles reload their list; `ScriptingService` also remembers the last 20 console runs, with their printed text cut to 20,000 characters and their figure PNG files, and deletes a run's files when it drops out; `terminal:get_recent_runs` reads them, newest first, and no workspace variables are kept; a run returns only the figures it made or added to, not ones left open by earlier runs, and only runs that did not start in a console, such as an AI agent's, broadcast `terminal:plot_generated`, because a console opens its own run's figures from the reply), the handoff state and the safety guards. `ScriptingService` (`scripting_service.py`) holds the console's shared state and takes its work from four modules: `scripting_workspace.py` (the preloaded names, `help` and name completion), `scripting_runs.py` (running and stopping code, and the run history), `scripting_figures.py` (drawing figures for the browser, saving each run's figures and telling the open windows) and `scripting_library.py` (recipes, saved scripts and documents). The console's helpers live in `console_helpers.py`: `terminal:stop` (Ctrl+C in the terminal) raises `KeyboardInterrupt` in the worker thread that runs the code, so the run ends with the status `stopped` and the workspace stays; `selection` reads the latest pick that Image Processing sends with `ui:set_selection` (kept by `app_selection_service.py`, in memory only); and `show(...)` and `doc(...)` add requests to the run's reply (`app_requests`), which the console window carries out with the app's own navigation.
- `observatory/` serves the telescope, equipment, guiding, imaging, planning and the sequencer. `imaging_service.py` runs `imaging:capture` as a `capture` job on a thread, and `imaging:stop_capture` hands the stop to `control.imaging.stop_capture` (it returns `false` when nothing runs). `observatory_source_service.py` reports and changes the Observatory source setting. The backend builds, starts and removes no world: a launcher (`simulator/launch.py`) does that and runs the backend as its child with `ASTROMETRICS_LAUNCHER` set. `observatory:get_source` reports the source the launcher started the backend with (`ASTROMETRICS_OBSERVATORY_SOURCE`, or `real`), the saved choice, `available` and `unavailable_reason` (false when no launcher runs the backend, or programs are missing, from `ASTROMETRICS_LAUNCH_MISSING_PROGRAMS`), and the failure reason; `commands` is `null`, `running` is `false` and `library_copy` is empty. `observatory:set_source` writes the choice and the backend ends with exit code 75 (`RESTART_EXIT_CODE`) after it stops its services (`backend/observatory_source.py`); the launcher starts the next session with the saved choice. Without a launcher the change is refused. The choice file code and the launch variable names live in `backend/launch_contract.py`, public through `backend/public_interface.py`; that is the one backend module the simulator layer imports. When the simulator fails to start, `source` is `no_telescope` (an older launcher's `offline` is read the same way). `observatory:get_source` also reports `launch`, the read-only `[Launch]` section of the settings in use (`label`, `live_hardware`, `disposable_library`, `offline`, `locked_keys`), or `null` without one; the backend only reports it. `SettingsService` refuses a save that changes a key in `locked_keys`, or the `[Launch]` section; a save that sends the same value back is not a change.
- `processing/` serves ingestion, stacking and image processing, jobs, the frame quality measurement run and the slow stack reviews (`stack_review_service.py`, which starts a preview remake or a stack comparison as a background job and answers with the result or the job to follow).

## Jobs started from outside the app

The AI's job tools (`mcp_servers/backend/app_jobs.py`) call the same RPC methods as the app's buttons, so the backend owns those jobs exactly as for a click. Three services take the extra choices those tools need:

- `processing:stack` (`ImageProcessingService.process_target`) takes the frame list the Stack button sends, or, with no list, the library's frame choice (`kind`, `filter_name`, `first_file`, `last_file`, `since`, `until`, `camera_id`, `focal_length_mm`). The choice is checked first with a plan from `processing.stack(plan_only=True)`, which writes nothing, so a choice that matches no frame is an error and not a failed job. `plan_only` answers with that plan and starts no job. `force`, `denoise`, `denoise_strength` and `star_toning` go to the stack. Either way the job is the one `stacking` job, and `processing:cancel` reaches it, also while it waits for a heavy-work slot: the job stops waiting, runs no stage and stays `cancelled`. A running stack stops too: the frame check and the frame measurement stop within half a second (at most one frame per worker finishes in the background), every other frame loop stops at its next frame, the programs it started (Siril, GraXpert, Cosmic Clarity, StarNet) are ended at once with their helpers, and the earlier stack is put back. The job is logged at info level and sends no failure notification. The job store ignores any later write that would give a cancelled job another status.
- `telescope:sync` and `telescope:sync_logs` (`SyncService`) take `dry_run`, which answers with the library's plan and copies nothing. A real frame or log sync is recorded as a `remote_sync` job (the log sync with the target `logs`), whoever started it, so the job list shows it with its log and progress.
- `analysis:analyze_image` (`AnalysisOrchestrator`) takes `stages`, a list from the library's `ProcessingPipelines.SELECTABLE_ANALYSIS_STAGES` (`astrometry`, `photometry`, `spectroscopy` and `spectral_variation`; any other name is refused). It runs them as one library call inside the one analysis job, so the job can be cancelled and a second start for the target answers `already_running`. The library adds astrometry first when a stage needs it and its result is missing or older than the stack. A stage uses the target's stack when there is one; the sent image files stand in only for a stage whose stack the target lacks. The job's final message lists the stages run, the stages added and the stages skipped with their reasons. Without `stages` the backend chooses, in one place for the app and the AI tools (`_default_stages`): a target with both an imaging and a spectral stack gets photometry and spectroscopy; with no files sent, its one stack decides (photometry or spectroscopy, and a target with no stack is refused); otherwise the file type chooses, as before, and raw spectral frames run the `spectroscopy` stage. With no files sent, a stage with nothing to work on is refused before a job starts. `camera_id` and `focal_length_mm` choose one of the target's stacks by camera and optic through the library's `processing.find_stack_configuration` (an unknown or unclear one is refused with the target's list); another camera's stack gets photometry by default and refuses spectral stages. The reply has `stages` and, for a chosen stack, its `configuration` key. `processing:remake_preview` takes the same `camera_id` and `focal_length_mm`. `spectral_variation` follows the sent raw spectral frames (every spectral frame of the target when none is sent), after the library adds spectroscopy when needed. The Analyze Target menu offers it as Spectral Variation, and a skipped stage's reason is in the job's closing message.
- `processing:check_stack` (`StackReviewService.start_stack_check`) answers what a stack would do with the frames: which it would set aside and why, and the darks, bias and flats each exposure group would use. It takes the same selection as `processing:stack` (`image_files`, or the library's frame choice; both together are refused), turns the listed paths into the target's own frame records, and runs `processing.predict_stack` as a background job because the check reads every frame. Nothing is stacked, moved, stored or saved. The result is a `StackPrediction`.
- `processing:remake_preview` also takes the StarNet choices (`starnet`, `star_strength`, `star_stretch`).
- `processing:list_bright_objects` (`target`, `refresh`) and `processing:set_bright_object` (`target`, `mode`, `simbad_id`, `ra_deg`, `dec_deg`, `major_axis_arcmin`) go straight to the library's processing API. The first lists the nebulae and galaxies SIMBAD places inside the target's stack, or answers with no objects and a message (no plate solution, SIMBAD out of reach); the first call for a stack file asks SIMBAD and later calls read the list saved beside the stack. The second saves which object the preview's masked stretch protects on the target. It makes no picture, so the choice is used the next time the target is stacked or post-processed.

Every job the backend creates (`JobService.create_job`) records the backend's process number and start time as its owner, as a library-run job does. After a restart the startup cleanup (`close_interrupted_jobs`) therefore marks the dead backend's open jobs `interrupted` at once. Cancel (`BaseBackgroundService.cancel_processing`) closes a row nothing runs as `cancelled`: its owner program has ended, or it has no recorded owner (a row from before owners were kept) and this backend has no task for it. A row owned by a different, live program is still refused. The already-running checks for stacking, analysis and ingestion (`get_live_jobs_for_target`) count `started` and `running` rows alike and skip rows with no live owner. A dead job is a status: it is logged at INFO and sends no notification.

The app learns about running jobs from the `processing` part of the `system_state_update` event. A service updates it when it starts or ends one of its own jobs. Every two seconds the telemetry loop (`publish_running_jobs` in `backend/startup.py`) also reads the running jobs from the shared job list and sends the event when they changed. A job that another program records (an MCP library tool, a console script) or that a library call records inside the backend (a preview remake) therefore shows in the job list while it runs. The job list then reloads, as it does for a job the app started.

## Planning services (`observatory/`)

- `plan_service.py` wraps the planning library's plan and package calls for the RPC route. After each write that succeeds, it sends `plan:changed` (session writes) or `packages:changed` (package writes) to every app window. A write from an old revision stores nothing and raises a conflict error that carries the current revision.
- `advisory_service.py` serves the quality advice and night history reads. It only reads. It does no ranking, grouping or sorting.
- `suggestion_refresh_worker.py` is described below.

## Suggestion refresh worker

The planning library keeps a set of suggested observation packages. It creates, updates and deletes them, adds calibration items to tonight's checklist and marks finished packages complete. That work (`refresh_suggestions`) reads the quality numbers, so it must run when they change. `SuggestionRefreshWorker` runs it in the background.

1. A trigger calls `request`. Triggers come after a frame quality measurement run, after a frame sync and from the Refresh suggestions button. A trigger names the targets whose data changed, or none, which means refresh everything.
2. `request` records the targets and starts one background thread if none is running. It never waits and never raises, so it cannot break the announcement that called it.
3. The thread takes everything recorded so far, runs one refresh and looks again. Triggers that arrived during the run get one more run. At most one run is going and one is waiting, however many triggers come.
4. A run that failed is logged, and the worker goes on.
5. After a run that changed something, the worker sends `packages:changed` with the kind `refreshed` and the counts. If the run added checklist items, it also sends `plan:changed` for tonight's session.

## Heavy read limiter

Every RPC call runs on one of a fixed set of worker threads. A slow whole-catalog read that the client has given up on keeps its thread until it finishes. A burst of retries could take every worker and block even a simple status call. `HeavyReadLimiter` (`infrastructure/heavy_read_limiter.py`) stops that in two ways:

- Only a few heavy reads run at the same time. A read that cannot get a place within a short wait fails at once with a retryable "busy, try again" conflict error.
- Identical requests that arrive together share one computation. A later request waits for the answer of the one already running.

The star catalog listings and counts use it (`data/stellar_service.py`). The numbers (reads at once, wait times) are constants at the top of the module. The per-target star counts and class counts are kept until the catalog changes, but an empty answer is never kept: the library may not have been filled yet at start-up, and a kept empty answer showed "0 stars" for every target until it expired. They are sized so that most of the workers stay free and so that a wait ends before the client's own time limit.

## Heavy lane for RPC methods

Python lets only one thread run Python code at a time. When a view opens and a dozen calls that scan the whole library run together, every call, even a light one, waits behind them each time it needs a turn. A TPM run measured calls that should take a millisecond waiting more than a second. `backend/routers/rpc_router.py` lists these scanning methods in `HEAVY_METHODS` (for example `history:nights` and `astronomy:list`). Only `HEAVY_LANE_SLOTS` of them run at once, and the rest wait without taking a worker thread. All other methods run freely. Add a method to the list when a trace shows it busy for more than about 100 ms.

The lane itself lives in `infrastructure/heavy_lane.py`, so the start-up warm-ups can use it too. Encoding a finished reply (`encode_rpc_success_body` in `rpc_protocol.py`) does not use the lane. It runs in the ordinary thread pool, so a finished result never waits behind queued heavy builds.

For exact behavior, read the code.

## Start-up warm-ups

After the app is ready, `backend/startup.py` fills caches in the background, one step after another (the steps are chained in `_warm_up_in_order` in `backend/main_backend.py`). None of them delays `/api/ready`, except the first group.

1. `warm_start_up_caches` loads the star catalog, the Earth-orientation table and the stellar summaries side by side. The splash screen waits for these.
2. `warm_depth_goals` builds the depth goal status of up to three targets, one at a time, by calling the same function as `advisory:depth_goal`. The first target is the one the telescope points at, when the telemetry loop already knows it. The others are the targets with a stacked picture, newest imaged first, which is the target the Image Processing screen opens on. A target appears once. A failure is logged at debug level and skipped.
3. `warm_night_reviews` builds the three newest night reviews.

Each step runs in the heavy lane (`run_heavy`), so a warm-up never adds to the user's first heavy calls. Leaving the app cancels the warm-up before the next step starts. The target the telescope points at is looked up in the library first; a name that is not a library target is skipped.

A failed step only makes the first visit slower, so it is logged as a warning, not an error. The steps read and never write.

## Host check and CORS

`infrastructure/host_check.py` refuses any request whose `Host` header is not one the backend serves. This stops DNS rebinding, where a hostile page makes the browser treat the backend as its own site. `localhost`, `127.0.0.1` and `[::1]` pass with any port. When the backend is bound to a network address (`run_backend.sh --lan`), private-network addresses, `.local` names and this computer's host name pass too. The RPC route sets no CORS headers of its own: the CORS middleware in `main_backend.py` allows only the origins in `session_auth.py`.

## Restart check

Changing the observatory source restarts the backend, so it first asks `Container._running_work` what is running. Stacking jobs, frame downloads, the guide log copy, a target imaging session and automatic downloads that wait for their timer all block the restart. If the check itself fails, the backend counts as busy.

## Measuring new dark and bias frames

The library's rescan of calibration frames does not measure darks and biases, so a new set would stay "Not checked". `ImageProcessingService.measure_new_calibration_frames` starts that measuring (`calibration:measure_frames`, not forced, so only new or changed files are read) as a background job. It is the one place that starts it. Two callers use it: `IngestionService`, after a rescan that added darks or biases, and `SyncService`, after a Bias, Dark or Flat folder sync that filed darks or biases. Adding only lights or flats starts nothing.

Only one such job runs at a time. A request that arrives while one runs is remembered, and the job starts one more pass when it ends, so late frames are not missed. The job writes its own log in the job list. When a pass ends, the service sends `calibration:measured`, and the Calibration Library panel reads its health again.
