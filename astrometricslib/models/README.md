# Models

This folder holds the library's pydantic data structures (pydantic is a Python package for classes with typed, validated fields): the shapes of the data the pipelines produce, store, and hand back to callers. Nothing here does any calculation. A model file defines fields and validation, not behavior.

Terms are defined in the [glossary](../../documentation/Glossary.md). This document also defines each term the first time it appears.

## What each file is for

- `target.py` — `Target` and `FrameRecord`, the records for an astronomical target and its individual raw frames.
- `stellar_source.py` — `StellarObject`, one star's record, and its nested per-domain results.
  - **Photometry.** Photometry is brightness measurement. The results hold the star's light curve, its brightness over time, with per-point flux uncertainties and mid-exposure BJD_TDB times. BJD_TDB is a time scale referred to the center of mass of the solar system, so the light-travel time across the Earth's orbit does not shift the times.
  - **Spectroscopy.** The results include a summary from the extractor (the step that cuts the star's spectrum out of the image): how it measured the sky beside the spectrum and how wide a box it summed. They also include the record of the airmass correction. Airmass measures how much atmosphere the light passed through (1 straight overhead). The atmosphere dims blue light more than red, and more so at higher airmass. Pre-processing therefore scales each spectrum to the airmass of the standard star (the reference star of known spectrum that calibrates the instrument) before classification, and the record says whether it did and, if not, why.
  - **Match verdicts.** The file defines, once each, the limits that turn a spectral match into a verdict: `NO_GOOD_MATCH_RMS`, `UNRELIABLE_MATCH_RMS`, `AMBIGUOUS_RMS_GAP` and `DIFFERS_FROM_CATALOG_SUBTYPES`, with the unit of each in its docstring. A spectral class is the letter of a star's type (O, B, A, F, G, K, M, hottest to coolest); a subtype adds a digit from 0 to 9 within the class, such as G2.
    - The RMS limits are relative RMS values: the root-mean-square difference between the star's spectrum and a reference template, as a fraction of the spectrum's average brightness.
    - The gaps `rms_gap_to_second_best` (subtype level) and `rms_gap_to_next_class` (class level) are differences of two RMS values, not probabilities. A small gap means a second template fits almost as well.
- `spectral_cross_checks.py` — the two records a spectrum's classification keeps beside the template fit: `ReddeningRecord` (the E(B-V) removed before classifying, its source, and the best type with and without dereddening). Dereddening is the removal of the reddening that interstellar dust adds; E(B-V) is the size of that reddening in magnitudes. `LineIndexClassification` holds the type that six line strengths point to, and how far it is from the template-fit type. A line strength here is the depth of one absorption line, a narrow dip in the spectrum where an element in the star's atmosphere absorbs light. `SpectroscopyResult` holds them as `reddening` and `line_index_classification`.
- `measured_line_spread.py` — `MeasuredLineSpread`, a spectrum's own blur (full width at half maximum, in Å and pixels, with scatter) in wavelength bands, measured from its trail width and stored on `SpectroscopyResult`.
- `known_variability.py` — sorts what the catalogs say about a star into known variable, suspected variable, not listed as variable, or unknown. It reads three sources. The first is SIMBAD's object types (SIMBAD is an online database of named astronomical objects). The second is Gaia DR3's `phot_variable_flag` (from the European Space Agency's Gaia star catalog). The third is the AAVSO (American Association of Variable Star Observers) Variable Star Index (VSX), which also lists stars checked and found constant. The answer describes the catalogs' record, not the sky, and `describe_known_variability` names which catalogs were consulted; `unknown` means none were, and is never the same as `not_listed_as_variable`. `is_confirmed_constant` asks for a positive statement (Gaia `CONSTANT` or VSX `CST`), not just silence. The SIMBAD code lists come from SIMBAD's own definition table and need no network.
- `catalog_queries.py` — what the catalog `query` methods return: `TargetQueryResult`, `StarQueryResult` (with `OverlayStar` and `TargetStarCount`), `CalibrationQueryResult`, and `ReindexReport` from `TargetCatalog.reindex_frames`. Only the fields of the chosen `detail` are filled.
- `processing_results.py` — what `ProcessingPipelines` returns: `StackResult` (the frames chosen and, unless only a plan was asked for, the stack and its quality summary), `PreviewRemakeResult` and `ProcessTargetResult`.
- `wavelength_scale.py` — the wavelength zero-point error of a spectrum: the shift of its whole wavelength scale caused by a misplaced zero-order image (the undispersed image of the star). `WavelengthZeroPointRecord` holds the shift for one spectrum, how sure it is, the lines that gave it and whether the pipeline removed it; `WavelengthScaleSummary` holds the run's scatter, which the `wavelength_scale` gate reads.
- `calibration_ingest.py` — the results of checking calibration frames: `FlatSetAssessment` (is one set of flats good enough, and if not, why) and `CalibrationIngestReport` (what a rescan of the calibration library added, per group, with an assessment of each new flat set).
- `calibration_inventory.py` — `CalibrationEntry` and `CalibrationStats`, how many dark, bias and flat frames the calibration library holds for each camera setting (the shape `CalibrationLibrary.get_stats` returns), including each row's binning (such as `1x1`) and, for darks, the sensor temperature. `wayfindinglib/models/equipment_and_site/calibration.py` defines its own, differently shaped `CalibrationEntry` and `CalibrationStats`; merging the two is open as item A10 (duplicated models) in `documentation/plans/REVIEW_ACTION_PLAN.md`.
- `moving_object.py`, `moving_object_config.py` — the data structures for tracking a candidate moving object (asteroid) through the detection cascade, and the settings that control that search. The cascade is the chain of checks a candidate must pass in turn. The first check it fails rejects it (see `pipelines/asteroid_detection/README.md`).
- `camera_profile.py` — what the pipelines need to know about one camera model: saturation threshold, sensor characteristics, and optionally the conversion gain and read noise (electrons) that photometry uses for flux uncertainties. These are stored per camera setting, one `SensorSettingNoise` entry for each gain setting, offset and binning, and a frame uses an entry only when its own setting matches exactly. The conversion gain is in electrons per ADU. ADU (analog-to-digital units) are the camera's raw counts.
- `sensor_noise_measurement.py` — `SensorNoiseMeasurement`, the result of measuring a camera setting's gain and read noise from flat and bias frames: the numbers, their pair-to-pair spread, the frame counts, a source sentence for the camera profile, and the reason when nothing could be measured.
- `applied_camera_profile.py` — `AppliedCameraProfile`, the short copy of a camera profile that each pipeline's quality summary carries, so a reader can see which camera facts a result rests on.
- `provenance.py` — the IVOA (International Virtual Observatory Alliance) Provenance Data Model (PROV-DM) classes recording which run, at what software version, consuming which inputs, produced a given result. See `astrometricslib/drivers/provenance_store.py` for where this is stored and queried.
- `quality/` — the quality records: gate results, batch-wide quality summaries, per-pipeline input and output quality assessments, and the report shapes that quality tools return. See [quality/README.md](quality/README.md).

For exact behavior, read the code.
