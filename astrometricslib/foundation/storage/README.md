# Storage

This folder holds the generic storage plumbing that both libraries share. Nothing here knows about telescopes, targets or stars. It only knows about databases, locks and drives.

Terms are defined in the [glossary](../../../documentation/Glossary.md). This document also defines each term the first time it appears.

## What each file is for

- `local_database.py` — opens and writes SQLite database files on this computer (`connect_db`), and holds the JSON encoder for values SQLite has no column type for (`safe_json_dumps`, `NumpyEncoder`).
- `butler.py` — `Butler`, a generic keyed-model store. It records Pydantic model instances to SQLite tables by id, with get, put and exists operations. Both libraries instantiate it for their catalog and record data. `select_where` reads one ordered page of rows that satisfy a SQL condition, and `count_where` counts such rows. The database filters, orders and cuts the page, so only the rows of the page reach Python. Library code writes the SQL text, and every value that comes from a caller goes in as a parameter. A caller that lists a large table, such as the star catalog, uses these two instead of loading every row. `read_record_field` reads one top-level field of some rows' stored records inside the database, without parsing them. A `DatasetSpec` can name `read_columns` and a `deserializer`, so a record can leave out a field that a column already holds and get it back when the row is read.
- `data_versions.py` — one small counter per kind of library data (`targets`, `quality`, `stars`), kept in a table named `data_versions` in `astrometrics.db`. Every writer adds one to its counter in the same database transaction as its write: the `Butler` when its `DatasetSpec` names a `data_version_kind`, and the quality store. The library reads the counters (`get_library_data_version`) to learn whether anything a cache was built from changed. They and the narrower versions below are read only inside the library (`bump_data_version` and `read_data_versions` stay public through `astrometricslib.drivers` for a database that keeps its own counters, such as `wayfinding.db`): each public data version is an opaque text made from one of them in `pipelines/shared/data_version_texts.py` (`targets.get_data_version` with or without a target, `stars.get_data_version`, `quality.records.get_data_version` with no filter for the quality counter, `targets.get_record_versions`, `quality.records.get_camera_data_version`, `quality.stacks.get_data_version` and `quality.records.get_data_version` with `subject_ids`), so a caller outside the library compares texts and sees no counts or row numbers. `get_target_data_version` covers one target: its stored document (the frame and stack records), its quality measurements and its calibration identities, so a new frame of another target does not change it (`TargetDataVersion`: the count, newest row number, newest time and sum of the row numbers of the measurements, and the document's size and hash). `get_camera_data_versions` sees the measurements and calibration records of named cameras only (with `finished_before_night` it counts only measurements of finished nights, so a frame of the night in progress does not change it), and `get_target_camera_names` says which cameras a target uses. `get_stack_quality_data_version` sees stack-level rows, calibration identities and capture settings, so a new frame of any target does not change it. `get_frame_metric_signs` gives the count, newest row number and row-number sum of one metric's frame rows for each group of frames, and `get_target_document_signs` the size and hash of each target document. A result built from a few metrics of every frame in the library (the capture history of the equipment) uses `quality.records.get_data_version` per metric; the quality store itself reads only the rows added since its last read of those metrics. No version sees data of a camera that the result does not name. Because the counters are in the file, a write by another program counts too. A write made by raw SQL that does not call `bump_data_version` is not seen, and neither is a database file swapped for an older copy, so restore a backup only while the app is stopped. An in-place UPDATE by another process that leaves the count, newest row number and newest time unchanged is not seen either, and the camera version does not see a later edit to a frame record stored in another target's document. With `finished_before_night`, a frame-level row with no night is left out (it may be from tonight); a stack-level row with no night counts. Stack records and frame records live inside the target documents, so they count as `targets`; the rows that record set-aside frames are quality rows. Evidence for the version of a night review and a target report: [validation register](../../../documentation/library_design/validation/wayfinding.md), WAY-D102, WAY-D104 and WAY-D107 (Design estimate, with a measurement on a copy of the real library).
- `process_locks.py` — file locks the operating system enforces, so two programs cannot use the same resource at once (`file_lock`, `acquire_resource_slot`). The resources include a telescope mount, a camera or a copy of Siril. Waiting for a slot has no time limit, but a run given up on (a cancelled job) stops waiting within one poll, and never starts its work even if the slot frees at that moment (`RunAbandonedError`). A slot also gets a small record next to its lock file, naming the process and the work that holds it. A waiter logs who it is behind every five minutes (`describe_slot_holders`). The record is only for people reading logs: the lock alone decides who holds a slot, and a record left by a dead process is not reported.
- `mount.py` — `require_mounted_storage` refuses to write below the `frames_mount_point` setting unless a drive is mounted there. When the setting is empty, nothing is checked.

For exact behavior, read the code.
