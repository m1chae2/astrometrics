# Models

This folder holds the library's pydantic data structures: the shapes of the data the pipelines produce, store, and hand back to callers. Nothing here does any calculation — a model file defines fields and validation, not behavior.

Terms are defined in the [glossary](../../documentation/library_design/Astrometrics_Library_Architecture.md#appendix-b-glossary).

## What each file is for

- `target.py` — `Target` and `FrameRecord`, the records for an astronomical target and its individual raw photographs.
- `stellar_source.py` — `StellarObject` and its nested per-domain results: a star's photometry (brightness measurement: its light curve, the brightness over time, with per-point flux uncertainties and mid-exposure BJD_TDB times; BJD_TDB is a time scale corrected to the centre of mass of the solar system, so light-travel time across the Earth's orbit does not shift the times) and spectroscopy results (including a summary of how the extractor read the sky and how wide its box was, and the record of the airmass correction; airmass measures how much atmosphere the light passed through, 1 straight overhead). It also defines, once each, the limits that turn a spectral match into a verdict (`NO_GOOD_MATCH_RMS`, `UNRELIABLE_MATCH_RMS`, `AMBIGUOUS_RMS_GAP`, `DIFFERS_FROM_CATALOG_SUBTYPES`), with the unit of each in its docstring. The RMS limits are relative RMS values (root-mean-square difference as a fraction of the spectrum's average brightness), and the gaps `rms_gap_to_second_best` (subtype level) and `rms_gap_to_next_class` (class level) are differences of two RMS values, not probabilities.
- `spectral_cross_checks.py` — the two records a spectrum's classification keeps beside the template fit: `ReddeningRecord` (the E(B-V) removed before classifying, its source, and the best type with and without dereddening, the removal of the reddening that interstellar dust adds) and `LineIndexClassification` (the type that six line strengths, the depths of chosen absorption lines, point to, and how far it is from the template-fit type). `SpectroscopyResult` holds them as `reddening` and `line_index_classification`.
- `astrometry_quality.py`, `photometry_quality.py`, `spectroscopy_quality.py` — per-star quality judgments each of those three pipelines attaches to a star's result (for example, how confident a catalog match is, or how good the raw data behind a light curve was).
- `measured_line_spread.py` — `MeasuredLineSpread`, a spectrum's own blur (full width at half maximum, in Angstroms and pixels, with scatter) in wavelength bands, measured from its trail width and stored on `SpectroscopyResult`.
- `stacking_quality.py` — the two judgments a stacking run attaches to its summary: whether the inputs were sound (`StackingInputQuality`) and whether the stack came out well (`StackingOutputQuality`).
- `known_variability.py` — sorts what the catalogs say about a star into known variable, suspected variable, not listed as variable, or unknown. It reads three sources: SIMBAD's object types (SIMBAD is an online database of named astronomical objects), Gaia DR3's `phot_variable_flag` (from the European Space Agency's Gaia star catalogue), and the AAVSO (American Association of Variable Star Observers) Variable Star Index (VSX), which also lists stars checked and found constant. The answer describes the catalogs' record, not the sky, and `describe_known_variability` names which catalogs were consulted; `unknown` means none were, and is never the same as `not_listed_as_variable`. `is_confirmed_constant` asks for a positive statement (Gaia `CONSTANT` or VSX `CST`), not just silence. The SIMBAD code lists come from SIMBAD's own definition table and need no network.
- `quality_summary.py` — the batch-wide `*QualitySummary` classes each pipeline run produces, and the shared base class every one of them extends.
- `gate_result.py` — `GateResult` and `GateStatus`, one record per run-level quality check (a gate): `passed`, `failed` or `not_checked`, with the measured value, the limit it was compared with, and where the limit came from. A check that could not run is `not_checked` with its reason, never `passed`. Each `*QualitySummary` keeps its gates in `gates`.
- `catalog_queries.py` — what the catalog `query` methods return: `TargetQueryResult`, `StarQueryResult` (with `OverlayStar` and `TargetStarCount`), `CalibrationQueryResult`, and `ReindexReport` from `TargetCatalog.reindex_frames`. Only the fields of the chosen `detail` are filled.
- `processing_results.py` — what `ProcessingPipelines` returns: `StackResult` (the frames chosen and, unless only a plan was asked for, the stack and its quality summary), `PreviewRemakeResult` and `ProcessTargetResult`.
- `quality_reports.py` — what `QualityDiagnostics` and `ProcessingPipelines.stack_summary` return: `RawFrameCheckReport`, `InputQualityReport`, `SpectralFrameCheckReport`, `StackQualityReport` and `StackSummary`. These only describe; they never change a target.
- `gaia_xp_comparison.py` — the comparison of one calibrated spectrum with Gaia DR3's low-resolution XP spectrum (`GaiaXpComparison`, with per-band residuals), stored on `SpectroscopyResult.gaia_xp_comparison`, and the roll-up for a whole run (`GaiaXpRunSummary`). The calculation is in `pipelines/spectroscopy/post_processing/compare_to_gaia_xp.py`.
- `wavelength_scale.py` — the wavelength zero-point error of a spectrum: the shift of its whole wavelength scale caused by a misplaced zero-order image (the undispersed image of the star). `WavelengthZeroPointRecord` holds the shift for one spectrum, how sure it is, the lines that gave it and whether the pipeline removed it; `WavelengthScaleSummary` holds the run's scatter, which the `wavelength_scale` gate reads.
- `calibration_ingest.py` — the results of checking calibration frames: `FlatSetAssessment` (is one set of flats good enough, and if not, why) and `CalibrationIngestReport` (what a rescan of the calibration library added, per group, with an assessment of each new flat set).
- `calibration_inventory.py` — `CalibrationEntry` and `CalibrationStats`, how many dark, bias and flat frames the calibration library holds for each camera setting (the shape `CalibrationLibrary.get_stats` returns), including each row's binning (such as `1x1`) and, for darks, the sensor temperature. `wayfindinglib/models/equipment_and_site/calibration.py` defines its own, differently shaped `CalibrationEntry` and `CalibrationStats`; merging the two is open as plan item A10.
- `excluded_frames.py` — the descriptions of light frames the stacker sets aside: `SetAsideFrame` (one frame, with the measurements behind the decision), `QuarantinePreview` (what the check would move) and `RestoreReport` (what a restore listed or moved back).
- `stack_comparison.py` — the result of comparing two stacks: `StackMeasurements` (sky level, pixel noise, large-scale flatness, star width, zero fraction of one stack) and `StackComparison` (two of them, the change in each, and a sentence for each).
- `moving_object.py`, `moving_object_config.py` — the data structures for tracking a candidate moving object (asteroid) through the detection cascade, and the settings that control that search.
- `camera_profile.py` — what the pipelines need to know about one camera model: saturation threshold, sensor characteristics, and optionally the conversion gain (electrons per ADU; ADU, analog-to-digital units, are the camera's raw counts) and read noise (electrons) that photometry uses for flux uncertainties.
- `provenance.py` — the IVOA (International Virtual Observatory Alliance) Provenance Data Model (PROV-DM) classes recording which run, at what software version, consuming which inputs, produced a given result. See `astrometricslib/drivers/provenance_store.py` for where this is stored and queried.

For exact behavior, read the code — the code is always the source of truth.
